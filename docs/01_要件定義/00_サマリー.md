# Phase 1 サマリー — premake

> 病院内の空きスペース・空き病室を、アートメイク施術を行う看護師がスポット利用できるようにする予約マッチングプラットフォーム（Web 先行・手数料モデル・将来モバイル対応）。

---

## 1. エグゼクティブサマリー

premake は、医療機関の遊休スペースとアートメイク施術を行う看護師をマッチングする B2B/B2B2C プラットフォームである。コアの法令対応として、貸主医療機関の医師が施術ごとに電子指示書を発行する **A 案（指示医モデル）** を採用し、医師法・保助看法上の要件を盤石化。

ステークホルダーは 5 役（看護師 / 施設管理者 / 指示医 / 運営 / 法人管理者）+ ゲスト（利用客）+ AI Coding Agent。**全 88 機能**（P0 84 / P1 4）を MVP として一気に作り切る方針で、**目標は 2-3 ヶ月でパブリック β（20 施設 × 100 看護師）**。

UX・デザイン・セキュリティ・法令対応を最優先とし、開発スピードは AI エージェント活用で確保。決済は **Stripe Connect**、認証は **メール+パスワード + Google OAuth + MFA**。多店舗チェーンクリニックも法人 (Organization) 配下に複数施設 (Facility) を持てるモデルで対応。

## 3. 機能サマリー

| 優先度 | 件数 | 主要機能 |
|--------|------|----------|
| **P0** | 84 件 | A 認証（13）/ B 法人施設（9）/ C 検索予約（10）/ D 指示書記録（8）/ E 決済（9）/ F メッセージ（4 β）/ G レビュー（4 β）/ H 運営（8）/ I 公開（4）/ J ダッシュボード（5）/ K 顧客予約（7）/ 横断（3） |
| **P1** | 4 件 | FR-60 お知らせ配信 / FR-79 フィーチャーフラグ / FR-80 ヘルスチェック / FR-86 施設別キャンセルポリシー上書き |

### コアクリティカルパス（β に必須の連鎖）
**A 認証 → B 施設 → C 予約 → D 指示書 → E 決済 → K 顧客予約**

### β表記機能
- **F メッセージ・G レビュー** は実装するが UI 上「β」バッジ表示。テストは E2E 除外、スモークのみ。

## 7. Phase 2（外部設計）への引き継ぎ

### 7.1 Phase 2 で深掘りすべき技術設計事項
- **DB 設計**: 88 機能のエンティティ・関連・RLS ポリシー（特に多テナント分離）
- **API 仕様**: REST or GraphQL の選定、エンドポイント一覧
- **認証基盤**: Clerk / Supabase Auth / 自前のいずれを採用するか
- **決済設計**: Stripe Connect の Direct/Standard/Express の選定、Authorization → Capture → Transfer のステートマシン詳細
- **電子署名・タイムスタンプ**: X.509 + RFC 3161 の実装方式
- **画像・PDF 暗号化**: KMS、署名付き URL、immutable lock
- **検索インデックス**: PostgreSQL FTS / Meilisearch / Algolia の選定
- **通知基盤**: Resend / SendGrid / Twilio / AWS SNS の選定
- **フィーチャーフラグ**: ConfigCat / LaunchDarkly / 自前
- **テスト戦略**: P0 コアの E2E、F/G β機能のスモーク範囲

### 7.2 未解決の課題（Phase 2 で詰める）
- 看護師の Stripe Connect 連携の扱い（スペース利用料は施設 Connect、利用客事前決済は看護師 Connect、両立する設計）
- 多店舗法人の手数料按分ルール
- 指示書 PDF の改ざん検知の具体実装
- カウンセリングのみ完結時の料金体系
- 利用客の重複予約検知の業務ルール

### 7.3 Phase 1 で確定しておくべきだが未確定の事項
- システム概要の 1 行サマリー [仮決定]
- 法務・税務の本確認（β中に並行で進める前提）
