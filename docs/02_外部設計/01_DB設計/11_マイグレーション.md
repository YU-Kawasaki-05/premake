## 3. シードデータ

| テーブル | 目的 | 件数 |
|---|---|---|
| consent_templates (platform) | 法令必須項目を持つ共通同意書 | 1 |
| questionnaire_templates (platform) | 共通問診票（アレルギー・妊娠・既往歴等） | 1 |
| term_versions | 利用規約 v1 / プライバシー v1 / 特商法 v1 | 3 |
| feature_flags | β機能のフラグ初期値 (show_review_beta=true 等) | ~10 |
| users (ops) | 運営アカウント数名（環境変数から取り込み） | 1〜3 |

### 3.1 開発用シード追加（seed.sql のみ）
- `users` (nurse / facility_admin / doctor のテストアカウント) | 5〜10 |
- `facilities` (テスト施設) | 2〜3 |
- `spaces` | 5〜10 |
- `bookings` (各 status を網羅) | 20+ |

> **本番には決して開発用シードを流さない**。`SUPABASE_ENV=production` で seed.sql 実行を block する hook を設置。

## 4. ロールバック方針

- 各マイグレーションは可能な限り **可逆**（`up.sql` + `down.sql`）。
- ただし、Postgres の制約上、データ消失を伴う UP は一方通行（`down.sql` は backup → drop に止める）。
- 本番でのロールバックは原則禁止。前進修正（forward migration）で対応。

## 5. マイグレーション運用

- **ローカル**: `supabase db reset` で全 migration 実行 + seed
- **CI**: PR 時に migration の syntax チェック + dry-run
- **本番**: GitHub Actions から `supabase db push` で適用、適用前に Supabase の DB Branch でリハーサル
- **マイグレーション失敗時**: 即座にロールバック（trans 単位）+ Slack 通知
