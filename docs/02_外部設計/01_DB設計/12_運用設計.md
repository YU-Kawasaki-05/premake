### 1.1 Storage 容量試算
- 施術前後写真: 平均 2MB × 8 枚 × 100,000 件 = 1.6 TB（1 年）
- 指示書 PDF: 50KB × 100,000 = 5 GB
- 同意書 PDF: 30KB × 100,000 = 3 GB
- 看護師 / 医師免許: 1MB × 数千件 = 数 GB
- スペース写真: 500KB × 数百枚 × 200 施設 = ~10 GB

> Supabase Pro 無料 100 GB → 早期に Pro Plus / 別ストレージ検討。

## 2. 暗号化対象カラム（pgcrypto）

| テーブル | カラム | 理由 |
|---|---|---|
| mfa_settings | totp_secret_encrypted | TOTP secret |
| customer_bookings | customer_name, customer_name_kana, customer_email, customer_phone | 個人情報 |
| prescriptions | customer_name | 個人情報 |
| treatment_records.body 内顧客識別情報 | application 層で暗号化 | |

> Supabase は **Storage 全体が AES-256 at-rest 暗号化**。さらに署名付き URL のみアクセス。

### 2.1 暗号化方式

```sql
-- 暗号化キーは Vault や environment variable から取得
-- INSERT
INSERT INTO customer_bookings (customer_name, ...) VALUES (
  pgp_sym_encrypt('山田 太郎', current_setting('app.encryption_key')),
  ...
);

-- SELECT
SELECT pgp_sym_decrypt(customer_name::bytea, current_setting('app.encryption_key'))
FROM customer_bookings WHERE id = ...;
```

> 実装は Server Action 層で wrap。Client 側に raw bytes を返さない。

| バケット | 内容 | 公開設定 | 注意 |
|---|---|---|---|

| `prescriptions` | 電子指示書 PDF | private | immutable lock 推奨 |
| `consents` | 同意書 PDF | private | |
| `chat-attachments` | チャット添付 | private、TTL 7 日 | |
| `profile-images` | 看護師/施設プロフ | public-read | |
| `signatures` | 自署サイン画像 | private | |

### 3.1 バケットポリシー例（Supabase）

```sql
-- treatment-records は対象 booking の関係者のみアクセス可
CREATE POLICY "treatment_records_read"
ON storage.objects FOR SELECT
USING (
  bucket_id = 'treatment-records'
  AND auth.uid() IN (
    SELECT nurse_user_id FROM treatment_records
    WHERE id::text = (storage.foldername(name))[1]
    UNION
    SELECT doctor_user_id FROM prescriptions p
    JOIN booking_sessions bs ON bs.prescription_id = p.id
    JOIN treatment_records tr ON tr.booking_session_id = bs.id
    WHERE tr.id::text = (storage.foldername(name))[1]
  )
);
```

## 4. データ越境チェック（FR-78 連動）

各テーブルに対し以下を [`../03_権限設計.md`](../03_権限設計.md) の RLS で保証:

| 越境パターン | 防止策 |
|---|---|
| 別法人の facilities 参照 | facilities.organization_id でフィルタ |
| 別施設の bookings 参照 | bookings.facility_id でフィルタ |
| 別看護師の自分予約以外閲覧 | bookings.nurse_user_id = auth.uid() |
| 利用客が他客の K 予約閲覧 | customer_bookings は ゲストセッショントークン経由のみ照会可 |
| 一般ユーザーが audit_log 参照 | RLS で ops 以外 全 SELECT 拒否 |
| Service Role の暴発 | RLS をバイパスする経路は Edge Function / Server Action 経由のみ、Client SDK は anon key |

## 5. パフォーマンス考慮

### 5.1 ホットなクエリ
- 看護師ダッシュボード: bookings (nurse_user_id, status, created_at)
- 施設ダッシュボード: bookings (facility_id, status, created_at)
- 検索: spaces (search_vector + location)
- 通知未読カウント: notifications (user_id, read_at IS NULL)
- ジョブ取得: worker_jobs (status='pending')

### 5.2 partition 戦略
- `audit_log` 月次（既述）
- `worker_jobs` 月次（成功ジョブは 30 日後にアーカイブ）
- `notifications` 半年（古いものはコールド層へ）

### 5.3 マテリアライズドビュー候補
- `mv_facility_monthly_kpi`: 施設月次 KPI（FR-66, FR-85）
- `mv_nurse_monthly_revenue`: 看護師月次売上（FR-65）

→ 月次バッチで `REFRESH MATERIALIZED VIEW CONCURRENTLY`。

## 6. バックアップ・DR

- **Supabase 自動バックアップ**: Daily（Pro plan 7 日 / Pro Plus 14 日）
- **WAL アーカイブ**: PITR（Pro Plus 以降）
- **手動バックアップ**: 重要マイグレーション前に必ず実施
- **災害時 RTO**: 4 時間以内（Phase 2 NFR-AVL）
- **災害時 RPO**: 1 時間以内（Phase 2 NFR-AVL）

## 7. 監査・コンプライアンス

- **保存期間**: 医療記録系（prescriptions / treatment_records / customer_consents）= 7 年（医療法）
- **監査ログ**: 7 年（FR-76）
- **個人情報保護**: 削除要求時は当該ユーザーの medical_records を削除せず、PII 列を pseudonymize（仮名化）
