# API 仕様 — 設計方針

> [00_index.md](00_index.md) に戻る

## 1. アーキテクチャ

### 1.1 実装スタイル
DEC-20 (Next.js 15 + Server Actions) に基づき、論理エンドポイントを 3 種類に分類する:

| 種類 | 実装 | 用途 |
|---|---|---|
| **Server Action** | `app/actions/{domain}/{name}.ts` | 認証ユーザー (U-01〜U-06) の内部操作。型安全、フォーム連携、RSC との統合 |
| **Route Handler (内部)** | `app/api/{path}/route.ts` | アップロード・ファイル配信・SSE 等、Server Action では扱いにくい用途 |
| **Route Handler (公開)** | `app/api/c/{path}/route.ts` `app/api/webhooks/{path}/route.ts` | ゲスト（利用客）/ Webhook 受信 / 将来モバイル API |

> 本ドキュメントは「論理 API 仕様」として REST 風に統一記述。Server Action 実装の場合は HTTP `POST /api/internal/{action}` と同等とみなす（実装は関数呼び出し）。

### 1.2 将来モバイル拡張
将来的な iOS / Android クライアント (DEC-04) のため、以下を方針:
- Server Action のロジック層はモバイルから直接呼べないため、**ビジネスロジック層を独立**させる:
  ```
  app/actions/bookings/createBooking.ts   ← Web 用（Server Action）
  src/services/bookings.ts                ← ロジック層（共有）
  app/api/v1/bookings/route.ts            ← モバイル用（Route Handler、Phase 後半で実装）
  ```
- モバイル API は `/api/v1/...` 配下、Bearer トークンで認証

## 2. URL 構造

### 2.1 ルート
- `/api/v1/...` — 認証ユーザー向け Route Handler（内部 + 将来モバイル）
- `/api/webhooks/...` — Stripe / その他外部 Webhook
- `/api/c/...` — 利用客（ゲスト）公開エンドポイント
- `/api/internal/...` — Server Action 相当の内部 API（実装は Server Action 関数）

### 2.2 リソース命名
- スネークケースは使わない、URL は **kebab-case**
- リソースは複数形（`/bookings`, `/spaces`）
- ネストは 2 階層まで（`/spaces/{id}/availability` OK、`/spaces/{id}/availability/rules/{rid}` は NG → `/space-availability-rules/{rid}` に）

## 3. リクエスト / レスポンス共通仕様

### 3.1 ヘッダ

```
Authorization: Bearer {jwt}              # モバイル / Route Handler
Cookie: sb-access-token=...              # Web (Supabase Auth)
Content-Type: application/json
X-Idempotency-Key: {uuid}                # 副作用ある POST に必須
X-Request-Id: {uuid}                     # トレース用
Accept-Language: ja                      # 多言語拡張時用
```

### 3.2 成功レスポンス

```json
// 単一リソース
{
  "data": { "id": "...", "..." }
}

// 一覧（cursor-based pagination）
{
  "data": [ ... ],
  "page": {
    "cursor": "eyJ...",       // 次ページが無ければ null
    "limit": 20,
    "total_estimate": 240
  }
}

// アクション完了（副作用ありで返却データ少ない場合）
{
  "data": { "ok": true, "id": "..." }
}
```

### 3.3 エラーレスポンス

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります",
    "details": [
      { "field": "email", "code": "INVALID_FORMAT", "message": "メール形式が正しくありません" }
    ],
    "request_id": "req_abc123"
  }
}
```

### 3.4 エラーコード一覧（共通）

| code | 状況 | HTTP |
|---|---|---|
| VALIDATION_ERROR | バリデーション失敗 | 400 |
| UNAUTHORIZED | 未認証 | 401 |
| FORBIDDEN | 権限なし | 403 |
| NOT_FOUND | リソース不在 | 404 |
| CONFLICT | 重複 / 状態不整合 | 409 |
| RULE_VIOLATION | ビジネスルール違反 | 422 |
| RATE_LIMITED | レート制限 | 429 |
| EXTERNAL_SERVICE_ERROR | Stripe / Twilio 等の障害 | 502 |
| INTERNAL_ERROR | 想定外のエラー | 500 |

### 3.5 ドメイン固有エラーコード（例）
| code | 該当 EP | 意味 |
|---|---|---|
| LICENSE_NOT_APPROVED | EP-C002 等 | 看護師免許審査未完了で予約申込 |
| BOOKING_SLOT_TAKEN | EP-C002 | 予約時刻が他予約と衝突 |
| INVITATION_EXPIRED | EP-A005 | 招待トークン失効 |
| MFA_REQUIRED | EP-A012 | MFA 入力フェーズへ |
| STRIPE_AUTH_FAILED | EP-C006 | Stripe オーソリ失敗 |
| PRESCRIPTION_NOT_REQUIRED | EP-D003 | 既に発行済み |
| ANOMALY_REQUIRES_MD_REVIEW | EP-D012 | 異変記録は医師確認必須 |

## 4. ページネーション

- **方式**: cursor-based（`cursor` クエリパラメータ）
- **デフォルト**: `limit=20`、最大 `limit=100`
- **応答**: `page.cursor` が `null` で末尾

```
GET /api/v1/bookings?limit=20&cursor=eyJ...
```

## 5. 認可（共通）

- すべての認証ユーザー API は **JWT 検証 + role チェック + RLS** の三段階。
- RLS の詳細は [03_権限設計.md](../03_権限設計.md)。
- Service Role キーはサーバーのみ、絶対にクライアントに漏らさない。

## 6. レート制限

| 用途 | 制限 |
|---|---|
| 認証エンドポイント (login / signup) | 同一 IP: 10 req/min |
| パスワードリセット要求 | 同一メール: 5 req/h |
| SMS 送信系 | 同一電話番号: 5 req/h |
| 通常 API | 認証ユーザー: 600 req/min |
| 公開検索 | 匿名 IP: 60 req/min |

実装は Vercel KV (Upstash Redis) + middleware で。

## 7. 冪等性

- すべての副作用ある `POST` は `X-Idempotency-Key` ヘッダ必須。
- DB に `idempotency_keys` テーブルか各テーブルに `idempotency_key` カラムを持たせ、同一キーの再送は前回レスポンスを返す。
- Server Action は内部で UUID 自動生成可（フォーム送信の二重 submit 対策）。

## 8. バージョニング

- 内部 Route Handler: `/api/v1/...`
- breaking change は `/api/v2/...` を立ち上げ、旧版を deprecation 期間（最低 90 日）残す
- Server Action は呼び出し元と同 deploy なのでバージョニング不要

## 9. CORS

- 内部 API: 同一オリジンのみ
- 公開 API（`/api/c/...`、`/api/v1/...`）: 将来モバイル向けに必要なドメインを allowlist
- Webhook 受信: CORS 不要（サーバー間）

## 10. ログ・監査

- すべての mutation API は監査ログ（[`audit_log`](../01_DB設計/09_tables_G_運営監査.md)）に記録。
- 個人情報を含むレスポンスはアプリケーションログに出力しない（FR-78）。
- request_id を全リクエストに付与し、Sentry / Axiom と連携。

## 11. Validation

- 入力検証は **zod schema** を全エンドポイントに必須。
- スキーマは `src/schemas/{domain}/{name}.ts` に集約、Server / Client で共有。
- Server Action は zod safeParse で受け、失敗時 `VALIDATION_ERROR` を返す。

```typescript
// 例: src/schemas/auth/signup.ts
export const signupSchema = z.object({
  email: z.string().email().max(255),
  password: z.string().min(12).regex(/[A-Z]/).regex(/[a-z]/).regex(/[0-9]/).regex(/[^A-Za-z0-9]/),
  name: z.string().min(1).max(50),
  name_kana: z.string().regex(/^[゠-ヿ\s]+$/).max(50),
  phone: z.string().regex(/^\+81-?\d{2,3}-?\d{4}-?\d{4}$/),
  agreed_to_terms: z.literal(true),
});
```
