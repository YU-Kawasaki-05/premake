# 権限設計 — ロール定義

> [00_index.md](00_index.md) に戻る

各ロールの境界・割り当て方法・主要権限を定義。

---

## ROLE-01: nurse（看護師, U-01）

### 割り当て
- `EP-A001` (メールサインアップ)
- `EP-A002` (Google OAuth)

### 状態によるサブ権限
| state | can do |
|---|---|
| email_unverified | プロフィール編集、メール再送 |
| email_verified, license_status=pending_review | 免許審査中バナー、検索閲覧不可 |
| email_verified, license_status=approved, can_book=true | フル機能（検索 / 予約 / 公開ページ管理 / 施術記録投入） |
| status=suspended | ログイン不可 |

### 主要権限
- 自分関連の bookings / payments / treatment_records / reviews
- 公開ページ (nurse_pages) 自分のみ編集
- 他看護師のデータは閲覧不可

---

## ROLE-02: facility_admin（施設管理者, U-02）

### 割り当て
- 招待受諾 (`EP-A003`)
- 申請承認 → 招待発行 → 受諾

### テナント
- `app_metadata.facility_id` で 1 施設に紐付き

### 主要権限
- 自施設の facilities / spaces / space_pricing / space_availability_*
- 自施設の bookings / 承認・拒否
- 自施設の指示医割当
- 自施設の Stripe Connect
- 自施設の予約 chat スレッド
- 自施設のレビュー閲覧

### 制約
- 他施設のデータ閲覧不可
- 法人レベルダッシュボードは閲覧不可（法人管理者のみ）
- 監査ログは自施設のみ閲覧可

---

## ROLE-03: doctor（指示医, U-03）

### 割り当て
- 施設管理者 / 法人管理者 / 運営からの招待
- M:N で複数施設兼任可（`doctor_facility_assignments`）

### テナント
- `app_metadata.facility_id` は主たる施設、`doctor_facility_assignments` で他施設も
- RLS では `doctor_facility_assignments` を JOIN して許可判定

### 状態によるサブ権限
- license_status=pending_review: 指示書発行不可
- license_status=approved: prescription_issue_enabled=true、aal2 で発行可

### 主要権限
- 自分が担当する prescriptions の発行（EP-D003）
- 担当施設の prescriptions / treatment_records / consent / questionnaire 閲覧
- 担当施設の bookings 閲覧

### 制約
- 編集権限は限定（電子指示書発行 / 施術記録確認のみ）
- 他施設の医療記録は閲覧不可

---

## ROLE-04: ops（運営, U-04）

### 割り当て
- 自社内、手動作成のみ
- MFA 必須 (FR-07 BR-01)

### 主要権限
- 全テーブル閲覧可（PII マスキング適用、フル表示は閲覧理由必須）
- ユーザー審査・凍結・復活
- 違反案件・取引監視・返金
- CSV エクスポート（PII 含む時は二名承認）
- 代理オンボーディング (FR-87)
- お知らせ配信
- フィーチャーフラグ管理
- 監査ログ閲覧

### 制約
- aal2 必須（多くの重要操作）
- 全アクションが監査ログ記録
- 個別データへの **書き込み** は限定（凍結・復活・返金・代理入力等）

---

## ROLE-05: org_admin（法人管理者, U-06）

### 割り当て
- 法人申請 → 運営承認 → 招待
- 招待受諾 (`EP-A003`) で `app_metadata.organization_id` 設定

### テナント
- `app_metadata.organization_id` で 1 法人に紐付き

### 主要権限
- 自法人 organizations の編集
- 自法人配下の facilities 全て CRUD
- 自法人配下の spaces / bookings / payments 横断閲覧
- 自法人配下の施設管理者・指示医を招待
- 自法人レベル Stripe Connect

### 制約
- 他法人のデータ閲覧不可
- 個別 facility の細かい編集は施設管理者でも可（権限重複あり）
- 直接予約や施術記録投入はできない

---

## ROLE-06: guest（利用客, U-05）

> Supabase Auth に user としては登録されない（DEC-12）

### 認証
- SMS OTP（電話番号）
- 各操作で email + booking_number + OTP の三要素

### 主要権限
- 自分の `customer_bookings` の閲覧・変更・キャンセル
- 自分の同意書 / 問診票記入（記入用トークン経由）
- 自分の事前決済

### 制約
- 他の利用客のデータ閲覧不可
- 看護師・施設のデータ閲覧不可
- 検索 / 横断機能なし

---

## ROLE-07: service（サーバー専用）

### 用途
- Stripe Webhook 処理
- バックグラウンドジョブ
- 代理オンボーディング
- マイグレーション

### 主要権限
- RLS バイパス（Service Role）

### 制約
- Client から呼び出し不可
- 全アクション監査ログ記録
- 環境変数からのみキー取得、コードに hardcode 禁止

---

## ロール間の重複と優先順位

ある操作で複数ロールが該当する場合（例: org_admin と facility_admin が同じ facility を編集）、両方とも許可。RLS は OR 条件で書く。

```sql
-- 例: facilities の UPDATE は org_admin（自法人配下）または facility_admin（自施設）
CREATE POLICY "facilities_update" ON facilities FOR UPDATE
  USING (
    auth.jwt() -> 'app_metadata' ->> 'role' = 'ops'
    OR (
      auth.jwt() -> 'app_metadata' ->> 'role' = 'org_admin'
      AND organization_id::text = auth.jwt() -> 'app_metadata' ->> 'organization_id'
    )
    OR (
      auth.jwt() -> 'app_metadata' ->> 'role' = 'facility_admin'
      AND id::text = auth.jwt() -> 'app_metadata' ->> 'facility_id'
    )
  );
```
