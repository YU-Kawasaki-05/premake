# テスト戦略 — premake

> Phase 1 の AC（受入基準）を機械的にテストへ紐付け、Phase 4（整合性チェック）の対象となるカバレッジ網羅率を算出可能にする。

---

## 1. テストピラミッド目標

| レイヤー | 比率 | 範囲 |
|---|---|---|
| **Unit** | 70% | ビジネスロジック・スキーマバリデーション・ユーティリティ |
| **Integration** | 25% | Server Actions / API Routes / DB アクセス / RLS |
| **E2E** | 5% | コアユーザーフロー（P0 のみ） |

### カバレッジ目標
- **行カバレッジ**: 80%
- **ブランチカバレッジ**: 70%
- **重要モジュール（業務ロジック・RLS）**: 90%

### カバレッジ除外
- `src/types/*` 型定義
- `supabase/migrations/*` マイグレーション
- `*.config.ts`, `*.d.ts`
- `app/(marketing)/*` 静的ページ
- 自動生成コード（Supabase generated types 等）

## 2. レイヤー別テスト方針

### 2.1 Unit テスト

- **対象**: BR-XX-XX を持つロジック / スキーマバリデーション / ユーティリティ
- **ツール**: Vitest
- **配置**: 対象ファイルと同階層に `*.test.ts`
- **必須対象**:
  - `src/schemas/**/*.ts` の zod スキーマ全件
  - `src/services/**/*.ts` のビジネスロジック関数
  - キャンセルポリシー計算（FR-41）
  - 料金計算（FR-15）
  - セッション間隔バリデーション（FR-88）

```typescript
// 例: src/services/cancelPolicy.test.ts
import { describe, test, expect } from 'vitest';
import { calculateRefund } from './cancelPolicy';

describe('calculateRefund', () => {
  test('7 日前以前なら 100% 返金', () => {
    expect(calculateRefund({ amount: 10000, hoursBeforeStart: 8 * 24 })).toBe(10000);
  });
  test('24 時間以内なら 0% 返金', () => {
    expect(calculateRefund({ amount: 10000, hoursBeforeStart: 12 })).toBe(0);
  });
});
```

### 2.2 Integration テスト

- **対象**: Server Actions、Route Handlers、DB アクセス、RLS ポリシー
- **ツール**: Vitest + Supabase ローカル（CLI で起動）
- **配置**: `tests/integration/`
- **必須対象**:
  - 全 P0 機能の Server Action（FR-XX 単位）
  - 全テーブルの RLS ポリシー（越境アクセスが拒否されることを検証）
  - Stripe Webhook 受信処理（モック署名）

```typescript
// 例: tests/integration/bookings/createBooking.test.ts
test('看護師が予約申込できる (FR-21 / AC-21-01)', async () => {
  const { user } = await signUpAndApprove({ role: 'nurse' });
  const result = await createBookingAction({ space_id, sessions });
  expect(result.status).toBe('pending_approval');
});

test('別看護師の予約は閲覧できない (RLS)', async () => {
  const userA = await createNurseUser();
  const userB = await createNurseUser();
  const bookingA = await createBookingAs(userA);
  await expect(getBookingAs(userB, bookingA.id)).rejects.toThrow('NOT_FOUND');
});
```

### 2.3 E2E テスト

- **対象**: Phase 1 の AC のうち P0 のコアフロー
- **ツール**: Playwright
- **配置**: `tests/e2e/`
- **必須対象**:
  - 認証フロー（FR-01 〜 FR-04, FR-07）
  - コア予約フロー（FR-19 → FR-21 → FR-22 → FR-29 → FR-33 → FR-34 → FR-38）
  - 顧客予約フロー（FR-69 → FR-70 → FR-32 → FR-72）
  - 運営審査フロー（FR-08 → FR-54）

```typescript
// 例: tests/e2e/booking-flow.spec.ts
test('看護師が予約成立から施術完了まで（FR-21 → FR-29 → FR-33 → FR-34 → FR-38）', async ({ page }) => {
  // 1. 看護師ログイン
  // 2. 検索 → 予約申込
  // 3. 別ブラウザコンテキストで施設承認
  // 4. 別ブラウザで指示医発行
  // 5. 施術記録投入
  // 6. 指示医確認
```

### 2.4 Visual Regression テスト（β 後検討）

- **判断**: β 段階は手動 QA で代替、本番化で導入
- **ツール候補**: Playwright + Percy / Chromatic

### 2.5 Load Test

- **判断**: β 段階は不要（スケール要件 NFR-SCL-01 に達していないため）
- **本番前**: k6 で検索 / 予約申込 / Webhook 受信のスループット確認

### 2.6 a11y テスト

- **対象**: P0 全画面
- **ツール**: axe-core / Playwright + axe-playwright
- **CI 必須**: 自動チェックで a11y violation 0 件

### 5.1 Factory パターン
```typescript

export function createNurseUser(overrides?: Partial<User>) {
  return {
    role: 'nurse',
    email: `nurse-${randomId()}@test.local`,
    name: '山田 H',
    license_status: 'approved',
    can_book: true,
    ...overrides,
  };
}
```

### 5.2 Seed
- 開発 / Integration テスト用: `supabase/seed.sql`
- E2E テスト用: 各テストの `beforeEach` で factory を使い動的生成

### 5.3 クリーンアップ
- Integration: 各テスト末に `transaction rollback`
- E2E: `tests/e2e/setup.ts` で `truncate` + factory 再投入

### 5.4 テスト用 Stripe / Twilio
- Stripe: テストモード API キー、`stripe trigger` でイベント送信
- Twilio: Magic Numbers / テスト OTP（固定）

## 6. CI パイプライン

| トリガー | ジョブ | 並列度 | 失敗時 |
|---|---|---|---|
| PR 作成 | Lint + Type Check | 1 | Block |
| PR 作成 | Unit | 4 並列 (vitest --shard) | Block |
| PR 作成 | Integration | 2 並列 | Block |
| PR 作成 | E2E (smoke のみ: 認証 + 予約承認) | 1 | Block |
| PR 作成 | a11y check | 1 | Warn |
| main merge | E2E (full suite) | 4 並列 | Block, ロールバック検討 |
| main merge | Lighthouse audit | 1 | Warn |
| nightly | E2E + Visual Regression | 4 | Slack 通知 |
| weekly | Load Test (本番前のみ) | - | Slack 通知 |

### 主要 CI 設定
- Vercel Preview Deploy で PR ごとに環境発生
- Supabase は CI 用 instance を `pnpm exec supabase start` で起動 or 専用 branch project
- E2E は preview deploy URL に対して実行
- Test Reporter（GitHub Actions）でカバレッジ可視化

## 7. テスト品質ルール

### 7.1 命名規則
- Unit: `describe('関数名', ...)` + `test('〇〇すると△△になる', ...)`
- Integration: ユースケース単位で記述、AC-ID をコメントに含める
- E2E: ユーザー視点で「何をして何が起こるか」

### 7.2 AC との紐付け
**AI 生成テストには `// @verifies AC-XX-XX` を冒頭コメントに必須**:

```typescript
// @verifies AC-21-01
test('看護師が予約申込できる', async () => { ... });

// @verifies AC-21-02, AC-21-05
test('既予約と同時刻の申込はエラー', async () => { ... });
```

これにより Phase 4 整合性チェックが grep で AC ↔ テストの双方向マッピングを検出可。

### 7.3 AAA パターン
```typescript
test('xxx', () => {
  // Arrange
  const input = ...;
  // Act
  const result = doSomething(input);
  // Assert
  expect(result).toBe(...);
});
```

### 7.4 フレーキーテスト対応
- 再現確認できるまで quarantine（test.skip + Issue 化）
- 修正できないテストは削除 or rewrite
- 確率失敗 50% 以上ならマージ block

### 7.5 テスト独立性
- 各テストは順序依存しない
- Shared state は明示的に setup / teardown
- 並列実行可能（外部リソースは isolation）

## 10. Phase 4 整合性チェック連動

Phase 4 のチェックは以下を自動測定:

1. 全 P0 AC が `// @verifies AC-XX-XX` 付きテストに対応している（カバレッジ %）
2. 全 FR の `features/FR-XX_*.md` に `実装ファイル` / `テストファイル` が記入済み
3. `_index.yml` の `ac_test_mapping` の `status` が `pending → passing` に遷移
4. RLS ポリシーが全テーブルで定義済み（漏れ検出）
