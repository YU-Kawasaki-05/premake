# ローンチ計画 — premake

> フィーチャーフラグ + 段階展開で β→本番化までを安全に進める。初日から計測・回収できる状態でローンチする。

---

## 1. ローンチ戦略

### 1.1 形態
**フィーチャーフラグ + 段階展開**（クローズドα → クローズドβ → 限定公開 → 一般公開）

### 1.2 段階展開計画

| フェーズ | 期間 | 対象ユーザー | 機能範囲 | フィーチャーフラグ |
|---|---|---|---|---|
| **α (内部)** | Sprint 11-12 (Week 11-12) | 運営 + テストユーザー数名 | 全機能（テスト目的） | `internal_only=true` |
| **クローズドα** | Week 12-13 | 1 施設 × 1 看護師（運営代理オンボーディング） | 全機能 | `closed_alpha=true` |
| **クローズドβ** | Week 14-19（約 6 週）| 20 施設 × 100 看護師（DEC-07） | 全機能 | - |
| **限定公開** | β 後 4 週 | 限定された新規 100 施設募集 | 全機能 | `public_signup_enabled=true (限定)` |
| **一般公開** | 限定後 | 全員 | 全機能 + LP (DEC-10) | `general_release=true` |

### 1.3 移行判断基準

クローズドβ → 限定公開:
- 適法性違反インシデント = 0 件
- エラー率 < 0.5%
- 主要 KPI が目標達成（後述）
- ユーザーフィードバック反映完了

限定公開 → 一般公開:
- 限定公開期間で問題なく運用
- 運営体制が複数施設を捌けることを実証
- LP / マーケティング準備完了

## 2. 計測する成功指標（KPI）

| KPI | 計測方法 | β 目標 | 計測ツール |
|---|---|---|---|
| **β 期間中の予約成立件数** | `bookings WHERE status='completed'` 集計 | 100 件以上 | Metabase |
| **適法性違反インシデント** | violations + audit_log | **0 件** | 運営ダッシュボード |
| **看護師 NPS** | 月次アンケート | +30 以上 | Google Forms / 内製 |
| **施設 NPS** | 月次アンケート | +30 以上 | 同上 |
| **エラー率** | Sentry | < 1% | Sentry |
| **API p95 レイテンシ** | Vercel Analytics | < 500ms | Vercel |
| **稼働率** | Vercel + Supabase 監視 | > 99.5% | uptime monitor |
| **GMV（取扱高）** | payments.amount 集計 | 月次成長率 | Metabase |
| **プラットフォーム手数料収益** | platform_revenue | 月次 | Metabase |
| **施設稼働率** | bookings vs 公開時間 | 30%+ | Metabase |
| **キャンセル率** | bookings.status=cancelled | < 10% | Metabase |
| **平均施術単価** | payments.amount / completed 件数 | - | Metabase |
| **Lighthouse スコア** | CI 自動測定 | 90+ | Lighthouse CI |

## 6. ロールバック計画

### 6.1 想定シナリオ

| シナリオ | 検知 | ロールバック方法 |
|---|---|---|
| 重大バグでサービス停止 | Sentry エラー急増 | Vercel 1-click rollback to previous deployment |
| マイグレーション失敗 | Production DB 異常 | バックアップから復元 + forward migration で修正 |
| 個人情報漏洩 | 監査ログ異常 / 通報 | サービス一時停止 + 影響範囲調査 + 法的通知 |
| 決済不整合 | Stripe Webhook 失敗急増 | Stripe Capture 機能を kill switch で停止、手動で reconcile |

### 6.2 ロールバック手順（共通）

1. **Slack #incidents で宣言**
2. 影響範囲確認 + ステータスページ更新
3. ロールバック実行
4. 動作確認
5. Post-mortem 作成

### 6.3 データ整合性確保

- マイグレーション後のロールバックは原則 forward migration（過去の migration を revert しない）
- 重大マイグレ前は手動スナップショット必須
