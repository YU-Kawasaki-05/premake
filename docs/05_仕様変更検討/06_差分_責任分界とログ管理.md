## 1. 何が変わるか（要約）

| 観点 | 現行 | 新方向性 |
|---|---|---|
| 医療事故・副作用の一次責任 | 不明瞭（看護師 / 施設のいずれか） | **医師・クリニック** が中心 |
| 施術記録の管理主体 | 看護師中心、施設も閲覧 | **クリニック中心**（診療録の一部） |
| 同意書の管理主体 | プラットフォーム経由 | **クリニックの自由診療契約の一部** |
| premake のシステム責任 | 範囲不明瞭 | システム障害・情報漏えいに限定明示 |
| 監査ログ | 標準（FR-76） | **医療情報安全管理ガイドライン (厚労省 第 6.0 版) 準拠** |
| 個人情報の取扱 | 標準 PII 保護 | **要配慮個人情報・診療情報として強化** |

## 2. 責任分界マトリクス [法務確認資料 §3 ベース]

| 論点 | 一次責任 | premake 役割 |
|---|---|---|
| 施術可否判断 | **医師・クリニック** | 判断しない |
| 医師指示書発行 | **医師・クリニック** | 発行システム提供（FR-29） |
| 施術実施 | **看護師** | 業務指示なし |
| 施術場所・衛生 | **クリニック** | 設備情報の登録支援のみ |
| 患者説明・同意 | **医師・クリニック** | 同意書フォーム提供（FR-32） |
| 施術記録・写真 | **クリニック中心** | **保管補助** |
| 決済・返金 | **クリニック**（売主） | システム支援、自社決済代行ではない |
| 事故・副作用対応 | **クリニック・医師** | 連絡補助 |
| 広告・プロフィール | **表示主体ごと** | 規制チェック支援 |
| **システム障害** | **premake** | 一次責任 |
| **情報漏えい (システム起因)** | **premake** | 一次責任、医療情報安全管理ガイドラインに従う |

## 3. 施術記録の管理主体 → クリニック中心へ

### 3.1 現行 → 新方向性の比較

| 項目 | 現行 | 新方向性 |
|---|---|---|
| データ所有者 | 看護師 | **クリニック**（診療録に該当） |
| 物理的保管 | Supabase Storage | 同左、ただし **クリニックの委託先** として premake |
| 閲覧権限 | 看護師・施設管理者・指示医 | **クリニックの院内規程に従う**、premake は閲覧管理 |
| 保存期間 | 7 年 | **7 年（医療法 同左）** |
| 削除権限 | premake | **クリニック判断**（医療記録保存義務の範囲内で） |

### 3.2 RLS の変更

施術記録 (treatment_records) の RLS を以下に再構成:

```sql
-- 現行
CREATE POLICY "tr_select" ON treatment_records FOR SELECT USING (
  auth.is_ops()
  OR nurse_user_id = auth.uid()
  OR facility_id = auth.current_facility_id()
  ...
);

-- 新方向性: クリニックを中心に再構成
CREATE POLICY "tr_select" ON treatment_records FOR SELECT USING (
  auth.is_ops()
  -- クリニック側（医師・施設管理者）が全て閲覧可
  OR facility_id = auth.current_facility_id()
  OR auth.doctor_belongs_to_facility(facility_id)
  -- 看護師は自分の施術のみ閲覧可（クリニックから業務委託で施術した記録）
  OR (
    nurse_user_id = auth.uid()
    AND EXISTS (SELECT 1 FROM nurse_facility_engagements
                WHERE nurse_user_id = auth.uid()
                  AND facility_id = treatment_records.facility_id
                  AND status IN ('active', 'paused', 'terminated'))
  )
);
```

### 3.3 患者本人による閲覧

- 患者（利用客）は **クリニックに対して** 自分の診療録の開示を請求できる（医療法の権利）
- premake は **クリニックの依頼を受けて** 該当データをエクスポート（FR-58 拡張）
- patient 自身が premake に直接アクセスして閲覧する機能は **設けない**（運用が複雑化、医療機関主導が原則）

## 4. 同意書のクリニック契約化

### 4.1 同意書の改訂方向

| 項目 | 現行 | 新方向性 |
|---|---|---|
| タイトル | premake の同意書 | **「{クリニック名} におけるアートメイク施術についての同意書」** |
| 同意先 | プラットフォーム経由で看護師 | **クリニック** |
| 必須項目 | 法令ベース | 同左 + **クリニックを医療提供主体として明示** |
| 保管 | Supabase Storage | 同左、所有者はクリニック |
| バージョン管理 | platform / facility / nurse | **platform / clinic** に簡素化、nurse 個別テンプレは削除候補 |

### 4.2 FR-31 同意書テンプレートの整理

- **owner_type='nurse'** は削除（看護師個人のテンプレートは持たない）
- **owner_type='facility'** が中心、クリニックがカスタマイズ
- **owner_type='platform'** は法令必須項目を含む基礎テンプレート

### 4.3 同意書記入 (FR-32) のフロー変更

- 同意書は **「クリニック X の自由診療同意書」** として再構成
- 看護師 H が施術担当として記名（情報提供）
- premake は記入フォーム提供 + PDF 化 + 保管補助

## 5. 監査ログ → 医療情報安全管理ガイドライン対応

### 5.1 厚労省「医療情報システムの安全管理に関するガイドライン 第 6.0 版」への準拠

新方向性では、premake が **医療情報の保管・処理を行う事業者** として、厚労省ガイドラインに準拠する必要がある。

### 5.2 既存 FR-76 監査ログとの整合

| ガイドライン要件 | 現行 FR-76 対応 | 追加対応 |
|---|---|---|
| 全アクセス記録（アクセスログ） | ✓ | - |
| 改ざん防止（追記専用） | ✓ | - |
| 保存期間 7 年 | ✓ | - |
| ハッシュチェーン | ✓ | - |
| **委託元（クリニック）への定期報告** | × | **追加: 月次アクセスレポート** |
| **委託契約での明示** | × | **追加: クリニック ↔ premake 契約でアクセスログ提供義務** |
| **アクセス権限の最小化** | △ | RLS で実現済、追加運用ルール明文化 |
| **2 要素認証** | △ | 医療情報アクセス時 aal2 強化（指示医・記録閲覧時） |

### 5.3 追加機能候補

| 仮機能 ID | 機能名 | 用途 |
|---|---|---|
| **FR-NEW-20** | クリニック向け月次アクセスレポート | 当該クリニックの記録への全アクセス履歴を月次 PDF 化 |
| **FR-NEW-21** | 患者の自己情報開示請求受付 | クリニック経由で患者の診療情報開示を補助 |
| **FR-NEW-22** | 委託契約に基づく安全管理措置の文書化 | クリニック向け契約書に「premake の安全管理体制」明示 |

## 6. 個人情報の取扱：要配慮個人情報・診療情報

### 6.1 個人情報保護法上の整理

| 種別 | 現行 | 新方向性 |
|---|---|---|
| 一般個人情報 (氏名・電話・メール) | ✓ 暗号化保護 | 同左 |
| **要配慮個人情報** (病歴・施術歴) | △ 言及あり | **明示・厳格管理** |
| **診療情報** (医師指示・施術記録・写真) | △ 暗号化済 | **クリニック委託として管理** |

### 6.2 プライバシーポリシー (FR-62) の改訂方向

| 項目 | 改訂内容 |
|---|---|
| 取得情報 | 「要配慮個人情報を取得する」を明示、根拠は本人同意 |
| 取扱主体 | **クリニックが利用目的を定め、premake は委託先として処理** |
| 第三者提供 | クリニック ⇔ premake の関係は「委託」であり「第三者提供」ではない旨明示 |
| 保管期間 | 7 年（医療記録）+ 退会時の取扱 |
| 開示請求 | クリニック経由で請求可能 |
| 委託先（再委託） | Supabase / Vercel / Resend / Twilio / Stripe 等を明示 |

### 6.3 同意取得の強化

- サインアップ時の同意 → 細分化（「要配慮個人情報の取得・利用」「医療情報の保管」「クリニックへの提供」の項目別同意）
- 看護師サインアップ時にも「業務委託契約に基づき施術記録を提供すること」を明示同意

## 7. 事故・副作用対応のフロー

### 7.1 既存設計の維持と拡張

[Phase 1-2 FR-56 違反検知・対応 / FR-33 施術記録投入] を維持しつつ:

- 事故・副作用報告は **クリニック・医師に即時通知**（運営にも通知）
- premake は通知補助のみ、医療上の対応はクリニック
- **重大事故時の運営行動 runbook** を新規追加

### 7.2 新規 runbook: S-06 重大事故・副作用発生

```
docs/runbooks/S-06-medical-incident.md（新規）

【検知】
- treatment_records.anomaly_notes に重大事象が記録
- 関係者からの直接通報

【初動】
1. クリニック・医師に即時通知（既存）
2. **運営に通知**（重大度判定）
3. 当該予約・施術を suspended (継続不可状態) に
4. 関係者（看護師・指示医・施設管理者）にも通知
5. 必要に応じて他の関係予約も一時停止

【調査】
- クリニックが医学的調査の主体
- premake はシステムログ・関連データの提供
- 個人情報保護委員会への通知の要否を法務確認

【記録】
- 全行動を audit_log に詳細記録
- インシデントレポートを作成（社内）
```

## 10. 思考の足跡

### 10.1 検討した別案

#### 別案 X: 施術記録を premake 中心管理にする
- 不採用理由: 医療提供主体がクリニック、診療録の所有者もクリニック。法的整合性が崩れる

#### 別案 Y: 看護師が独自に診療録を管理
- 不採用理由: 看護師は診療録の作成主体になれない（医師法・医療法）

### 10.2 残された問い

- **要配慮個人情報の取得同意**: サインアップ時か、施術前か、両方か
- **アクセスログの患者開示請求**: 患者が自分の情報へのアクセス履歴を知る権利の取扱
- **海外クラウド利用の明示**: Supabase / Vercel が海外サーバの場合の越境移転の同意
- **インシデント発生時の患者通知**: 個人情報漏えい時の通知義務（個情委ガイドライン）

### 10.3 弁護士に確認したい論点

1. 看護師個人事業主と **委託契約** vs 医療法上の「**従業者**」の境界
2. premake が **医療情報の保管委託先** として満たすべき安全管理基準（厚労省ガイドライン §6 関連）
3. **個人情報漏えい時の通知義務**（個人情報保護法 第 26 条）の運用
4. **要配慮個人情報の取得同意** の取得方法・タイミング
5. 海外クラウド事業者（Supabase が AWS、Vercel が AWS / Cloudflare 等）の **越境移転** の取扱
