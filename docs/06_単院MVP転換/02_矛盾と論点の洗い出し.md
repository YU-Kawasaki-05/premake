## 1. 事業モデルレベル

### M-1. 🟢 旧仕様のマッチングプラットフォーム前提は失効している

- **矛盾**: docs/01〜03 の 88 機能は「外部看護師がスペースを検索・予約し、運営が審査し、手数料 15% を取る」ツーサイドマーケット前提。弁護士見解はこのスキーム自体に禁止リスクを指摘し、6/28 検討でも「マーケットプレイス構築はやるな」と結論済み。
- **解消**: 旧仕様のうちマッチング・審査・手数料按分・スペース検索・レビュー・チャット(FR 数で約半分)を**凍結**と明示する。docs/01〜03 は「参照資産」に格下げし、要件定義 v2 を正とする。
- **残作業**: User 追認 → 決定事項ログに「DEC-37: 単院向け予約管理システムへの転換」として記録。

### M-2. 🟢 6/28「アートメイク前提の実装はやるな」 vs 今回「アートメイク予約システムを作る」

- **矛盾(見かけ上)**: 6/28 の Decision Memo は「売り物が決まる前の DB/API 実装は投機」と明言。今回はまさにその実装に入る。
- **解消**: 状況が変わった。「クリニックが欲しいと言っている」は 6/28 検証プランの「医師が何で埋めたいかを聞く」への回答が得られた状態であり、投機ではなく**需要シグナルへの応答**。ただし 6/28 の教訓は実装に反映する:
  1. **器は業種非依存**(予約対象メニューの抽象化)→ B/M/治験に同じ器を流用
  2. **クリニック前面**(看護師個人を前面にしない)
  3. 検証設計を組み込む(利用実測・機能要望ログ)
- **注意**: 「1院が欲しいと言った」は N=1 のオポチュニティであり、6/28 の枠組みでは「コンシェルジュ MVP → 一般化テスト」の入口に過ぎない。**このシステム開発 = 事業の確定ではない**ことを実装計画上も明示する(器に投資し、アートメイク固有部分は薄く)。

### M-3. 🟡 「SaaS はビジネスとして成り立たない」見立てと、開発着手の整合

- **論点**: 6/28 確定事項「純オペ SaaS は競合密で勝てない → 見送り」。今回作るものは形式上まさに予約 SaaS。
- **解消の方向**: 今回の開発の目的関数を「SaaS 売上」に置かない。位置づけは:
  1. **信頼関係の深化**(入口の実行)
  2. **器の建造**(B/M/治験に流用できる予約・顧客基盤)
  3. **検証**(クリニック運用への食い込み度、拡張需要の観測)
- **未解決**: このクリニックとの商業条件(無償 / 有償 PoC / 成果報酬等)。6/28 の検証基準は「1院から**有償** pilot 実コミット」だった。無償提供は WTP 検証を放棄することになる。→ [03_確認事項](03_確認事項リスト.md) Q7

### M-4. 🟡 「もっと簡単にマネタイズする方法」の具体化が未着手

- **論点**: User 言及の「もっと簡単なマネタイズ」が何を指すか未定義。候補: (a) B(メーカー試験会場)への早期展開、(b) M(既存客クロスセル)基盤化、(c) 予約データを起点にした集客支援、(d) 単純な月額 SaaS 料。
- **影響**: 器の抽象化の優先順位(どの方向の拡張を最初に楽にしておくか)に影響。
- **対応**: 確認事項 P1 として質問。ただし MVP のデータモデル(テナント + メニュー抽象化 + 患者マスタ)はどの候補でも共通に必要なので、**実装はブロックしない**。

## 2. 法務・コンプライアンス

### L-1. 🔴 「医者の先生がちゃんといる」の粒度 — 施術体制の確認

- **論点**: 弁護士見解の手堅い解釈は「**医療機関が雇用している看護師とともに医師が施術**」(= 施術中医師常駐・緊急対応体制)。User は「問題ない」と判断しているが、システム設計に必要な粒度で確認したい:
  - 施術者は誰か: (a) 医師本人 / (b) 雇用看護師(医師が診察・指示・常駐) / (c) 外部(業務委託)看護師
  - (c) が混ざる場合、弁護士見解のリスクが残存し、契約管理機能の要否も変わる
- **システムへの影響**: スタッフのデータモデル(雇用スタッフのみか、外部施術者の契約状態管理が要るか)、指示書ワークフローの必須度、免許管理の要否。
- → [03_確認事項](03_確認事項リスト.md) Q1

### L-2. 🟢 premake の立ち位置が「院内業務ツール」になり、法務リスクが激減する

- **整理**: 単院向け予約管理システム(クリニックが自院の患者・スタッフを管理する SaaS)であれば:
  - **職業紹介・労働者派遣・募集情報等提供のいずれにも非該当**(人と雇用を仲介しない)
  - 患者→クリニック直接決済なら、弁護士指摘の「患者→premake 支払い」問題(職安法 43 条の 3)も**発生しない**
  - premake は純粋なソフトウェアベンダー。旧リスク登録簿の RISK-01(法令違反)/RISK-02(医療提供とみなされる)は大幅低減
- **残る法務論点**(消えないもの):
  1. **医療広告**: 患者向け公開予約ページの広告該当性・限定解除要件(→ L-3)
  2. **医療情報の安全管理**: 問診・施術記録・写真は要配慮個人情報/診療情報。3省2ガイドラインへの配慮、クリニックとの個人情報取扱を含む利用契約
  3. **利用規約・プライバシーポリシー・特商法表記**(オンライン決済導入時)
- **対応**: 単院ツールとしての整理を弁護士に一度確認するのが安全(軽い確認で済む見込み)。タイミングは公開予約ページの仕様確定時が効率的。

### L-3. 🟡 患者向け公開予約ページと医療広告規制

- **論点**: 患者が Web から予約できるページは医療広告に該当しうる。掲載内容による:
  - 予約機能 + 施術名・料金・注意事項のみ → 限定解除要件を満たしやすい(リスク小)
  - 症例写真(ビフォーアフター)、看護師の指名・実績 → 限定解除要件の厳格な充足が必要。体験談は原則不可
- **6/28 の結論**: 「クリニック前面・症例は限定解除準拠・クリニック内での看護師指名」なら成立しうる。
- **推奨**: MVP は**症例なし・予約機能中心**の最小構成で出し、症例ギャラリー・指名は限定解除要件チェックリストを整備してから Phase 2 で追加。
- → [03_確認事項](03_確認事項リスト.md) Q5

### L-4. 🟡 医療情報(問診・記録)の管理主体と premake の受託者性

- **論点**: 問診票・施術記録は クリニックの診療情報。premake(運営者 = User)はその取扱いを受託する立場になり、クリニックとの契約(利用規約 + 個人情報の取扱条項 or 業務委託契約)が必要。
- **対応**: MVP リリース前にクリニックとの利用契約書(簡易版でよい)を用意する。旧 docs/00_共通/premake_法務確認資料 の §契約関係が下敷きに使える。
- **技術面**: 旧設計の RLS + 暗号化 + 監査ログ + PII マスキングの基本線は流用(Supabase で実現可能)。保存期間(旧仮決定: 7年)も踏襲候補。

## 3. プロダクトスコープ

### S-1. 🔴 「予約管理システム」の中身が未定義

- **論点**: クリニックの「欲しい」の中身が文書化されていない。可能性は:
  - (a) **患者向けオンライン予約**(Web 予約受付、リマインダー、キャンセル)
  - (b) **院内のスケジュール・台帳管理**(受付が使う予約台帳、施術室・スタッフの稼働管理)
  - (c) 両方
- **影響**: MVP の画面構成・工数・医療広告対応の要否が根本的に変わる。現在の運用(紙? Google カレンダー? 他 SaaS?)と困りごとが要件の源泉。
- → [03_確認事項](03_確認事項リスト.md) Q2(最重要)

### S-2. 🟢 予約対象メニューの抽象化(確認不要の設計判断)

- **判断**: 「拡張しやすく」の User 指示から、予約対象は `services`(メニュー)として抽象化する。アートメイク(眉/アイライン/リップ、カウンセリング、リタッチ)は初期データとして投入。B(メーカー試験枠)や他メニューも**データ追加だけで**扱える器にする。
- **やりすぎない線**: 治験の GCP 対応等の専用機能は作らない。「メニュー・所要時間・料金・必要書類(問診/同意書)の組み合わせ」が変わるだけで対応できる範囲に留める(過剰抽象化の回避)。
- **UI**: 第一弾はアートメイクの業務語彙で作る(汎用語彙の無機質な UI にしない)。→ Q4 で確認

### S-3. 🔴 決済のスコープ

- **論点**: MVP に決済を含めるか。
  - (a) 現地決済のみ(システムは金額記録のみ or 関知しない)→ 最速・法務論点最小
  - (b) Stripe オンライン事前決済 → 特商法表記・返金ポリシー・Webhook 整備が必要
- **弁護士見解との関係**: 患者→クリニック(クリニック自身の Stripe アカウント)への直接決済であれば問題ない。「患者→premake」の資金フローだけ避ける。
- → [03_確認事項](03_確認事項リスト.md) Q3

### S-4. 🟡 指示書・施術記録・同意書の投入時期

- **論点**: 旧 D カテゴリ(電子指示書・施術記録・同意書)は設計資産として価値が高く、規制強化時代の「適法運用の証跡」としてクリニックへの提供価値にもなる。ただし MVP に入れると重い(電子署名・PDF・TSA 等)。
- **推奨**: MVP = 予約 + 患者 + 問診まで。指示書・記録・同意書の電子化は Phase 2(クリニックの既存運用—紙カルテ/既存電カル—と併用でスタート)。
- **確認**: クリニックが「予約管理」に何を含めているか次第で前後する。→ Q2 の回答に依存

### S-5. 🟢 患者マスタが新たに必要(旧仕様にない中核概念)

- **整理**: 旧 DEC-12 は「ゲスト予約のみ・会員登録なし」で患者を都度データとして扱った。単院の予約管理では**院内から見た患者マスタ**(リピート・リタッチ履歴、名寄せ、連絡先)が本質価値。患者自身のログインは引き続き不要(ゲスト予約 + 院内で名寄せ)。
- **判断**: `patients` テーブルをテナント配下の中核エンティティとして新設。確認不要で v2 要件に織り込む。

### S-6. 🟡 患者との連絡チャネル

- **論点**: 旧設計はメール(Resend)+ SMS(Twilio)。日本の美容系クリニックの実務では **LINE が事実上の標準**の可能性が高い。リマインダーの到達率に直結。
- **推奨**: MVP はメール必須 + SMS任意。LINE 公式アカウント連携(通知・予約導線)は クリニックの現運用を聞いてから Phase 2 で判断。
- → 確認事項 P1

## 4. 技術・実装

### T-1. 🟢 技術スタックは旧決定を踏襲(確認不要)

- Next.js(App Router)+ TypeScript + Supabase + Vercel + Tailwind + shadcn/ui + RHF/zod + Resend + Sentry。旧 DEC-20〜29 の選定理由は単院 SaaS でも全て有効。
- **後ろ倒し・不採用**: Twilio SMS(必要になってから)、Stripe Connect 按分(不要)、TSA 電子署名(指示書フェーズ)、PostGIS / FTS 検索(不要)、Axiom(Sentry のみで開始)、Upstash/reCAPTCHA(公開フォーム次第)。
- 実装時にバージョンは最新安定版を再選定(Next.js 15 系→現行安定版、React 19、Tailwind v4 等)。

### T-2. 🟢 マルチテナント設計を最初から入れる(確認不要の設計判断)

- 全テーブルに `clinic_id`(テナントキー)を持たせ、RLS でテナント分離。単院運用でも 1 テナントとして扱う。
- 根拠: User 指示「拡張しやすく」。2院目以降・B/M 展開時にスキーマ変更なしで追加できる。旧 60 テーブル設計の RLS 知見が流用でき、増分コストは小さい。
- 法人(organization)階層は**入れない**(単院に過剰)。必要になったら clinics の上に足す。

### T-3. 🟢 旧設計資産の流用マップ

| 旧資産 | 流用度 | 備考 |
|---|---|---|
| bookings + booking_sessions(セッションモデル) | ◎ 骨格流用 | カウンセリング→施術→リタッチのステップ列 |
| questionnaire_templates / responses | ◎ | 問診票はほぼそのまま |
| consent / prescriptions / treatment_records | ○ Phase 2 で流用 | 所有者をクリニックに単純化 |
| notifications / worker_jobs / audit_log | ◎ | 基盤系はそのまま |
| users / facilities | △ 再設計 | facilities → clinics(テナント)、ロール体系縮小 |
| spaces / space_availability | △ 変形 | 「外部貸しスペース」→「院内リソース(施術室/ベッド)+ 営業時間・枠」に単純化 |
| 検索 / 審査 / レビュー / チャット / Connect 按分 | ✕ 凍結 | |
| 画面設計(04_画面設計) | △ | トーン&コンポーネント方針は参考。画面構成は作り直し |
| テスト戦略 / 開発ガイドライン(@implements 規約) | ◎ | そのまま採用 |

## 5. 検証設計(ビジネス)

### V-1. 🟡 この開発で何を検証するか

6/28 の枠組みに接続した検証仮説を実装に織り込む:

| 仮説 | 計測方法(システムに組み込む) |
|---|---|
| H1: 予約管理はクリニックの実ペイン(オポチュニティでなくペイン) | 週次アクティブ利用(受付/スタッフのログイン・操作イベント)、システム外予約(電話→手入力)の残存率 |
| H2: 患者はオンライン予約を使う | 公開ページ経由予約比率、離脱ポイント |
| H3: 有償でも使い続ける(WTP) | 商業条件の設計(Q7)+ 継続利用 |
| H4: 器は他用途に伸びる | クリニックからの機能要望ログ(要望を記録する運用/機能)→ B/M 方向のシグナル検出 |

- 軽量なイベント計測(自前テーブル or Vercel Analytics)を MVP から入れる。

### V-2. 🟡 Kill / Double-down 条件の再設定

- 6/28 の Kill 条件「遊休が極薄 + 医師がどの本命にも乗らない」は今回のスコープでは未判定のまま。
- 本開発向けの条件(案、User と要すり合わせ):
  - **Kill**: 導入後 4 週間で週次利用が定着しない(受付が紙/既存運用に戻る)
  - **Double-down**: 日次利用が定着 + クリニックから拡張要望(スタッフ追加・他メニュー・集客系)が自発的に出る + 有償化に合意
