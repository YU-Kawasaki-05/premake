## P0 — 実装をブロックする確認(4 件)

### Q1. クリニックの施術体制

**質問**: 施術は誰が行うか?
- (a) 医師本人が施術
- (b) 雇用している看護師が施術(医師が事前診察・指示、施術中も院内に常駐)
- (c) 外部(業務委託)の看護師も施術する

**なぜ聞くか**: 弁護士見解(6/7)の手堅い解釈は (a)(b) のみ。(c) が混ざると法的リスクが残存し、システムにも契約状態管理・免許管理が必要になる。
**システムへの影響**: スタッフのデータモデル、指示書ワークフローの必須度。
**推奨**: —(事実確認。(b) を想定してドラフトを作成中)

**回答(2026-07-07)**: 基本的には雇用看護師。ただし**業務委託契約の人もいる可能性あり**(その場合も医師と面識があり指示構造はある)。
**設計への反映**: スタッフモデルに雇用区分(`employment_type: employed / contracted`)を属性として持つ。premake は斡旋・仲介をしない(クリニックが自分で連れてくる看護師の予約・運用を支えるに徹する = 6/28 結論と整合)ため職安法系リスクなし。業務委託者の契約状態管理は Phase 2 で要否判断。

### Q2. 「予約管理システム」の中身と現在の運用

**質問**: クリニックが欲しいのはどちらか?
- (a) 患者向けオンライン予約 + 院内の予約・スケジュール管理の両方
- (b) まず院内管理のみ(受付が電話等で受けた予約を台帳管理)
- (c) まず患者オンライン予約のみ

あわせて: 現在の予約管理方法(紙 / Google カレンダー / 他システム)と、一番の困りごとは?

**なぜ聞くか**: MVP の画面構成・工数・医療広告対応の要否が根本的に変わる。要件の源泉。
**推奨**: (a)。予約管理の省力化の核は患者導線(受付の電話対応・リマインダーの自動化)にあるため。
**回答(2026-07-07)**: **患者予約 + 院内管理 + 看護師が場所(施術枠)を予約できる仕組み**の 3 層。
**設計への反映**: 「スタッフ(看護師)が院内の部屋×時間帯の施術枠を自ら確保する」機能を MVP スコープに追加(v2-05b)。業務委託看護師が自分の顧客を持つ実態に対応。患者予約はその枠(または受付が作った枠)に対して入る。ただし公開ページの見せ方は**クリニック前面**を維持(看護師個人の集客ページにはしない = 弁護士見解)。

---

### Q3. 決済のスコープ

**質問**: MVP に決済機能を入れるか?
- (a) 現地決済のみ。システムは料金表示と会計メモ程度(推奨)
- (b) Stripe オンライン事前決済も MVP に含める
- (c) 決済不要(完全に関知しない)

**なぜ聞くか**: (b) は特商法表記・返金ポリシー・Webhook 整備が付随し MVP が重くなる。患者→クリニック(クリニック自身の Stripe)直接決済なら法務上は問題ない。
**推奨**: (a) で開始し、決済は Phase 2。キャンセル・無断キャンセル対策として「事前決済 or デポジット」の要望が強い場合のみ MVP に繰り上げ。
**回答(2026-07-07)**: **決済機能なし**。料金は表示してもよいが受付(支払処理)はしない。料金を書くかどうか自体も任意(患者向けオンライン予約を実運用で開放するかがまだ未確定のため)。
**設計への反映**: 決済機能ゼロ。`services.price` は保持しつつ**メニューごとの料金表示フラグ**で出し分け。患者向け公開予約は**テナント設定 `public_booking_enabled` でオン/オフ**でき、オフでも院内管理システムとして完全に機能する設計にする。

### Q4. 予約対象メニューの範囲

**質問**: 第一弾の予約対象は?
- (a) アートメイクのみ(UI・語彙もアートメイク特化。器は抽象化しておく)(推奨)
- (b) クリニックの全メニュー(美容医療全般)を最初から扱う

**なぜ聞くか**: 問診票・カウンセリング→施術のフロー・所要時間管理がメニューによって異なる。(b) だと初期データ整備とテストの幅が広がる。
**推奨**: (a)。器(services 抽象化)は最初から入れるので、(b) への拡張はデータ追加のみで可能。
**回答(2026-07-07)**: **(b) 全メニューを最初から**。「いったん最初から作りたい! あなたの技術を信じている」
**設計への反映**: services をカテゴリ付き汎用メニューとして設計(アートメイクは 1 カテゴリ)。セッション構成(カウンセリング→施術→リタッチ)はメニューごとに構成可能なステップ定義として持ち、単発メニュー(1 ステップ)も同一モデルで扱う。問診テンプレはメニュー紐付け(不要なメニューは紐付けなし)。

## P1 — 初期 Sprint 中に確定(実装と並行で OK)

### Q5. 患者向け公開ページに載せる内容(医療広告)

- 予約機能 + 施術名・料金・注意事項のみ(広告リスク小、推奨)か、症例写真・スタッフ紹介まで載せるか。
- 症例・指名を載せる場合は限定解除要件チェックリストを整備し、弁護士に単院ツールとしての整理と合わせて軽く確認する。

**回答(2026-07-07)**: **症例写真・スタッフ指名まで必要になりそう**。
**設計への反映**: 医療広告の限定解除要件対応が必須化。症例投稿時にリスク・副作用・費用の記載を強制し、体験談は不可とするガードレールを実装する。指名は「クリニック前面・院内指名」の形を維持。詳細は [10_v2_仕様/05_主要設計論点.md](../10_v2_仕様/05_主要設計論点.md) §2。

### Q6. 指示書・施術記録・同意書の電子化の投入時期

- 推奨: MVP は予約+患者+問診まで。指示書・記録・同意書は Phase 2(それまで紙 / 既存運用と併用)。
- クリニックの既存カルテ運用(紙 or 電カル製品名)も確認したい。

**回答(2026-07-07)**: 電子カルテ領域は GMO 等の競合が強く、**本格参入はしない**。ただし **指示書には入り込む余地がある**かもしれない。同意書・施術記録も**ログとしてきちんと残す**ことは重要。既存テンプレートの実態は未把握で、その整理が課題。
**設計への反映**: 電カルの代替は狙わず、「予約起点の指示書ワークフロー + 同意書・記録のログ保存」に絞る。既存電カルとは共存(将来エクスポート連携)。詳細は [10_v2_仕様/05_主要設計論点.md](../10_v2_仕様/05_主要設計論点.md) §3。

### Q7. このクリニックとの商業条件

- 無償提供 / 有償 PoC(月額 or 一括)/ 無償→有償化の条件付き。
- 6/28 の検証基準は「有償 pilot 実コミット」。無償は WTP 検証を放棄する点に注意。
- 参考相場: 美容クリニック向け予約・オペ SaaS は月額 3〜10 万円帯が多い。

**回答(2026-07-07)**: **無償は WTP 検証の放棄になるため避ける**。実際に使って売上が上がるなら有償にしたい。→ 「価値が出たら課金」の成果連動的な導入を志向。KPI 確認期間は 4 週間。

### Q8. リリース目標時期

- クリニアップとの約束があるか。推奨計画は [04_新スコープ提案](04_新スコープ提案_単院MVP.md) の 6〜8 週間案。

**回答(2026-07-07)**: 明確な目標時期はなし。**導入後の KPI 確認期間を 4 週間**とする(Kill/Double-down 判定はこの 4 週で行う)。

### Q9. クリニックの規模感

- スタッフ数(医師/看護師/受付)、施術室(ベッド)数、月間のアートメイク件数、営業日・時間。
- 非機能要件(同時利用・データ量)と枠管理 UI の設計に使う。

**回答(2026-07-07)**: 現時点では**未把握**。導入クリニックへのヒアリングで確定する(S2 のシード精緻化までに)。当面は少人数・単院想定で設計を進める。

### Q10. 患者との連絡チャネル

- 現在の連絡手段(電話 / メール / LINE)。LINE 中心なら Phase 2 で LINE 公式アカウント連携を優先度高く検討。
- MVP はメール通知(+リマインダー)を想定。

**回答(2026-07-07)**: **LINE が多いはず。LINE とメールの両方**が使われている想定。
**設計への反映**: LINE 連携(通知・予約確認・キャンセル導線)の優先度を上げる。ノーショー対策とも直結するため、キャンセル設計と併せて検討([10_v2_仕様/05_主要設計論点.md](../10_v2_仕様/05_主要設計論点.md) §1・§4)。MVP はメール、LINE は早期 Phase 2 候補。

### Q11. サービス名・ドメイン

- 対外名は「premake」のままで良いか(DEC-01 はコードネームとしての決定)。公開予約ページはクリニック名が前面なので、サービス名の露出は最小でも成立する。

**回答(2026-07-07)**: **現状のまま(premake)で問題なし**。

## P2 — 該当フェーズまでに確定

### Q12. 弁護士への再確認のタイミング

- 単院・院内ツール + クリニック前面の公開予約ページという新整理での軽い確認。公開ページ仕様確定時(Sprint 中盤)を推奨。
- 確認観点: ①公開ページの広告該当性と限定解除、②premake の診療情報受託者としての契約条項、③(c) 外部看護師が居る場合の扱い。

**回答(2026-07-07)**: **小さく進める**方針(全面的な顧問契約でなく、論点を絞ったスポット相談)。相談前に論点を最小化しておく必要あり。症例掲載の限定解除運用が最優先の相談項目になる見込み。

### Q13. 「もっと簡単なマネタイズ」の方向性

- User の念頭にある候補を聞きたい: B(メーカー試験会場)早期展開 / M(既存客クロスセル)/ 集客支援課金 / 単純 SaaS 月額 / その他。
- 器の拡張優先順位(どの方向を最初に楽にするか)に反映する。

**回答(2026-07-07)**: **B(メーカー試験の会場提供)が重要候補**。ただしそれ以外の候補も継続探索が必要で、**別途しっかりリサーチを依頼予定**(User が後日改めて発注)。
**設計への反映**: services の抽象化(`kind`)で試験枠を将来載せられる形は維持。ただし B は「予約」より案件・被験者・謝礼管理の比重が大きいため、器の共通化範囲はリサーチ結果を待って判断(現時点で過剰設計しない)。詳細は [10_v2_仕様/05_主要設計論点.md](../10_v2_仕様/05_主要設計論点.md) §4。

### Q14. 2 院目以降の展開意思

- 「信頼のおける方にだけ」の範囲。紹介ベースで 2〜3 院に広げる意思があるなら、オンボーディング(クリニック追加)の運営 UI の優先度が上がる(当面は運営が手動セットアップで十分)。

**回答(2026-07-07)**: **紹介で 2〜3 院に広げる意思あり**。運営側の手動対応も一部あるが、**基本はオンボーディング UI を作り込みたい**。
**設計への反映**: 運営代理オンボーディング(ops がクリニック・メニュー・スタッフを初期投入)の UI を段階的に強化。1〜2 院は手動でも回るため、投資タイミングは 2 院目の目処が立った時点。マルチテナントのデータ分離(RLS)は既に前提化済み。
