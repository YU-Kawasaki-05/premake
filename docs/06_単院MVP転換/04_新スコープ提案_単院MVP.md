## 1. プロダクトコンセプト

**「クリニックの自由診療予約を、規制対応込みで一気通貫管理する院内 SaaS。第一弾はアートメイク、器は業種非依存。」**

- 医療提供主体はクリニック。premake はソフトウェアベンダーに徹する(マッチングも決済代理受領もしない)。
- 患者向けには「クリニック X の予約ページ」として見える(premake ブランドは前面に出さない)。
- 6/28 検討の「器」をコードにする: 予約対象(メニュー)・リソース(部屋/スタッフ)・参加者(患者)を抽象化し、B(メーカー試験の会場枠)/ M(既存客への別メニュー)にデータ追加だけで対応できる形。

### 1.1 やらないこと(旧仕様から凍結)

看護師⇄施設マッチング / スペース検索・掲載 / 運営審査ワークフロー / 手数料按分(Connect)/ 看護師個人の公開ページ / レビュー / チャット / 法人多店舗階層。

## 2. ユーザーとロール

| ロール | 人 | 主な操作 |
|---|---|---|
| `owner`(院長/管理者) | 1 | クリニック設定、メニュー・スタッフ・枠管理、全予約閲覧、患者マスタ |
| `doctor`(医師) | 1〜 | 予約・問診の確認。(Phase 2: 指示書発行・記録承認) |
| `staff`(看護師・受付) | 数名 | 予約台帳の操作(作成/変更/キャンセル)、患者対応、問診確認 |
| `ops`(premake 運営 = User) | 1 | テナント作成、初期セットアップ、監視 |
| 患者(ゲスト) | - | 公開ページから予約・問診記入・変更/キャンセル。**ログイン不要**(メール + 予約番号 + 認証リンク) |

- 院内 3 ロールは 1 ユーザー複数ロール可(小規模クリニックでは同一人物が兼務するため)。旧 7 ロール体系より単純化。
- 患者はログインさせないが、院内側には `patients` マスタがあり、受付が名寄せ・履歴管理できる。

## 3. MVP 機能スコープ(v2-FR 案)

### C1. 基盤・認証
| ID | 機能 |
|---|---|
| v2-01 | スタッフのログイン(メール+パスワード、Google OAuth)/ 招待制サインアップ(owner→staff) |
| v2-02 | テナント(クリニック)設定: 基本情報、営業時間、定休日 |
| v2-03 | 監査ログ・操作イベント記録(検証計測を兼ねる) |

### C2. メニュー・リソース
| ID | 機能 |
|---|---|
| v2-04 | サービスメニュー管理: 名称、カテゴリ、所要時間、料金、説明、公開/非公開、要問診フラグ、セッション構成(カウンセリング→施術→リタッチ) |
| v2-05 | リソース管理: 施術室(ベッド)、担当可能スタッフ、営業時間内の提供枠ルール |

### C3. 予約(中核)
| ID | 機能 |
|---|---|
| v2-06 | 予約台帳(カレンダー): 日/週ビュー、部屋×時間のマトリクス、ドラッグでの作成・変更。**受付が 1 日中触る画面として最優先で磨く** |
| v2-07 | 予約 CRUD: 作成(院内代理予約含む)、変更、キャンセル(理由記録)、ステータス管理(申込→確定→来院→完了/無断キャンセル) |
| v2-08 | セッションモデル: 1 予約に複数ステップ(カウンセリング/施術/リタッチ)。旧 DEC-15 を踏襲 |
| v2-09 | ダブルブッキング防止(部屋・スタッフ・患者の重複検知) |

### C4. 患者
| ID | 機能 |
|---|---|
| v2-10 | 患者マスタ: 連絡先、来院履歴、施術履歴、メモ。ゲスト予約からの自動名寄せ候補提示 |
| v2-11 | 問診票: テンプレート編集(メニューに紐付け)、患者記入(予約後にリンク送付)、院内閲覧。要配慮情報として扱う |

### C5. 患者向け公開予約ページ(Q2=a の場合)
| ID | 機能 |
|---|---|
| v2-12 | クリニック公開ページ: メニュー一覧(名称・所要時間・料金・注意事項)。**症例写真なしの最小構成**(医療広告リスク最小) |
| v2-13 | ゲスト予約フロー: メニュー選択 → 空き枠選択 → 連絡先入力 → メール確認(マジックリンクで本人性担保)→ 確定 |
| v2-14 | 患者側の予約照会・変更・キャンセル(メール+予約番号) |

### C6. 通知
| ID | 機能 |
|---|---|
| v2-15 | メール通知: 予約確定・変更・キャンセル、前日リマインダー、問診依頼(Resend) |
| v2-16 | 院内通知: 新規予約・キャンセルのダッシュボード表示(β: メール併用) |

### Phase 2 候補(MVP 後、要望と検証結果で並べ替え)
指示書・施術記録・同意書の電子化(旧 D カテゴリ流用)/ Stripe 決済・デポジット / LINE 連携(通知・予約導線)/ 症例ギャラリー(限定解除準拠)/ スタッフのシフト管理 / 集計ダッシュボード(稼働率・売上)/ 2 院目オンボーディング UI / B 用途(メーカー試験枠)のメニュー種別拡張。

## 4. データモデル骨子(14 テーブル)

全テーブルに `clinic_id`(テナントキー)+ RLS。旧 60 テーブルから骨格を流用しつつ大幅に単純化。

```
clinics                     テナント。営業時間・定休日・公開ページ設定
users / user_roles          院内スタッフ + ops。Supabase Auth 連携
patients                    患者マスタ(院内視点)。ゲスト予約から名寄せ
services                    メニュー。所要時間/料金/要問診/セッション構成(JSONB)
rooms                       施術室・ベッド
staff_service_assignments   誰がどのメニューを担当できるか
schedule_rules / closures   提供枠ルール(営業時間・例外日)
bookings                    予約ヘッダ。患者・メニュー・ステータス
booking_sessions            ステップ列(カウンセリング/施術/リタッチ)。部屋・スタッフ・開始終了時刻
questionnaire_templates     問診テンプレ(メニュー紐付け)
questionnaire_responses     記入済み問診(要配慮 → RLS 厳格 + 閲覧ログ)
notifications               送信ログ(メール)
audit_logs                  監査 + 利用計測イベント
worker_jobs                 非同期ジョブ(リマインダー等)。旧設計流用
```

- 患者向け認証はゲストトークン(予約ごとの署名付きリンク)。患者の Supabase Auth アカウントは作らない。
- `services.kind` で将来の用途拡張(treatment / trial_venue / cross_sell...)を吸収。UI はまず treatment のみ。

## 6. デザイン方針(DEC-06 継承・最重要)

**「試作品ではなくプロダクト品質」を単院 MVP でも貫く。** AI 生成っぽい無個性(紫グラデ・絵文字過多・カード羅列)を禁じ、人間のデザイナーが作った業務ツール/ブランドサイトの質感を出す。

### 院内画面(受付・スタッフが长時間使う)
- 情報密度と視認性優先。予約台帳は「紙の台帳より速い」ことが唯一の成功基準
- 落ち着いたニュートラル基調 + 状態色(確定/未確定/来院/キャンセル)は色覚多様性対応のパレット
- キーボード操作・楽観的 UI 更新(受付は電話しながら操作する)

### 患者向け公開ページ(クリニックの顔)
- 美容医療の文脈に合う上品さ: 余白を大きく、明朝系見出し + ゴシック本文、写真は控えめで清潔感
- クリニック名・院長名・所在地を前面に(医療提供主体の明示 = 法務要件でもある)
- モバイルファースト(患者流入はほぼスマホ)
- 医療広告の必須表記(自由診療の旨・リスク副作用・費用)をデザインに自然に組み込む

## 7. 実装計画(6〜8 週間案)

| Sprint | 期間 | ゴール | 内容 |
|---|---|---|---|
| S0 | 3〜4 日 | 基盤 | スキャフォールド、Supabase ローカル、マイグレーション v2-001〜、RLS、CI、Vercel デプロイ、デザイントークン |
| S1 | 1 週 | 認証・テナント | v2-01〜03。owner が staff を招待できる |
| S2 | 1 週 | メニュー・リソース・枠 | v2-04〜05。枠生成ロジック(営業時間×部屋×スタッフ) |
| S3 | 1.5 週 | 予約コア | v2-06〜09。予約台帳カレンダー(最重要 UI)、院内代理予約 |
| S4 | 1 週 | 患者・問診 | v2-10〜11。名寄せ、問診テンプレ+記入 |
| S5 | 1.5 週 | 公開予約ページ | v2-12〜14。ゲスト予約フロー、デザイン磨き込み |
| S6 | 1 週 | 通知・仕上げ | v2-15〜16。リマインダー、E2E、法定ページ、クリニック実データ投入 |
| 導入 | - | 現地セットアップ | クリニックでの初期データ投入・レクチャー・並走運用開始 |

- S3 と S5 がデザイン品質の山場。ここに時間を厚く配分。
- 各 Sprint 末に動くデモを User に提示。クリニックには S3 完了時点(院内台帳が動く)で中間デモ可能。
- Q2=b(院内管理のみ先行)なら S5 を Phase 2 に送り、4〜5 週間に短縮可能。

## 8. 検証計画(組み込み)

- audit_logs を利用計測を兼ねる設計にし、週次で「アクティブ日数 / 予約作成数(院内 vs 患者経由)/ キャンセル率」を ops が見られる最小ダッシュボードを S6 で用意。
- 機能要望はクリニックとのやり取りから `docs/07_運用ログ/要望.md`(導入後作成)に記録し、B/M 方向のシグナルを拾う。
- Kill / Double-down 条件は [02_矛盾と論点 §V-2](02_矛盾と論点の洗い出し.md) 参照(User とすり合わせ予定)。
