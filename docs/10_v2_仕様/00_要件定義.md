> 作成日: 2026-07-07 / 根拠: [06_単院MVP転換](../06_単院MVP転換/00_index.md)(P0 確認回答済み)

## 1. コンセプト

**「クリニックの自由診療予約を、規制対応込みで一気通貫管理する院内 SaaS。第一弾は実在クリニック 1 院、器は業種非依存。」**

- 医療提供主体はクリニック。premake は**ソフトウェアベンダーに徹する**(マッチングなし・決済代理受領なし・施術者斡旋なし)。
- 患者向けには「クリニック X の予約ページ」として見える。premake ブランドは前面に出さない。
- 予約は 3 層で捉える:
  1. **スタッフ(看護師)が院内の部屋×時間の施術枠を確保する**(業務委託看護師が自分の顧客を持つ実態に対応)
  2. **患者の予約**が枠に入る(公開ページ経由 or 受付の代理入力)
  3. **院内の予約台帳**で全体を管理する
- 全メニュー対応(User 確認済み)。アートメイクは重要ユースケースの一つで、カウンセリング→施術→リタッチのセッション列を持つ代表例。
- **決済機能なし**(料金はメニュー属性として保持、表示はフラグ制御)。
- 患者向け公開予約は**テナント設定でオン/オフ**。オフでも院内管理システムとして完結する。

### 1.1 目的(なぜ作るか)

| # | 目的 | 計測 |
|---|---|---|
| 1 | クリニックの予約運用を実際に置き換え、「予約管理」が実ペインであることを検証する | 週次アクティブ利用、システム外予約の残存率 |
| 2 | 信頼関係の深化と、拡張需要(B: メーカー試験 / M: クロスセル方向)のシグナル収集 | 機能要望ログ |
| 3 | 業種非依存の「器」(テナント・メニュー・予約・患者基盤)をコードとして建造する | 2 院目・別用途をデータ追加のみで載せられるか |

### 1.2 やらないこと

看護師⇄施設マッチング / スペース検索・掲載 / 運営審査 / 決済・手数料 / 看護師個人の公開集客ページ / レビュー / チャット / 法人多店舗階層 / SMS(当面) / ネイティブアプリ。

## 2. ユーザーとロール

| ロール | 説明 | 主な操作 |
|---|---|---|
| `owner` | 院長・管理者 | テナント設定、メニュー・部屋・スタッフ管理、全機能 |
| `doctor` | 医師 | 予約・問診の閲覧確認(Phase 2: 指示書・記録承認) |
| `staff` | 看護師・受付 | 施術枠の確保、予約台帳の操作、患者・問診対応 |
| `ops` | premake 運営(User) | テナント作成・初期セットアップ・利用計測閲覧 |
| 患者(ゲスト) | ログインなし | 公開ページから予約・問診記入・照会・変更・キャンセル |

- 1 ユーザー複数ロール可(兼務が普通の規模)。権限は role の和集合。
- スタッフには雇用区分属性 `employment_type: employed / contracted` を持つ(権限差はなし。表示・集計用)。
- 患者は Supabase Auth アカウントを持たない。予約ごとの署名付きトークンリンクで本人操作を担保。

## 3. 機能一覧(v2-01〜26)

### C0. 基盤・認証・テナント

| ID | 機能 | 概要 |
|---|---|---|
| v2-01 | スタッフ認証 | メール+パスワード、Google OAuth。セッション管理 |
| v2-02 | スタッフ招待 | owner がメール招待 → 招待リンクからサインアップ。ロール・雇用区分指定 |
| v2-03 | テナント設定 | クリニック基本情報(名称・住所・院長名・連絡先)、営業時間・定休日、公開予約オン/オフ、予約承認モード(自動確定/手動承認)、キャンセル受付期限 |
| v2-04 | 監査ログ・操作イベント | 全 mutation を記録。利用計測を兼ねる。問診閲覧は閲覧ログも |

### C1. メニュー・リソース・枠

| ID | 機能 | 概要 |
|---|---|---|
| v2-05 | メニュー管理 | CRUD。カテゴリ、名称、説明、所要時間、バッファ時間、料金+**料金表示フラグ**、公開フラグ、セッション構成テンプレート(例: カウンセリング30分→施術120分、リタッチ90分)、問診テンプレ紐付け、指名可否 |
| v2-06 | 部屋管理 | 施術室・ベッドの CRUD。名称、対応メニューカテゴリ(任意) |
| v2-07 | 担当設定 | スタッフ×メニューの担当可否 |
| v2-08 | 施術枠管理 | **スタッフが部屋×時間帯の施術受付枠を確保**(= 看護師の場所予約)。ブロック(休憩・私用)も。部屋の時間帯重複は排他。owner/受付は他人の枠も操作可 |

### C2. 予約(中核)

| ID | 機能 | 概要 |
|---|---|---|
| v2-09 | 予約台帳カレンダー | 日/週ビュー。部屋レーン⇄スタッフレーン切替。**受付が 1 日中触る最重要 UI** |
| v2-10 | 院内予約作成 | 受付の代理入力(電話予約)。患者検索 or 新規、メニュー、枠選択。schedule_block 外への強制作成も警告付きで可 |
| v2-11 | 予約変更・キャンセル | 日時・担当・部屋の変更、キャンセル理由記録 |
| v2-12 | ステータス管理 | requested → confirmed → checked_in → done / cancelled / no_show |
| v2-13 | ダブルブッキング防止 | 部屋×時間、スタッフ×時間、患者×時間の 3 軸重複を DB 制約 + UI で防止 |
| v2-14 | セッション管理 | 1 予約に複数ステップ(カウンセリング/施術/リタッチ/その他)。別日への分割、ステップごとの担当・部屋 |

### C3. 患者・問診

| ID | 機能 | 概要 |
|---|---|---|
| v2-15 | 患者マスタ | CRUD。氏名・かな・生年月日・連絡先・メモ・タグ・外部カルテ番号(任意)。来院/施術履歴ビュー |
| v2-16 | 名寄せ | ゲスト予約の連絡先から既存患者の候補を提示、受付が確認して紐付け(自動マージしない) |
| v2-17 | 問診テンプレ管理 | 質問項目(テキスト/選択/日付/同意チェック)をメニューに紐付け |
| v2-18 | 問診記入・閲覧 | 予約確定後にリンク送付 → 患者が記入。院内は権限者のみ閲覧(閲覧ログ付き) |

### C4. 患者向け公開予約(テナント設定でオン/オフ)

| ID | 機能 | 概要 |
|---|---|---|
| v2-19 | クリニック公開ページ | `/c/[slug]`。クリニック情報+公開メニュー一覧。**症例写真なし・体験談なしの最小構成**(医療広告リスク最小)。自由診療の注意表記 |
| v2-20 | ゲスト予約フロー | メニュー→(指名 任意)→空き枠→連絡先入力→**メール確認リンクで確定**(承認モードによっては院内承認待ち) |
| v2-21 | 患者側予約操作 | 照会・変更・キャンセル(トークンリンク経由、キャンセル期限はテナント設定) |
| v2-22 | 施術者指名 | クリニック内の選択肢として指名(任意設定・メニューごと)。**クリニック前面の原則を維持**(スタッフ個人の集客ページは作らない) |

### C5. 通知

| ID | 機能 | 概要 |
|---|---|---|
| v2-23 | メール通知 | 予約確定・変更・キャンセル(患者/院内双方)、問診依頼。Resend + React Email。送信元表示はクリニック名 |
| v2-24 | リマインダー | 前日リマインダー(worker_jobs + Vercel Cron)。問診未記入の催促を兼ねる |

### C6. 運営(ops)

| ID | 機能 | 概要 |
|---|---|---|
| v2-25 | テナント管理 | ops によるクリニック作成・owner 招待・初期データ投入(2 院目以降もここから) |
| v2-26 | 利用計測ダッシュボード | 週次: アクティブ日数、予約数(経路別)、キャンセル率。検証仮説の観測用(ops のみ) |

### Phase 2 バックログ(優先度は導入後の要望で決定)

指示書・施術記録・同意書の電子化(旧 D カテゴリ流用)/ Stripe 決済・デポジット / LINE 連携 / 症例ギャラリー(限定解除チェックリスト整備後)/ シフト管理 / 稼働率・売上ダッシュボード / 患者タグ・セグメント配信(M 方向)/ メニュー種別拡張: メーカー試験枠(B 方向)/ 外部カレンダー(Google)連携 / 業務委託スタッフの契約状態管理。

## 4. 業務フロー(主要 3 本)

### F1. 看護師が枠を確保し、患者が Web 予約する(公開オン時)

```
看護師: 施術枠登録(金曜 13-18時 × 施術室2)
  ↓ 公開ページの空き枠に反映(担当可能メニューのみ)
患者: メニュー選択 → 枠選択 → 連絡先入力 → 確認メールのリンククリック
  ↓ (承認モード=手動なら) 院内で確認 → 確定
確定通知(患者+院内) → 問診リンク送付 → 前日リマインダー
  ↓ 来院: checked_in → 施術 → done
```

### F2. 受付が電話予約を台帳に入れる(公開オフでも成立する基本線)

```
電話 → 受付: 台帳で空き確認(部屋・担当) → 患者検索(なければ新規) → 予約作成
  → 確定メール(患者メールあれば) → 以降 F1 と同じ
```

### F3. アートメイクの複数セッション

```
予約作成時にメニューのセッション構成を展開:
  セッション1: カウンセリング(30分) — 当日 or 別日
  セッション2: 施術(120分)
  (完了後) リタッチ予約(90分) を追加セッションとして同一予約に紐付け
患者履歴では 1 予約 = 1 コースとして時系列表示
```

## 5. 非機能要件(単院 MVP の現実解)

| 項目 | 要件 |
|---|---|
| 規模想定 | 1 テナント、スタッフ 10 名以下、患者数千件、予約月数百件(Q9 回答で更新) |
| 性能 | 台帳描画 p95 < 500ms、公開ページ LCP < 2.5s(モバイル) |
| 可用性 | Vercel + Supabase のマネージド水準。営業時間内の障害は即時対応(ops = User) |
| セキュリティ | 全テーブル RLS(テナント分離)、問診・患者情報は要配慮情報として閲覧ログ、TLS、バックアップ(Supabase 日次 + 手動エクスポート手順) |
| 監査 | mutation 全記録(操作者・対象・差分)。保存 7 年方針(旧仮決定踏襲) |
| アクセシビリティ | 公開ページは WCAG AA 目標(フォーム・コントラスト・キーボード) |
| 対応環境 | 院内: PC(Chrome/Edge/Safari)+ タブレット。公開: モバイルファースト |
| i18n | 日本語のみ |

## 6. 法務要件(リリースゲート)

- [ ] 公開ページに医療提供主体(クリニック名・院長名・所在地)を明示
- [ ] 自由診療の旨・リスク副作用・(表示する場合)費用の記載欄をメニュー説明に用意
- [ ] 体験談・ビフォーアフター写真は掲載しない(Phase 2 で限定解除チェックリスト整備後に再検討)
- [ ] 患者向けプライバシーポリシー、クリニック向け利用規約(個人情報・診療情報の取扱条項含む)
- [ ] 問診・患者データの RLS / 閲覧ログの動作確認
- [ ] 弁護士への軽い確認(単院ツール整理 + 公開ページ)— 公開ページ仕様確定時(S5 前)
