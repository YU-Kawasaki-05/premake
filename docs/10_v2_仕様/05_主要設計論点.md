# premake v2 主要設計論点

> 作成日: 2026-07-07 / 根拠: User 方針回答(2026-07-07)
> 症例・指名の掲載を出す方針が固まったこと、キャンセル設計の依頼、電子カルテに参入せず指示書に絞る判断を受けた設計メモ。実装は主に S5(公開ページ)/S6(通知・キャンセル)/Phase 2(指示書・記録)。

---

## §1. キャンセル・ノーショー対策(User 明示依頼)

### 1.1 なぜ難しいか
- アートメイクは **施術時間が長く(2〜3時間)単価が高い(10万円前後)**。ノーショー 1 件の逸失が大きい。
- MVP は **決済なし**のため、事前決済によるペナルティ徴収という最も強い抑止が使えない。
- 一方、医療(自由診療)では事前決済+キャンセル料は美容クリニックで一般的であり、Phase 2 の余地はある。

### 1.2 ノーショーの構造分解(打ち手を型に分ける)
| 原因 | 主な打ち手 |
|---|---|
| 単純な失念 | リマインダー多段(前日+当日)、LINE 到達、ワンタップ再確認 |
| 予定変更・面倒で連絡せず | 簡単なセルフ変更/キャンセル導線(期限内は無料) |
| 冷やかし・複数院同時予約 | カウンセリング先行、初回デポジット(Phase 2)、常習者フラグ |
| 当日体調・急変 | 期限外でも救済(ポリシーで区別)、再予約導線 |

### 1.3 段階設計

**MVP(決済なし)— 「摩擦を下げて失念を潰す」+「証跡を残す」**
1. **多段リマインダー**: 予約確定時・前日・当日朝。LINE 優先、無ければメール(§4 と連動)。
2. **ワンタップ確認/変更/キャンセル**: リマインダーから来店確認・日時変更・キャンセルが完結(トークンリンク、ログイン不要)。「連絡しづらいから来ない」を消す。
3. **キャンセルポリシーの明示 + 予約時同意**: 期限(例: 施術は 3 日前まで無料 / カウンセリングは前日まで)、期限後・当日・無断の扱いを予約時に提示し同意チェック。決済がないため**徴収はクリニックの個別運用**だが、同意ログが請求・お断りの根拠になる。
4. **ノーショー/直前キャンセルの記録**: `bookings.status` に `no_show`/`cancelled`(理由付き)。患者マスタに履歴を集約し、**リピート予約時に受付へ警告表示**(ブラックリストではなく判断材料)。
5. **カウンセリング先行フロー**: アートメイクの実態(カウンセリング→後日施術)を活かし、**新規は短時間カウンセリングで信頼を確認してから長時間施術枠を確保**。いきなりの長時間ノーショーを構造的に減らす。セッションモデル(v2-14)で表現可能。
6. **計測**: ノーショー率・直前キャンセル率を KPI 化(検証にも使う)。

**Phase 2 — 「効くが重い」デポジット/事前決済(Stripe)**
- **リスクベースで限定適用**: 新規患者の施術予約・高単価メニューにデポジット必須、リピーターは免除。全件必須にすると予約完了率が落ちるため、リスクの高い予約だけに絞る。
- 患者→クリニック(クリニック自身の Stripe アカウント)への直接決済であれば法務上も問題なし(§弁護士見解と整合)。
- キャンセルポリシーに応じた自動返金/一部徴収を Webhook で処理。

### 1.4 設計の肝(判断)
> MVP は **「決済で縛る」より「摩擦を消して失念を潰す + カウンセリング先行 + 証跡」**に賭ける。デポジットは Phase 2 でリスクベース導入。全予約一律のデポジットは予約完了率を下げるので採らない。

## §2. 医療広告対応 — 症例写真・スタッフ指名(必須化)

症例・指名を出す方針になったため、医療広告規制(医療法)への準拠が MVP のリリースゲートになる。

### 2.1 限定解除の 4 要件(症例写真・詳細情報を出す前提)
Web の予約ページは「患者が自ら求めて閲覧する」ため、以下を満たせば通常広告可能事項を超える情報(症例等)を出せる:
1. 患者が**自ら求めて**情報を取得する媒体であること(Web サイト = 満たす)
2. 問い合わせ先の明示(電話番号・メール等)
3. 自由診療は**通常必要な治療内容・費用**を明示
4. 自由診療は**主なリスク・副作用**を明示

加えて **体験談は限定解除しても掲載不可**、写真の**加工・誇大表現は不可**、**術前術後写真は詳細説明(内容・費用・リスク・副作用)とセット**でのみ可。

### 2.2 システムのガードレール(違反を仕組みで防ぐ)
- **症例投稿フォームで必須項目を強制**: 施術内容 / 費用 / 主なリスク・副作用 の記載が無いと**公開できない**(下書き止まり)。
- **体験談欄を作らない**(患者の感想を入力・表示する UI を設けない)。
- **患者の掲載同意を管理**: 症例写真は該当患者の掲載同意(範囲・撤回可能性)をレコードで保持。撤回で即非公開。
- **クリニック前面の維持**: 指名はクリニックの予約フロー内の選択肢。スタッフ個人の外部集客ページ(SNS 的プロフィール)は作らない。実績表示は限定解除の範囲に留める。
- **公開前チェックリスト**: 誇大表現・比較優良(「日本一」等)・「絶対」等の断定を弾くチェック項目を投稿 UI に併設。

### 2.3 データモデルへの追加(Phase: 症例機能実装時)
```
case_studies            症例。service_id、before/after 画像、施術内容、費用、リスク副作用(必須)、公開フラグ
case_study_consents     患者の掲載同意(範囲・取得日・撤回日)
```
`clinic_members.is_bookable` / `display_name` は指名用に S1 で用意済み。

### 2.4 弁護士相談(小さく)
症例掲載の限定解除運用と、premake が診療情報を預かる受託者としての契約条項を、論点を絞ってスポット相談する。相談前にチェックリスト草案を用意して確認コストを下げる。

## §3. 指示書・同意書・施術記録の位置づけ(電子カルテに参入しない)

### 3.1 判断
電子カルテ領域は GMO 等の競合が強く、**本格参入はしない**。premake の価値は「予約起点のワークフロー」にあり、電カルの代替ではなく**共存**する。

### 3.2 差別化の核 = 予約に紐づく「適法性の証跡」
- **指示書**: アートメイク特有の「医師の指示のもとで看護師が施術」を、**予約(セッション)ごとに指示書を紐づけて記録**する。規制強化(2023/2025 の通知)の時代に、適法運用の証跡として価値。既存電カルは予約と指示書を密結合していない点が入り込む余地。
- **同意書・施術記録**: フルの診療録ではなく、**予約に紐づくログとしての保存**に徹する。改ざん検知(ハッシュ)・閲覧ログ・保存期間管理を軽量に提供。
- **既存テンプレの取り込み**: クリニックが現在使っている様式が不明なため、**汎用フォームビルダー**(問診 v2-17 と同じ仕組み)で表現し、既存様式を移せるようにする。ゼロから標準様式を押し付けない。

### 3.3 スコープと段階
- **MVP**: 予約 + 患者 + 問診まで(指示書・記録・同意書は扱わない)。
- **Phase 2**: 予約に紐づく指示書ワークフロー(医師の発行 → 施術可能化)、同意書・施術記録のログ保存。データモデルは旧設計(prescriptions / treatment_records / consents)を予約紐づけで流用。
- **将来**: 電子カルテへのエクスポート/連携(参入でなく共存)。

### 3.4 過剰参入を避ける線
診療録としての完全性(改ざん防止の電子署名 TSA、レセプト連携等)は追わない。「予約に付随する軽量な証跡」を超えない。重くなったら電カルとの競合に飲まれる。

## §4. LINE 連携(通知の主力候補)

### 4.1 位置づけ
患者連絡は LINE + メールの併用実態。**LINE はリマインダー到達率が高く、ノーショー対策(§1)の中核**になり得る。予約確認・変更・キャンセルを LINE で完結できれば患者体験も大きく向上。

### 4.2 段階
- **MVP**: メール(Resend)で通知・リマインダー。LINE は未実装。
- **早期 Phase 2**: LINE 公式アカウント + Messaging API 連携。予約確定・リマインダー・ワンタップ確認/キャンセルを LINE で。友だち追加時に予約と患者を紐づけ。
- **前提**: クリニック側で LINE 公式アカウントの用意が必要(運用負荷)。導入クリニックの実態確認後に優先度を最終判断。

### 4.3 設計上の配慮
- 通知チャネルを抽象化(`notifications` に channel: email/line)。§S1 の通知基盤を channel 非依存で作っておけば、LINE 追加時に送信アダプタを足すだけで済む。

## §5. マネタイズ拡張 — メーカー試験(B)を本命に据えるが、今は器だけ

### 5.1 方針
B(化粧品・美容機器メーカーの臨床評価/モニター試験/研修の会場提供)が本命候補。ただし B は「予約」より **案件管理・被験者(=既存患者)管理・スケジュール・謝礼** の比重が大きく、予約システムとは要件が異なる。

### 5.2 今やること / やらないこと
- **やる**: services の `kind`(treatment / trial_venue 等)で将来メニュー種別を拡張できる余地は維持済み。患者マスタ(=被験者プール)は共通資産。
- **やらない(過剰設計を避ける)**: 案件管理・謝礼・GCP 対応等の B 専用機能は作らない。**別途のリサーチ(User が後日発注)で B の要件・市場・競合・規制を固めてから**、器の共通化範囲を判断する。

### 5.3 リサーチ依頼への申し送り(後日)
B を含むマネタイズ探索のリサーチでは、少なくとも次を明らかにしたい:
- B の需要側(化粧品・機器メーカー、CRO)の実在ニーズと支払額、既存の会場調達手段
- 会場提供が「治験」に該当する場合の規制(GCP・倫理審査)と、非該当(モニター/研修)の線引き
- 競合(臨床試験受託・被験者リクルート事業)と、premake の「被験者付き美容クリニック網」という差別化の成否
- M(既存客クロスセル)や集客支援など他候補との優先順位

## §6. 追加で指摘する論点(User 未言及・私から提起)

| # | 論点 | なぜ重要 | 対応方針 |
|---|---|---|---|
| 1 | **要配慮個人情報の管理** | 症例写真・問診・施術記録は要配慮個人情報/診療情報。単院ツールでも premake は受託者。漏洩は事業致命傷 | クリニックとの利用契約(個人情報取扱条項)、患者同意、保存期間、閲覧ログ、漏洩時対応手順を整備。RLS は実装済み |
| 2 | **マルチテナントのデータ分離監査** | 2〜3 院展開で、テナント間の医療情報漏洩は致命的 | テナント追加時の分離テストを運用化。RLS の with check は S1 で対応済み。E2E に越境アクセス拒否を追加 |
| 3 | **owner/doctor の MFA** | 医療情報を扱うアカウントの乗っ取り対策 | Supabase Auth の MFA を将来必須化(特に owner/doctor)。優先度は本番公開前 |
| 4 | **バックアップ・BCP** | 予約データ消失はクリニック業務停止に直結 | Supabase 日次バックアップ + 手動エクスポート手順 + 復旧手順の文書化 |
| 5 | **競合との差別化軸の堅持** | 純予約 SaaS(medical force / b4a)では勝てない(6/28 結論) | 差別化軸を「①自由診療特化+規制対応(指示書・症例の適法運用)②器の業種転用(B/M)」に固定し、汎用機能の作り込み競争に入らない |
| 6 | **「価値が出たら課金」の課金設計** | User は成果連動的な有償化を志向 | 利用実績(予約数・稼働)を計測し、無償トライアル→定着後に月額、の導線を設計。KPI 計測(v2-26)を課金判断にも使う |
| 7 | **オンボーディング投資のタイミング** | 作り込みは初期投資。1〜2 院は手動で足りる | 2 院目の目処が立った時点で運営代理オンボーディング UI を強化。それまでは ops 手動 + 最小 UI |
| 8 | **予約枠と施術者指名の運用衝突** | 指名(§2)と施術枠(v2-08 スタッフが枠を確保)が絡む。「指名した施術者の枠しか予約できない」制約が患者体験を狭める可能性 | 指名は「担当可能かつ枠がある施術者」に限定表示。指名なし(おまかせ)を既定にし、指名は任意 |

## §7. 実装への織り込み(スプリント割り付けの更新)

| 論点 | いつ | 備考 |
|---|---|---|
| キャンセル: リマインダー多段・セルフ操作・ポリシー同意・ノーショー記録 | S6(通知)+ S3-5(予約/公開) | MVP の中核。カウンセリング先行は予約フロー設計に織り込む |
| 医療広告: 症例フォームのガードレール・掲載同意 | 症例機能実装時(S5 の後 or Phase 2 前段) | MVP 公開ページは症例なしで先行も可。症例は要件が固まってから |
| 指示書・記録・同意 | Phase 2 | データモデルは予約紐づけで用意 |
| LINE 連携 | 早期 Phase 2 | 通知基盤を channel 抽象化して S6 で下地 |
| デポジット/事前決済 | Phase 2 | リスクベース限定 |
| B(メーカー試験)の器 | リサーチ後 | 今は kind 拡張余地のみ |
