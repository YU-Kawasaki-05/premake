# 受け入れテスト — 最優先 MVP パス(予約→施術の中核フロー)

> 作成日: 2026-07-22 / 仕様根拠: [docs/10_v2_仕様/](../10_v2_仕様/00_要件定義.md) / 抽出元: 本フォルダ 01〜06 の受け入れテスト仕様書 / 既知問題の根拠: [docs/40_品質監査_2026-07-21/](../40_品質監査_2026-07-21/00_サマリ.md)

## このドキュメントの目的と使い方

MVP の最重要業務は **「看護師(受付)が院内予約を作成 → 病院側が内容を確認・確定 → 当日チェックイン → 施術完了(done)」** の一本道である(決済機能は MVP 非対象)。本書はこの中核フローを最小コストで検証するために、既存の受け入れテスト仕様(215 ケース)から**必要十分なケースだけを実行順に抜き出した実行台帳**である。上から順に実施し、P0 が 1 件でも落ちたら中核フローは未成立と判断する。各ケースの詳細手順・確認 SQL は「テスト ID」が属する元ファイル(下表の参照先)を開くこと。「現状実装での注意」は監査で確定済みの既知問題。**2026-07-23 更新: 監査時の既知問題のうち ★1/★2/★3 バッチ対象はすべて実装済み**(検証記録 = [../40_品質監査_2026-07-21/03_実装検証レポート.md](../40_品質監査_2026-07-21/03_実装検証レポート.md))。残存する注意のみ下表に残している。

## 実行前提

### 環境
- Node 22(`nvm use`)/ `pnpm dev`(http://localhost:3000)。性能計測が要るケースのみ `pnpm build && pnpm start`。
- ローカル Supabase: `pnpm db:start` → `pnpm db:reset`(`supabase/seed.sql` 投入)。Studio `:54323` / 受信メール確認は Inbucket `:54324`。
- メール: `RESEND_API_KEY` 未設定時は実送信なし・サーバーログに `[email:dev] would send …`(到達確認は Resend 設定済みステージングで別途)。
- 通知の駆動: 通知は `notifications` に `queued` で積まれ、`GET /api/cron` で送信。手動実行 `curl {BASE}/api/cron`(`CRON_SECRET` 設定時は `-H "Authorization: Bearer $CRON_SECRET"`)。

### seed アカウント(パスワードは全員 `premake-dev`)
| 用途 | メール | ロール / 属性 | クリニック |
|---|---|---|---|
| ops(運営) | `ops@premake.local` | is_ops=true(擬似 owner) | 所属なし |
| owner(院長) | `owner@demo.local` | owner, doctor / 指名不可 | demo(唯一の owner) |
| staff(看護師・鈴木) | `nurse1@demo.local` | staff / 指名可(is_bookable) | demo |
| staff(委託・田中) | `nurse2@demo.local` | staff / 指名可(is_bookable) | demo |

- demo クリニック(slug=`demo` / clinic_id=`10000000-0000-4000-a000-000000000001`)。公開予約=オン・承認モード=manual・営業時間 月〜金 10:00–19:00 / 土 10:00–17:00 / 日休。
- **seed に中核フローの前提データが揃っている**: 部屋 2 室(施術室1/2)、メニュー(アートメイク眉=カウンセリング30分+施術120分/バッファ15分・メディカルピーリング等)、担当マトリクス(鈴木・田中に全メニュー割当)、明日の施術枠、確定予約 1 件(山田 花子)。

### 事前データの準備工程
中核フローには **部屋・メニュー・担当割当** が必須。**施術枠(open)は院内予約作成では参照されない**(`createBooking` は `schedule_blocks` を一切見ない=枠外でも無警告で作成される。AT-BOOK-011 参照)ため、枠の準備は「施術枠表示・公開予約」を併せて確認する場合のみ必要。上記 seed をそのまま使う場合、フェーズ ② はスキップして「値の確認」に留めてよい。ゼロから環境を組む場合のみフェーズ ② を実施する。

> 注: 本書は中核フローに絞った縦断パスであり、[00_概要.md](00_概要.md) §4 の推奨実行順序(まず 07 の RLS 基盤 P0 → 01 → …)の完全な代替ではない。**07(RLS・EXCLUDE の実 DB 動的検証)と 01 の認証基盤 P0 が土台として通っている前提**で本パスを走らせること。

## リリース判定の目安

### このパスが全て green なら保証されること
- **院内発の予約→施術の運用ループが一周する**: 看護師/受付が院内予約を作成でき、病院側が台帳で内容を確認・確定し、当日 チェックイン→施術完了(done)まで状態機械どおりに進み、キャンセルで枠が解放される。
- **予約データが壊れない**: 部屋×時間・スタッフ×時間の二重予約が(同時実行含め)DB レベルで防止され、不正なステータス遷移がサーバーで拒否される。
- **テナント分離が予約作成経路で保たれる**: 他クリニックの患者/メニュー/部屋/担当 ID を混入させても弾かれ、越境予約が起きない。
- **患者への基本通知が届く**: 確定・キャンセル・前日リマインダーが `notifications` に積まれ Cron で送信され、リマインダーは重複しない。Cron は不正な認可で叩けない(SEC-01 修正後)。

### green でも保証されないこと
- **公開 Web 予約は未検証**(05)。特に auto 確定は「なりすまし確定・承認漏れ・退職者/施術不可スタッフへの誤割当」が別途リスク。MVP を院内 manual 運用に限定するなら本パス+04/06 の A 判定で到達可能、公開予約を ON にするなら 05 と 07 のレート制限・空き枠露出が実装必須ラインに上がる。
