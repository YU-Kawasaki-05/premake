## 2. ID・優先度規約

- テストケース ID: `AT-<エリア>-<連番3桁>`(例: `AT-PUB-010`)。エリアコードは AUTH / CAT / BOOK / PAT / PUB / NTF / NFR。
- 優先度:
  - **P0 — リリースゲート**: 1 件でも不合格なら本番投入不可。データ破壊・二重予約・情報漏えい(テナント越境・RLS)・法務要件(§6)・中核業務フロー(F1/F2/F3)。
  - **P1 — 主要機能**: 不合格は修正必須だが、回避運用が成立する場合はリリース判断の余地あり。
  - **P2 — 周辺・表示**: 記録して次イテレーションで対応可。

## 3. テスト環境と共通前提

- **アプリ**: Node 22(`nvm use`)、`pnpm dev`(http://localhost:3000)。本番相当の計測(LCP 等)は `pnpm build && pnpm start`。
- **DB**: ローカル Supabase(`pnpm db:start` → `pnpm db:reset` で `supabase/seed.sql` 投入)。REST: `127.0.0.1:54321` / DB: `127.0.0.1:54322` / Studio: `127.0.0.1:54323`。
- **seed アカウント**(パスワードは全て `premake-dev`): `ops@premake.local`(ops)/ `owner@demo.local`(owner)/ `nurse1@demo.local`・`nurse2@demo.local`(staff)。デモクリニックは `slug=demo`。
- **メール**: `RESEND_API_KEY` 未設定時はサーバーログに `[email:dev] would send …` が出る(実送信なし)。実送信の受け入れは Resend を設定したステージングで実施。
- **通知・リマインダーの駆動**: 通知は `notifications` テーブルへのキュー投入 → `GET /api/cron` で送信。手動実行: `curl {BASE}/api/cron`(`CRON_SECRET` 設定時は `-H "Authorization: Bearer $CRON_SECRET"`)。
- 各ファイルの「§1 テスト範囲と前提」に、そのエリア固有の追加セットアップ(例: 03 は検証用メニュー・別クリニック、06 は `test-clinic` と計測用データ、07 は第 2 クリニック作成 SQL)を記載している。seed をそのまま使うエリア(05 等)と自前データを作るエリア(03・06 等)があるため、**各ファイルの前提を必ず先に読むこと**。

## 4. 推奨実行順序

1. **07(RLS・セキュリティ基盤)の P0** — 土台が破れていたら以降のテストは無意味
2. **01(認証・招待・設定)** — 以降のテストで使うアカウント・クリニックを整備しながら実施
3. **02(メニュー・部屋・担当・枠)** → **03(予約中核)** → **04(患者・問診)** — 院内業務の依存順
4. **05(公開予約)** → **06(通知・法定)** — ゲスト導線とその通知
5. **07 の残り(性能・a11y・ブラウザ)** — 本番相当ビルドで計測

## 5. 期待結果の正と仕様乖離の扱い

- 期待結果は **仕様(docs/10_v2_仕様/)を正** として記述している。実装が仕様と異なることが執筆時点で判明しているケースは、期待結果はそのままに **備考に「現状実装: 〜」** を明記した。
- したがって現状のコードで実行すると **不合格になることが既知のケースが相当数ある**(例: メール確認リンクによる確定フロー未実装、予約変更 Action 未実装、院内向け通知未実装、週ビュー/スタッフレーン未実装、Google OAuth 未実装 など)。これらは「テストの誤り」ではなく「実装 or 仕様のどちらを直すかの判断待ち」であり、一覧は各ファイル末尾の備考・付録および別途の監査レポートに集約する。
- 判断が必要な論点(仕様側を改訂すべきか)は各エリアの執筆時に open question として抽出済み。リリース判定会の議題にすること。

## 6. トレーサビリティ

v2-01〜26 の全機能 ID をいずれかのファイルがカバーする(§1 の表)。各テストケースは「対象要件」に v2-XX を持ち、仕様書側の機能一覧と相互参照できる。§6 法務要件(リリースゲート)は 05・06・07 の P0 ケースに分解済み。

## 7. 合否記録

実施時は各ケースに 合格 / 不合格 / ブロック(前提未成立) / 対象外(仕様改訂待ち) を記録し、不合格は再現手順・スクリーンショット・該当 SQL 結果を添えて issue 化する。P0 の全数合格をもってリリースゲート通過とする。
