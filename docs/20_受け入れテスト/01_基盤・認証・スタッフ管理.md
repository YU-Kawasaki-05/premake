# 受け入れテスト仕様書 — 基盤・認証・スタッフ管理

> 対象要件: v2-01, v2-02, v2-03, v2-04, v2-25 / 作成日: 2026-07-21 / 仕様根拠: docs/10_v2_仕様/ / 状態: draft

## 1. テスト範囲と前提

### 1.1 対象機能
- **v2-01 スタッフ認証**: メール+パスワードのログイン/ログアウト、パスワードリセット、Google OAuth(仕様要件・実装確認込み)、セッション保護
- **v2-02 スタッフ招待**: owner によるメール招待、招待リンクからのサインアップ/参加、トークンの期限切れ・再利用・失効、ロール・雇用区分、複数ロールの権限和、最後の owner を外せないこと
- **v2-03 テナント設定**: 基本情報、営業時間・定休日、公開予約オン/オフ、承認モード、キャンセル期限
- **v2-04 監査ログ**: 全 mutation の記録、閲覧 RLS、権限昇格防止
- **v2-25 ops テナント管理**: ops によるクリニック作成・owner 招待

### 1.2 前提セットアップ
- ローカル/検証環境に `supabase/migrations/20260707000001_init.sql` を適用済み、`supabase/seed.sql` を投入済み。
- アプリを `pnpm dev`(または `next start`)で起動。ベース URL を以下 `{base}` と表記(例: `http://localhost:3000`)。
- Supabase ローカルの受信メール確認は Inbucket(`http://localhost:54324`)。本番/検証環境は Supabase Auth に設定した SMTP の受信箱。
- 監査ログ・RLS 確認は Supabase Studio の SQL Editor(`http://localhost:54323`)または `psql`。

### 1.3 テストデータ(seed 由来。パスワードは全員 `premake-dev`)
| 用途 | メール | ロール/属性 | クリニック |
|---|---|---|---|
| ops(運営) | `ops@premake.local` | `is_ops=true` | (所属なし) |
| owner(院長) | `owner@demo.local` | owner, doctor / 雇用 | demo(唯一の owner) |
| staff(看護師) | `nurse1@demo.local` | staff / 雇用・指名可 | demo |
| staff(委託) | `nurse2@demo.local` | staff / 業務委託・指名可 | demo |

- デモクリニック: slug=`demo`、名称「デモクリニック」、公開予約=オン、承認モード=manual、営業時間=月〜金 10:00–19:00 / 土 10:00–17:00 / 日 休診。
- 招待受諾やクロステナントの検証には、2 院目(例: slug=`demo2`)を AT-AUTH-013 で作成しておくと再利用できる。
- テスト実行で作成したユーザー/クリニック/招待は各ケース末尾のクリーンアップ、または DB リセット(`supabase db reset`)で戻す。

### 1.4 必要なアカウント・ロール
ops / owner / staff / 未ログイン / 他クリニックの member(クロステナント用に 2 院目 owner)。

## 3. テストケース詳細

### AT-AUTH-001: owner のメール+パスワードログイン → クリニックへ遷移
- **対象要件**: v2-01
- **優先度**: P0
- **前提**: 未ログイン。seed 投入済み。
- **手順**:
  1. `{base}/login` を開く。見出し「スタッフログイン」を確認。
  2. メールアドレス `owner@demo.local`、パスワード `premake-dev` を入力し「ログイン」を押す。
- **期待結果**:
  - `/demo`(予約台帳ホーム)へリダイレクトされる。サイドバーにクリニック名「デモクリニック」が表示される。
  - owner なので管理系ナビ(メニュー/部屋・担当/問診テンプレ/スタッフ/クリニック設定)が表示される。
  - 監査ログに `action='auth.login'`, `actor_type='member'`, `actor_user_id`=owner が記録される(SQL は AT-AUTH-032 参照)。
- **備考**: ログイン後の遷移先は「所属クリニックのうち作成日が最古の 1 件」。owner は demo のみ所属。

### AT-AUTH-002: ops のログイン → /ops へ遷移
- **対象要件**: v2-01, v2-25
- **優先度**: P1
- **前提**: 未ログイン。
- **手順**:
  1. `{base}/login` で `ops@premake.local` / `premake-dev` を入力しログイン。
- **期待結果**:
  - `/ops` へリダイレクト。ヘッダーに「premake」+バッジ「運営」が表示。見出し「クリニック」とテナント一覧テーブル(名称/slug/メンバー/公開予約/作成日)が表示される。
  - 一覧に「デモクリニック」行が存在する。

### AT-AUTH-003: 誤った資格情報 → 汎用エラー + 失敗ログ記録
- **対象要件**: v2-01, v2-04
- **優先度**: P1
- **前提**: 未ログイン。
- **手順**:

  - エラー「メールアドレスまたはパスワードが正しくありません」が表示。入力したメールアドレスはフォームに残る(パスワードはクリア)。
  - リダイレクトせずログインページに留まる。
  - 監査ログに `action='auth.login_failed'`, `actor_type='guest'`, `diff.email='owner@demo.local'`, および IP/user_agent が記録される。
- **備考**: 存在しないユーザー・誤パスワードいずれも同一メッセージ(アカウント存在の秘匿)。

### AT-AUTH-004: ログイン入力バリデーション
- **対象要件**: v2-01
- **優先度**: P2
- **前提**: 未ログイン。
- **手順**:
  1. メール欄に `not-an-email`、パスワードに任意文字を入れて送信(HTML5 検証を回避する場合は devtools で `type` を変更、もしくは Server Action の zod 検証を確認)。
  2. 続けてパスワード空で送信。
- **期待結果**:

  - パスワード空は「パスワードを入力してください」。
  - いずれもサーバー側 zod 検証で弾かれ、認証 API は呼ばれない。

### AT-AUTH-005: 所属なし・招待なしでのログイン → 強制ログアウト
- **対象要件**: v2-01
- **優先度**: P1
- **前提**: どのクリニックにも所属せず、有効な招待も持たない認証済みアカウントを 1 件用意(例: Supabase Studio で auth ユーザーを作成し email 確認済みにする。clinic_members・invitations は作らない)。
- **手順**:
  1. `{base}/login` でそのアカウントでログイン。
- **期待結果**:
  - エラー「このアカウントに所属先がありません。管理者にお問い合わせください」が表示。
  - サーバー側で `signOut()` され、セッションは残らない(ブラウザを更新しても未ログイン状態)。

### AT-AUTH-006: 所属なし・有効な招待あり → 招待受け皿へ誘導
- **対象要件**: v2-01, v2-02
- **優先度**: P2
- **前提**: 未所属だが、そのメール宛の未受諾・未期限切れ invitation が存在するアカウント。手順:
  - Studio で auth ユーザー `pending@demo.local`(確認済み)を作成。
  - demo に対し AT-AUTH-017 で `pending@demo.local` 宛の招待を発行(受諾はしない)。
- **手順**:
  1. `{base}/login` で `pending@demo.local` でログイン。
- **期待結果**:
  - `/pending-invitations` へリダイレクト。見出し「参加できるクリニック」と「デモクリニック」+「参加する」ボタンが表示。
  - 監査ログに `auth.login`(member)が記録される。
- **備考**: 実装済み(AUTH-4 / 2026-07-22)。ページ描画(GET)は招待一覧の表示のみで副作用を持たない(旧実装は描画のたびに `token_hash` を再発行していたが廃止)。受諾用トークンの再発行(ローテーション)は「参加する」押下時(`openPendingInvitation` / POST)にのみ行い、対象は本人メール宛・未受諾・未期限切れの招待に限定(他人の招待 ID を推測してのローテーションを防ぐ。`src/features/invitations/actions.ts`)。押下後に生トークンを `/invite/{token}` へ渡し、以前に発行した同招待のリンクは無効化される。

### AT-AUTH-008: 未ログインで保護ルートへ直アクセス → /login

- **優先度**: P0
- **前提**: 未ログイン(cookie クリア)。

### AT-AUTH-009: パスワード再設定申請(列挙攻撃対策の同一応答)
- **対象要件**: v2-01
- **優先度**: P1
- **前提**: 未ログイン。SMTP/Inbucket が有効。
- **手順**:
  1. `{base}/reset-password` を開き、`owner@demo.local` を入力して「再設定リンクを送る」。
  2. 再度開き、存在しない `nobody@example.com` で同じ操作。
- **期待結果**:
  - どちらも同一の完了文言「入力されたメールアドレス宛に再設定用のリンクを送信しました。メールをご確認ください。」が表示される(アカウント有無を漏らさない)。
  - 実在アドレス宛にのみ Supabase Auth の再設定メールが届く(Inbucket 受信箱で確認)。メール内リンクは `{base}/auth/callback?next=/reset-password/update` を含む。
- **備考**: この再設定メールは Supabase Auth が送信(Resend ではない)。Resend は v2-23 の予約系通知用で、本エリアでは使用しない。

### AT-AUTH-010: 再設定リンク → 新パスワード設定 → ログイン
- **対象要件**: v2-01
- **優先度**: P1
- **前提**: AT-AUTH-009 で `owner@demo.local` 宛の再設定メールを受信済み。
- **手順**:
  1. 受信メールのリンクを開く(`/auth/callback` が code をセッション交換し `/reset-password/update` へ)。
  2. 見出し「新しいパスワードの設定」で新パスワード `new-premake-1`(8 文字以上)を入力し「パスワードを更新」。
  3. いったんログアウトし、新パスワードで再ログイン。
- **期待結果**:
  - 更新後、所属ホーム(`/demo`)へリダイレクト。
  - 新パスワードでログインできる。旧パスワード `premake-dev` ではログインできない。
  - 監査ログに `action='auth.password_update'`, `actor_type='member'` が記録される。
- **備考**: リンクが無効/期限切れの場合は `/auth/callback` が `/login` へ戻す。テスト後はパスワードを seed 値に戻す(`supabase db reset`)。

### AT-AUTH-016: 非 ops は /ops にアクセスできない
- **対象要件**: v2-25
- **優先度**: P0
- **前提**: `owner@demo.local`(is_ops=false)でログイン。
- **手順**:
  1. `{base}/ops` に直アクセス。
  2. `{base}/ops/metrics` にも直アクセス。

## 4. 補足: 実装との既知の乖離(spec_deviations)

1. **Google OAuth 未実装**(AT-AUTH-012): v2-01 / SCR-A01 は「メール+パスワード / Google」だが、ログインはメール+パスワードのみ。OAuth ボタン・`signInWithOAuth`・プロバイダ設定なし。
2. **招待メールの自動送信なし**(AT-AUTH-017): v2-02 は「メール招待」だが、現状は招待 URL を画面表示して手渡す運用(RESEND_API_KEY 設定後にメール化予定)。
3. **営業時間の日跨ぎ不可**(AT-AUTH-030): `open >= close` の文字列比較で 23:30–00:30 のような日付跨ぎ営業を登録できない。
4. **最後の owner ガードの TOCTOU 競合**(AT-AUTH-027): 「最後の active owner を外せない」防御はアプリ層のみで、同時操作の競合を DB レベルで根絶していない(申し送り #2)。
5. **レート制限なし**: ログインに IP/対象単位のレート制限が未実装(申し送り #3)。ブルートフォース耐性は本番前に要対応。
