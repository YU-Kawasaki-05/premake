## 1. テスト範囲と前提

### 1.1 対象機能
- **v2-09 予約台帳カレンダー**: 日ビュー(部屋レーン⇄スタッフレーン切替)、JST 表示、施術枠レイヤー、日付ナビ
- **v2-10 院内予約作成**: 受付の代理入力(患者検索/新規)、メニュー・担当・部屋・日時、枠外への警告付き強制作成
- **v2-11 予約変更・キャンセル**: 日時・担当・部屋の変更、キャンセル理由記録
- **v2-12 ステータス管理**: requested → confirmed → checked_in → done / cancelled / no_show の状態機械
- **v2-13 ダブルブッキング防止**: 部屋×時間・スタッフ×時間・患者×時間の 3 軸重複防止(同時実行含む)
- **v2-14 セッション管理**: 1 予約複数ステップ、別日分割、ステップごとの担当・部屋
- §4 F2(電話予約を台帳に入れる)・F3(アートメイク複数セッション)のシナリオ

### 1.2 対象コード・DB
- 画面: `src/app/(app)/[clinic]/page.tsx`(台帳ページ、ルート `/{slug}`)
- 機能: `src/features/bookings/`(actions.ts / booking-status.ts / session-layout.ts / components/day-ledger.tsx / booking-create-dialog.tsx / booking-detail-drawer.tsx / patient-picker.tsx)
- DB 制約: `supabase/migrations/20260707000001_init.sql`(`booking_sessions` の EXCLUDE 制約)

### 1.3 前提セットアップ(テスト開始前に整備)
1. テストクリニック `demo`(slug=`demo`)が存在し、営業時間が設定済み(例: 月〜金 09:00–19:00、土日定休)。
2. 部屋を最低 2 室登録: 「施術室1」「施術室2」(status=active)。
3. スタッフ(clinic_members)を 2 名以上、うち 1 名以上 `is_bookable=true`。
4. メニュー(services, status=active)を 2 件以上:
   - **単発メニュー**: 例「ヒアルロン酸」session_template = `[{kind:"procedure",duration_min:60,buffer_min:0}]`
   - **複数セッションメニュー**: 例「アートメイク眉」session_template = `[{kind:"counseling",duration_min:30,buffer_min:0},{kind:"procedure",duration_min:120,buffer_min:15}]`
5. 患者(patients)を 2〜3 件、うち 1 件は `email` あり、1 件は `email` なし。
6. 別クリニック `other`(slug=`other`)を 1 件用意し、その配下に患者・部屋・メニュー・スタッフを各 1 件(越境テスト用)。

- **メール確認**: Resend ダッシュボード(Emails ログ)または受信箱。MVP では通知は `notifications` テーブルへキュー投入 → worker が送信するため、`select * from notifications order by created_at desc` でも投入を確認できる。
- **監査ログ**: `audit_logs` テーブル。

## 3. テストケース詳細

### AT-BOOK-001: 台帳 日ビューの基本表示(部屋レーン×時間グリッド)
- **対象要件**: v2-09
- **優先度**: P1
- **前提**: staff でログイン。当日に予約が 1 件以上ある(なければ AT-BOOK-007 実施後に確認)。
- **手順**:
  1. `/{slug}`(例 `/demo`)を開く。
  2. 見出し「予約台帳」と当日の日付(例「2026/7/21(火)」)が表示され、日付横に「今日」バッジがあることを確認。
  3. 左に時間軸(01:00 刻みの目盛)、右に部屋レーン(部屋名ヘッダ付き)が横並びで表示されることを確認。
  4. 各レーンに 1 時間ごとの水平線が引かれていることを確認。
- **期待結果**:
  - 縦=時間、横=部屋のグリッドが表示される(既定は部屋レーン)。
  - 表示レンジは当日の営業時間(例 09:00–19:00)を基準に、はみ出す予約があれば自動的に拡張される。
  - 台帳描画は p95 < 500ms(§5 性能)。
- **備考**: 仕様(SCR-B01)は「15 分刻み・営業時間外は折りたたみ」だが、現状実装は 1 時間ごとの目盛線で営業時間 ± 予約範囲を単純表示(15 分グリッド線・折りたたみは未実装)。

### AT-BOOK-002: JST 時刻・ステータス色・予約チップ表示
- **対象要件**: v2-09
- **優先度**: P1
- **前提**: 当日に status の異なる予約が複数ある(confirmed / checked_in / done など)。
- **手順**:
  1. 台帳を開き、予約チップの表示を確認。
  2. チップ 1 行目に「開始時刻(JST HH:mm) 患者名」、2 行目にセッションラベル or メニュー名が表示されることを確認。
  3. ステータスごとに枠線色・背景色が異なることを確認(確定/来院/完了/承認待ち/不来院)。
  4. cancelled のチップは取り消し線 + 半透明で表示されることを確認。
- **期待結果**:
  - すべての時刻は Asia/Tokyo で表示される(UTC 保存・JST 表示。§AGENTS 日時規約)。
  - ステータス色は `--status-*` トークンに従う(確定=confirmed 色、来院=checked_in 色、完了=done 色、承認待ち=requested 色、不来院=no_show 色)。
  - **no_show の表示ラベルは「不来院」**(旧「無断」から変更, 2026-07-22)。`BOOKING_STATUS_LABELS.no_show='不来院'`。
- **備考**: チップ内の時刻は `HH:mm` のみ。ドロワーの日時表示は `HH:mm–HH:mm`(下記 AT-BOOK-015 参照)。仕様の推奨表示形式「7/12(金) 13:00–15:30」はドロワー等で日付を含む形が望ましいが、台帳内は時刻のみ表示。

### AT-BOOK-004: 日付ナビゲーション(前日/翌日/今日・?d=)
- **対象要件**: v2-09

### AT-BOOK-007: 院内予約作成: 既存患者を検索して予約
- **対象要件**: v2-10
- **優先度**: P0
- **前提**: staff でログイン。email ありの既存患者「山田 花子」、単発メニュー、is_bookable なスタッフ、部屋あり。当日以降の空き時間帯。
- **手順**:
  1. 台帳右上「新規予約」を押す。「新規予約」ダイアログが開く。
  2. 患者セクションで「既存患者」タブのまま、検索欄に「山田」を入力し検索ボタン(または Enter)。
  3. 候補一覧から「山田 花子」を選択(選択済みチップに Check アイコン + 氏名 + 電話が表示)。
  4. メニューで「ヒアルロン酸」を選択(所要時間・セッション数が表示される)。
  5. 担当を is_bookable なスタッフ、部屋を「施術室1」、日付=翌営業日、開始時刻=「14:00」を入力。
  6. 「予約を作成」を押す。
- **期待結果**:
  - トースト「予約を作成しました」が表示され、ダイアログが閉じる。
  - 台帳に 14:00 開始のチップ(患者名「山田 花子」)が表示される(ステータス=確定)。
  - DB: `bookings` に 1 行(`status='confirmed'`, `source='staff'`, `created_by`=操作者, `nominated_member_id`=担当, `booking_no` が `B-YYMMDD-XXXX` 形式)。`booking_sessions` に seq=1 の 1 行(`status='scheduled'`, time_range が 14:00–15:00 JST 相当の UTC tstzrange)。
  - email ありのため `notifications` に `kind='booking_confirmed'`, `recipient_type='patient'`, `recipient_email`=患者メール が投入される。
  - 確認 SQL:
    ```sql
    select b.booking_no, b.status, b.source, s.seq, s.time_range, s.status
    from bookings b join booking_sessions s on s.booking_id=b.id
    where b.clinic_id = :demo order by b.created_at desc limit 5;
    select kind, recipient_type, recipient_email, status from notifications order by created_at desc limit 3;
    ```
- **備考**: 仕様の booking_no 例は連番「B-250707-001」だが、現状実装は末尾 4 桁の大文字 16 進(`B-260721-A1B2`)。表示上の差異として記録。**No.36 実装済み(2026-07-22)**: 担当(`#bk-member`)の候補は **active な全メンバー**(is_bookable の別概念)。is_bookable=false の「佐藤院長」も候補に出る(F2 電話予約で非公開スタッフを代理担当に指定できる)。E2E `scripts/e2e-ops-flow.mjs`(b)で検証済み。

### AT-BOOK-009: 作成フォームのバリデーション(患者/メニュー/過去日時)
- **対象要件**: v2-10
- **優先度**: P1
- **前提**: staff でログイン。
- **手順・期待結果**(各ケースでフォームエラーが表示され、予約が作成されないこと):
  1. 患者未選択かつ新規氏名も空で送信 → 「患者を選択するか、新規患者名を入力してください」
  2. メニュー未選択で送信 → 「メニューを選択してください」
  3. 担当未選択で送信 → 「担当を選択してください」
  4. 部屋未選択で送信 → 「部屋を選択してください」
  5. 日付/時刻を過去(例 昨日 10:00)にして送信 → 「過去の日時は予約できません」
  6. メニューの session_template が不正(空配列や duration_min≤0)なメニューで送信 → 「メニューのセッション構成が不正です。メニュー設定を確認してください」
  7. (BC-NEW-05)DevTools で `startDate` を **暦上あり得ない値**(例 `2026-13-40`)に書き換えて送信 → 「日付が不正です」。regex を通っても実在日時でない値は `isRealJstDateTime` refine で弾かれ、`toISOString()` の RangeError で 500 にならない。
- **備考**: バリデーションはサーバー(Server Action)側 zod + アプリ層検証で行われる。クライアント側のみの回避では作成されないこと(DevTools で hidden 値を書き換えても弾かれること)を確認。BC-NEW-05(2026-07-22)で暦上不正日付を作成・リスケの両方で拒否するようにした。

### AT-BOOK-010: 越境防止(他クリニックの患者/メニュー/部屋/担当 ID)
- **対象要件**: v2-10, v2-13
- **優先度**: P0
- **前提**: staff(demo)でログイン。`other` クリニックの患者 ID・メニュー ID・部屋 ID・担当 ID を事前に控える。
- **手順**:
  1. 「新規予約」ダイアログを開く。
  2. DevTools で hidden input を書き換え、`serviceId` に other のメニュー ID を入れて送信。
  3. 同様に `roomId` / `memberId` / `patientId` を other の ID に差し替えて各々送信。
- **期待結果**(いずれも作成されず、それぞれのエラー):
  - 他クリニックのメニュー ID → 「メニューが見つかりません」
  - 他クリニックの担当 ID → 「担当スタッフが見つかりません」

### AT-BOOK-030: 予約変更(リスケ)のガード・競合
- **対象要件**: v2-11, v2-12, v2-13
- **優先度**: P1
- **前提**: staff でログイン。confirmed の予約 A(空き時間へ変更できる状態)、done または no_show の予約 B、別の予約 C が占有する時間帯を用意。
- **手順・期待結果**(No.1 リスケの異常系。UI で出せないものは Server Action `rescheduleBooking` を直接 / DevTools で送信):
  1. **status ガード**: done / no_show / checked_in / cancelled の予約 B のドロワーに「予約を変更」ボタンが**表示されない**。API を直接呼んでも「この予約は変更できません」で拒否(`RESCHEDULABLE={requested,confirmed}`)。
  2. **過去日時**: 予約 A のリスケダイアログで過去の日付/時刻を指定して「変更を保存」→「過去の日時には変更できません」。
  3. **暦上不正日付(BC-NEW-05)**: `startDate` を `2026-13-40` に改ざんして送信 →「日付が不正です」。
  4. **3 軸重複(23P01)**: 予約 A を、予約 C が埋めている部屋×時間帯(または担当×時間帯)へ変更 →「指定の時間帯は部屋または担当が既に埋まっています」。予約 A は元の枠のまま(全ロールバック)。
  5. **越境**: `memberId` / `roomId` を他クリニックの ID に改ざん →「担当スタッフが見つかりません」/「部屋が見つかりません」。`bookingId` が他クリニック → 「予約が見つかりません」。
  6. **status 変更後のリスケ**: 2 タブで予約 A のドロワーを開き、片方で先に status を checked_in に変えた後、もう片方でリスケを保存 →「この予約は変更できません」(Server Action が status をサーバー側で再取得し `RESCHEDULABLE={requested,confirmed}` で先に弾く)。※「別リスケを確定した後にもう片方でリスケ保存」は、最新 status(confirmed のまま)とセッション構成が有効なため**競合にならず後勝ちで上書き成功**する(単院受付の運用上は許容)。RPC の `p_expected_status` / セッション構成不一致による「他の操作と競合しました…」は、再取得と RPC の間に別コミットが割り込む真の同時実行のみで発火(`tests/booking-reschedule.test.ts` (c) で担保)。
- **備考**: `reschedule_booking` RPC は自己衝突(新枠 vs 旧枠)を避けるため EXCLUDE 2 本を `deferrable initially immediate` にし、Tx 内でのみ deferred(コミット時評価)にする。通常の作成(`createBooking`)は即時評価のままで挙動不変。手順 4 の他予約との衝突はコミット時に 23P01 で検出され全ロールバックされる。E2E `scripts/e2e-booking-reschedule.mjs` は正常系、DB テスト `tests/booking-reschedule.test.ts`(自己衝突シフト/衝突ロールバック/status 不一致/担当・部屋反映)で異常系を検証済み。
