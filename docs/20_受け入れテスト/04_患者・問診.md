# 受け入れテスト仕様書 — 患者・問診

> 対象要件: v2-15(患者マスタ), v2-16(名寄せ), v2-18(問診記入・閲覧) / 作成日: 2026-07-21 / 仕様根拠: docs/10_v2_仕様/ / 状態: draft

## 1. テスト範囲と前提

### 対象機能
- **v2-15 患者マスタ**: CRUD(氏名・かな・生年月日・電話・メール・外部カルテ番号・院内メモ・タグ)、検索(名前/かな/電話/メール)、患者詳細、予約・施術履歴(1 予約 = 1 コースの時系列)、問診回答セクション。
- **v2-16 名寄せ**: ゲスト予約(patient_id = null)の連絡先から既存患者候補を提示し、受付が確認して紐付ける。**自動マージしない**。
- **v2-18 問診記入・閲覧**: 予約確定後に問診リンクを送付 → 患者(ゲスト)が記入 → 院内は権限者のみ閲覧(閲覧ログ付き)。
- 横断: 患者 PII・問診の閲覧/検索/変更の監査ログ(v2-04)、RLS テナント分離(§5)、権限境界(AGENTS.md)。

### 対象画面・ルート(実装ベース)
| 画面 | URL | ロール |
|---|---|---|
| 患者一覧(SCR-C01) | `/{slug}/patients`(検索は `?q=`) | member(staff/owner/ops) |
| 患者詳細(SCR-C02) | `/{slug}/patients/{id}` | member |
| 問診テンプレ(SCR-E03) | `/{slug}/questionnaires` | owner のみ |
| 公開クリニックページ(SCR-P01) | `/c/{slug}` | ゲスト |
| ゲスト予約(SCR-P02) | `/c/{slug}/reserve` | ゲスト |
| 予約照会(SCR-P04) | `/c/{slug}/lookup`, `/c/{slug}/manage/{token}` | ゲスト(トークン) |
| 問診記入(SCR-P05) | (未実装 — §3 の該当ケース備考参照) | ゲスト(トークン) |

### 前提セットアップ
- ローカル or ステージング環境で `pnpm dev`(サンドボックスでは起動維持不可のため必ずローカル/CI で実施 — docs/30_申し送り 参照)。
- `supabase/seed.sql` 投入済み。デモクリニック `slug=demo` / `clinic_id=10000000-0000-4000-a000-000000000001`。
- **他クリニック分離テスト用に 2 院目を作成**しておくこと(ops でテナント作成 or SQL で `clinics` に別 slug を追加し、別 owner を `clinic_members` に登録)。以降これを `slug=other` とする。
- Supabase Studio(SQL Editor)へアクセス可能なこと(監査ログ・RLS 確認用)。
- Resend ダッシュボード or 実受信箱(問診依頼メール確認用)。ローカルは `notifications` テーブル /worker_jobs で代替確認可。

- 履歴・名寄せ・問診のテストには、公開予約 ON + 公開メニュー + open 枠が必要(seed の services/rooms/schedule_blocks を利用、なければ院内で作成)。

## 3. テストケース詳細

### AT-PAT-001: 患者新規登録(全項目)
- **対象要件**: v2-15
- **優先度**: P1
- **前提**: owner@demo.local でログイン。`/demo/patients` を開く。
- **手順**:
  1. 右上「患者を追加」をクリック。
  2. ダイアログ「患者を追加」で全項目入力: 氏名=`山田 花子`、かな=`やまだ はなこ`、生年月日=`1990-04-15`(日付ピッカー)、電話=`090-1111-2222`、メール=`hanako@example.com`、外部カルテ番号=`K-00123`、院内メモ=`アレルギー: 金属`。
  3. 「追加」をクリック。
- **期待結果**:
  - トースト「保存しました」が表示され、ダイアログが閉じる。
  - 一覧に「山田 花子 / やまだ はなこ / 090-1111-2222 / (更新日)」の行が追加される。
  - DB: `patients` に 1 行。全項目が入力どおり保存される(空欄は null)。`clinic_id` = demo。
    ```sql
    select name,kana,birthdate,phone,email,external_chart_no,notes,tags
    from patients where clinic_id='10000000-0000-4000-a000-000000000001' and name='山田 花子';
    ```
  - 監査: `audit_logs` に `action='patient.create'`, `actor_type='member'`, `target_type='patient'` が記録(→ AT-PAT-026 で詳細確認)。
- **備考**: タグ(tags)は仕様(v2-15)に含まれるが、患者フォームに入力欄が無い(現状実装: patient-form-dialog にタグ UI 未実装、常に `{}`)。spec_deviations_noted 参照。

### AT-PAT-002: 患者情報の編集(全項目更新)
- **対象要件**: v2-15
- **優先度**: P1
- **前提**: AT-PAT-001 の患者が存在。owner でログイン。
- **手順**:
  1. `/demo/patients` から「山田 花子」をクリック → 患者詳細へ。
  2. 右上「編集」をクリック。
  3. 電話を `080-3333-4444`、院内メモを `アレルギー: 金属 / 妊娠中` に変更、外部カルテ番号を空欄にする。
  4. 「保存」をクリック。
- **期待結果**:
  - トースト「保存しました」。詳細画面に変更後の値が反映(電話 080-3333-4444、外部カルテ番号「—」、院内メモ更新)。
  - DB: 該当行が更新され `updated_at` が進む。空にした外部カルテ番号は null。
  - 監査: `action='patient.update'` が記録される。
- **備考**: 編集は同一クリニック内で `.eq("clinic_id")` 縛り。差分(diff)は監査ログに記録されない(現状実装: update の recordAudit に diff 引数なし)。

### AT-PAT-003: 氏名未入力のバリデーション
- **対象要件**: v2-15
- **優先度**: P1
- **前提**: owner でログイン。「患者を追加」ダイアログを開く。
- **手順**:
  1. 氏名を空のまま、他項目のみ入力して「追加」をクリック。
- **期待結果**:
  - 登録されない。氏名必須のエラーが表示される(サーバー検証メッセージ「氏名を入力してください」、もしくはブラウザの required による送信ブロック)。
  - `patients` に行が増えていない。
- **備考**: 氏名 input には HTML `required` があるため、通常はブラウザ側で送信がブロックされる。サーバー検証(zod `min(1)`)も同メッセージを返す二重防御。

### AT-PAT-004: メール形式不正のバリデーション
- **対象要件**: v2-15
- **優先度**: P2
- **前提**: owner でログイン。「患者を追加」ダイアログ。
- **手順**:
  1. 氏名=`テスト 太郎`、メール=`not-an-email` を入力し「追加」。
- **期待結果**:
  - 登録されない。メール形式のエラーが表示される。
  - `patients` に不正メールの行が作られない。
- **備考**: メール input は `type="email"` のためブラウザ側でも弾かれる。サーバーは `z.union([z.email(), z.literal("")])` で検証し、失敗時は先頭 issue のメッセージ(汎用文言になる可能性あり)を返す。空文字は許容(未入力扱い)。

### AT-PAT-005: 入力値の境界(文字数上限)
- **対象要件**: v2-15
- **優先度**: P2
- **前提**: owner でログイン。
- **手順**:
  1. 氏名に 60 文字ちょうど → 「追加」→ 成功することを確認。
  2. 氏名に 61 文字 → 「追加」→ 失敗することを確認。
  3. 院内メモに 2000 文字 → 成功、2001 文字 → 失敗。電話 20 文字 → 成功、21 文字 → 失敗。外部カルテ番号 40 文字上限。
- **期待結果**:
  - 上限以内は保存成功、上限超過は保存されずエラー(サーバー zod: name/kana ≤60、notes ≤2000、phone ≤20、externalChartNo ≤40)。
- **備考**: フォーム側に maxLength 属性が無い項目はサーバー検証で弾かれる。

### AT-PAT-013: 検索文字列のインジェクション試験
- **対象要件**: v2-15, §5(PostgREST `.or` インジェクション対策)
- **優先度**: P0
- **前提**: 複数患者が登録済み。member でログイン。
- **手順**:
  1. 検索ボックスに次を順に入力し検索し、各回でエラー/情報漏えいが無いこと・患者テーブルが無傷であることを確認:
     - `a,email.ilike.%25@%25` (PostgREST フィルタ構文の注入狙い)
     - `x*():."'\` (フィルタトークン)
     - `%_` (ilike ワイルドカード)
     - `'); drop table patients;--` (SQL 風)
     - 全角/長文 100 文字超
- **期待結果**:
  - いずれもサーバーエラー(500)にならず、通常の一覧表示に戻る。
  - `sanitizeSearchTerm` により `,` `(` `)` `*` `:` `.` `"` `'` `\` `%` `_` が空白化され、連続空白は 1 つに畳まれ 60 文字で切られる。結果は「無害化後の文字列を部分一致」した患者のみ(多くは 0 件)。
  - 他クリニックの患者や全件が漏れて表示されない(`clinic_id` 縛りは維持)。
  - `patients` テーブルが削除・改変されていない(`select count(*) from patients;` が試験前と一致)。
- **備考**: パラメータは PostgREST 経由でエスケープされるため SQL 実行は起きないが、`.or()` はフィルタ構文を文字列連結するため無害化が必須。試験後にテーブル件数を SQL で確認すること。

## 付録: 監査ログ確認クエリ(共通)

```sql
-- 患者・問診まわりの監査を新しい順に確認
select action, actor_type, actor_user_id, target_type, target_id, diff, ip, created_at
from audit_logs
where clinic_id = '10000000-0000-4000-a000-000000000001'
  and (target_type in ('patient','questionnaire_template')
       or action like 'patient.%' or action like 'questionnaire%')
order by created_at desc
limit 50;
```
