# 受け入れテスト仕様書 — 公開予約(公開ページ・ゲスト予約・照会/変更/キャンセル・指名)

> 対象要件: v2-19, v2-20, v2-21, v2-22 / 作成日: 2026-07-21 / 仕様根拠: docs/10_v2_仕様/ / 状態: draft

## 1. テスト範囲と前提

### 1.1 対象機能
- **v2-19 クリニック公開ページ** `/c/{slug}`: クリニック情報・公開メニュー一覧・料金表示フラグ・自由診療の注意表記・医療提供主体の明示。症例写真/体験談なしの最小構成。
- **v2-20 ゲスト予約フロー**: メニュー →(指名 任意)→ 空き枠 → 連絡先入力 → 確認メール → リンククリックで確定。承認モード auto/manual の両分岐。空き枠の正しさ(open 枠・所要時間+バッファ・15分刻み・部屋/担当/既存予約の除外)。
- **v2-21 患者側予約操作**: 照会(予約番号+メール)・変更・キャンセル(トークンリンク・キャンセル期限)。
- **v2-22 施術者指名**: メニューごとの任意設定、「指定なし」既定。

### 1.2 前提セットアップ(ローカル/検証環境)
- アプリ: `pnpm dev`(http://localhost:3000)。以下 `{BASE}` = `http://localhost:3000`。
- Supabase ローカル: `pnpm db:start` → `pnpm db:reset`(`supabase/seed.sql` 投入)。REST は `http://127.0.0.1:54321`、DB は `postgresql://postgres:postgres@127.0.0.1:54322/postgres`。
- SQL 確認は Supabase Studio(http://127.0.0.1:54323)の SQL Editor か `psql "$DB_URL"` で実行。
- メール確認: 開発は `RESEND_API_KEY` 未設定でサーバーログに `[email:dev] would send { to, subject }` が出る(実送信なし)。実送信検証時は `RESEND_API_KEY` を設定し Resend ダッシュボード(Emails/Logs)で確認。送信元は現状 `premake <onboarding@resend.dev>`(本番はクリニック認証ドメインへ差し替え予定)。
- メール送信・前日リマインダーは Cron 経由。手動起動: `curl {BASE}/api/cron`(`CRON_SECRET` 設定時は `-H "Authorization: Bearer $CRON_SECRET"`)。通知は作成時点で `notifications`(status=queued)に積まれ、Cron 実行で送信される。

- クリニック: `slug=demo` / 名称「デモクリニック」/ 院長「佐藤 まこと」/ 〒150-0001 東京都渋谷区神宮前 1-1-1 / TEL 03-0000-0000 / **public_booking_enabled=true** / **booking_approval_mode=manual** / cancel_deadline_hours=24(既定)。

### AT-PUB-005: 公開メニューのみ掲載(非公開/アーカイブ除外)
- **対象要件**: v2-19(is_public / status)

- **手順**:

### AT-PUB-008: 公開オフ時に全公開導線が閉じる
- **対象要件**: v2-19 / v2-03(public_booking_enabled)
- **優先度**: P0

### AT-PUB-010: ゲスト予約 正常系(auto: メール確認で確定)
- **対象要件**: v2-20 / §4 F1
- **優先度**: P0
- **前提**: デモクリニックを **auto** に変更: SQL `update clinics set booking_approval_mode='auto' where slug='demo';`。受信可能なメール(または dev ログ)。
- **手順**:
  1. `{BASE}/c/demo` で「メディカルピーリング」の「予約する」→ `/c/demo/reserve` へ。
  2. 日付ナビ「翌日」で **明日** に移動。空き時刻チップ(例 13:00)を選択。
  3. 連絡先を入力: お名前「テスト 太郎」/ フリガナ「テスト タロウ」/ 電話「090-1111-2222」/ メール「guest+auto@example.com」。
  4. 「この内容で予約する」を押下。
  5. `curl {BASE}/api/cron` を実行して通知キューを送信。Resend ダッシュボード/受信箱(または dev ログ)を確認。
  6. メール内の「予約内容を確認する」リンク(= 確認/確定リンク)を開く。
- **期待結果(仕様)**:
  - 予約は最初 `requested` で仮押さえ(枠ロック)。連絡先入力後に「確認メール送信」画面が出る。
  - 確認メールのリンク(SCR-P03)を開くと予約が `confirmed` になり「ご予約が確定しました」と表示。確定通知が患者・院内双方に届く。
  - DB: `bookings.status='confirmed'`, `source='web'`, `guest_*` に入力値、`booking_sessions` が施術室・担当・時間で作成。
- **備考**: **現状実装(重大な仕様乖離)**: 確認メールのリンククリックによる確定ステップ(SCR-P03 / `confirm` purpose トークン)が無い。auto モードでは `createGuestBooking` が即 `status='confirmed'` で作成し、完了画面に管理リンクを直接表示する(「ご予約が確定しました」)。メールは `booking_confirmed` 通知(管理リンク入り)として Cron 送信され、確定用アクションリンクは含まれない。したがって手順5〜6は「確定操作」ではなく「確定済み通知の受領・管理リンク確認」になる。院内向け(member 宛)確定通知も現状は未送信(患者宛のみ enqueue)。spec_deviations 参照。
