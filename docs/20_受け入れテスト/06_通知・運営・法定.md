# 受け入れテスト仕様書 — 通知・運営・法定

> 対象要件: v2-23, v2-24, v2-26 + 00_要件定義 §6 法務要件 / 作成日: 2026-07-21 / 仕様根拠: docs/10_v2_仕様/ / 状態: draft

## 1. テスト範囲と前提

### 対象機能
- **v2-23 メール通知**: 予約確定・変更・キャンセル(患者/院内双方)、問診依頼。Resend + React Email。送信元表示はクリニック名。
- **v2-24 リマインダー**: 前日リマインダー(`notifications` + Vercel Cron `/api/cron`)。問診未記入催促を兼ねる。二重送信防止。送信失敗時の挙動。
- **v2-26 利用計測ダッシュボード**: ops のみ。週次 KPI(アクティブ日数、予約数 経路別、キャンセル率)。
- **§6 法務要件(リリースゲート)**: プライバシーポリシー・利用規約ページ、公開ページの医療提供主体明示・自由診療注記・症例写真なし、RLS/閲覧ログ、弁護士確認。

### 実装構成(手順を書く根拠)
- 通知は Server Action が `notifications` テーブルに `status='queued'` で積む(`src/features/notifications/enqueue.ts`)。実送信は Cron `GET /api/cron`(`src/app/api/cron/route.ts`)が `scanReminders()` → `processQueue()` の順で実行。
- メール送信は `src/lib/email.ts`。`RESEND_API_KEY` 未設定時はログ出力のみで成功扱い(開発)。差出人は `"{fromName}" <{address}>` 形式で、cron は `fromName=クリニック名`(ctx.clinicName)を渡す。アドレスは `EMAIL_FROM_ADDRESS`、未設定時は `onboarding@resend.dev`(No.21)。
- テンプレートは `src/features/notifications/templates.ts`。`NotificationKind` は 7 種:`booking_confirmed` / `booking_requested` / `booking_rescheduled` / `booking_cancelled` / `booking_cancelled_internal` / `reminder` / `booking_created_internal`。未知 kind は `renderNotification` が null を返し cron が failed で隔離(ROB-01)。
- 送信失敗はリトライ対象(No.20)。`processQueue` は失敗時に `notifications.attempts` を +1 し、上限 3 回未満は `queued` のまま(次回 cron で再送)、3 回到達で `failed`。context 取得失敗(参照先消失)は即 `failed`(error='context not found')。
- ops 画面は `/ops`(テナント一覧)・`/ops/metrics`(利用計測)。認可は `requireOps()`(`profiles.is_ops`)。
- 法定ページは `/privacy`・`/terms`。公開ページ `/c/[slug]` フッタからリンク。
- Cron スケジュールは `vercel.json`: `0 * * * *`(毎時)。認可は `CRON_SECRET` を定数時間比較(AUTH-3)。**本番相当(NODE_ENV≠development)で `CRON_SECRET` 未設定は 401**(SEC-01 fail-closed)。
- 院内向け通知の宛先は `resolveClinicInternalEmail()`:`clinics.email` 優先、無ければ active な owner の auth メールにフォールバック(どちらも無ければ enqueue しない)。

### 前提セットアップ
1. Supabase にマイグレーション適用済み(RLS 有効、`notifications` / `worker_jobs` / `audit_logs` テーブルあり)。
2. テスト用クリニック `test-clinic`(slug)が存在し、`name='テストクリニック'`、`director_name='山田太郎'`、`address`・`phone`・`business_hours` 設定済み。
3. 公開予約 ON のクリニックと、承認モード自動確定/手動承認をそれぞれ設定できること(`clinics.public_booking_enabled`, `booking_approval_mode` 等)。
4. Resend 本番検証用に `RESEND_API_KEY` を設定した環境(ステージング)を 1 つ用意。到達確認用の受信箱(実メールアドレス)を用意。
5. `CRON_SECRET` を設定した環境と未設定の環境を切り替えられること。
6. `APP_URL` が正しいホストを指すこと(管理リンク URL の検証に使用)。

### テストデータ(利用計測の期待値検証用)
`test-clinic` に直近 7 日で次を投入(SQL シードを scratchpad に用意):
- 予約 10 件(`source='web'` 6 件 / `source='staff'` 4 件)。
- うち `status='cancelled'` 2 件、`status='no_show'` 1 件、残り confirmed/done。
- `audit_logs` を 3 つの異なる日(created_at)に分散して投入(アクティブ日数=3 になるように)。
- 期待値: 予約数 10(Web 6 / 電話 4)、キャンセル率 30%(=(2+1)/10)、アクティブ日数 3。

## 3. テストケース詳細

### AT-NTF-001: ゲスト予約(自動確定)→ 患者に確定メール
- **対象要件**: v2-23
- **優先度**: P0
- **前提**: `test-clinic` 公開予約 ON・承認モード=自動確定。公開メニュー 1 件以上。空き枠あり。到達確認用受信箱 A を使用。`RESEND_API_KEY` 設定済みステージング。
- **手順**:
  1. 未ログインで `/c/test-clinic/reserve?service={serviceId}` を開く。
  2. 空き枠を選択し、氏名「予約 太郎」・メール(受信箱 A)・電話を入力して予約を確定する。
  3. 完了画面に予約番号が表示されることを確認。
  4. Cron を手動実行: `curl -s "$APP_URL/api/cron" -H "Authorization: Bearer $CRON_SECRET"`。レスポンス `{"ok":true,...,"sent":N}` を確認。
  5. 受信箱 A を確認。
- **期待結果**:
  - `notifications` に `kind='booking_confirmed'`, `recipient_type='patient'`, `recipient_email`=受信箱 A の行が作られ、Cron 実行後 `status='sent'`, `sent_at` が入る。
  - メール件名: `【テストクリニック】ご予約が確定しました`。
  - 本文に「予約 太郎 様」「メニュー: {メニュー名}」「日時: {`7/12(金) 13:00–15:30` 形式}」「予約番号: {booking_no}」と「予約内容を確認する」ボタン(`$APP_URL/c/test-clinic/manage/{token}` へのリンク)がある。
  - 管理リンクを開くと当該予約が照会できる。
  - 同時に院内宛 `kind='booking_created_internal'`(`recipient_type='member'`)も enqueue される(AT-NTF-008 で詳細検証)。
- **備考**: SQL 確認 `select kind,recipient_type,status,sent_at,attempts,error from notifications where booking_id='<id>' order by created_at;`。差出人表示名がクリニック名であること(From)は AT-NTF-010。

### AT-NTF-002: ゲスト予約(手動承認)→ 患者に受付メール(確認中)
- **対象要件**: v2-23
- **優先度**: P1
- **前提**: `test-clinic` を承認モード=手動承認に設定。受信箱 A。
- **手順**:
  1. AT-NTF-001 と同様にゲスト予約を送信。
  2. Cron 手動実行後、受信箱 A を確認。
- **期待結果**:
  - `bookings.status='requested'`。患者宛 `notifications.kind='booking_requested'`。
  - 件名: `【テストクリニック】ご予約を受け付けました(確認中)`。
  - 本文に「クリニックの確認後に確定します」旨と予約番号・日時・管理リンクがある。
  - 同時に院内宛 `kind='booking_created_internal'` が enqueue され、本文の強調文が「この予約は承認待ちです。管理画面での承認操作が必要です。」になる(auto の「自動確定済み」と対比。AT-NTF-008)。
- **備考**: 承認モードのフラグは `clinics.booking_approval_mode`(`auto`/`manual`)。前提設定は DB 直接更新でも可。

### AT-NTF-003: 手動承認予約を院内で確定 → 患者に確定メール
- **対象要件**: v2-23, v2-03
- **優先度**: P0
- **前提**: AT-NTF-002 の requested 予約が存在。owner でログイン。
- **手順**:
  1. owner が予約台帳で当該予約チップを開き、詳細ドロワーの「確定にする」を押す(requested→confirmed)。
  2. Cron を手動実行し、受信箱 A を確認。
  3. `select kind,recipient_type,status from notifications where booking_id='<id>' and kind='booking_confirmed';`
- **期待結果**:
  - 患者(受信箱 A)に `kind='booking_confirmed'`(件名 `【テストクリニック】ご予約が確定しました`)が queued→sent される。
  - **確定操作では院内宛の追加通知は積まれない**(booking_created_internal は予約作成時に既送。承認は院内スタッフ自身の操作のため。AT-NTF-008 参照)。
- **備考**: **実装済み(2026-07-22 / NT-NEW-1)**。`updateBookingStatus` の requested→confirmed 経路で `booking_confirmed` を enqueue する(旧・手動承認で確定メールが飛ばない乖離は解消)。E2E `e2e-public-booking.mjs` の承認フェーズが「確定にする」→ queued→sent を検証済み。

### AT-NTF-004: 院内代理予約(患者メールあり)→ 確定メール

### AT-NTF-007: 予約変更(日時・担当・部屋)→ 患者に変更メール
- **対象要件**: v2-23, v2-11
- **優先度**: P1
- **前提**: confirmed(または requested)予約(受信箱 A)が存在。owner ログイン。
- **手順**:
  1. 予約台帳で当該予約チップを開き、詳細ドロワーの「予約を変更」→ 変更ダイアログで新しい日付・時刻(必要なら担当・部屋)を選び保存。成功トースト「予約を変更しました」。
  2. Cron 手動実行後、受信箱 A を確認。
  3. `select kind,recipient_type,status from notifications where booking_id='<id>' and kind='booking_rescheduled';`
- **期待結果**:
  - 患者に `kind='booking_rescheduled'`(件名 `【テストクリニック】ご予約内容が変更になりました`)が queued→sent される。
  - 本文は「ご予約内容を変更しました。変更後の内容は以下の通りです。」+ メニュー・**変更後の日時**・予約番号 + 管理リンク「予約内容を確認する」。
  - `booking_sessions` の全 scheduled セッションが新開始時刻・新担当/部屋に再配置され、旧枠は解放される(`reschedule_booking` RPC で原子的)。
- **備考**: **実装済み(2026-07-22 / No.1・v2-11)**。院内リスケ `rescheduleBooking` が `booking_rescheduled` を enqueue。リスケ可能なステータスは requested / confirmed のみ(checked_in 以降・done・cancelled は不可)。**院内宛の追加通知は無い**(操作者が院内のため)。E2E は `e2e-booking-reschedule.mjs`。

### AT-NTF-008: 院内(member)通知 — 公開予約作成・患者セルフキャンセルで院内に通知
- **対象要件**: v2-23 / No.18・No.22
- **優先度**: P0
- **前提**: `test-clinic` に `email`(院内宛先)を設定(未設定時は active owner のメールにフォールバック)。公開予約 ON。
- **手順**:
  1. **作成**: 未ログインで公開予約を 1 件作成する(manual/auto 両方で強調文差を確認)。
  2. **患者キャンセル**: 作成した予約の管理リンク `/c/test-clinic/manage/{token}` から患者がセルフキャンセルする。
  3. 各操作後に Cron を手動実行し、`notifications` と院内受信先を確認。
- **期待結果**:
  - 手順1(作成)で `recipient_type='member'`, `kind='booking_created_internal'` が enqueue。件名 `【予約システム】新しい予約が入りました(要確認)`。本文の強調文は manual=「この予約は承認待ちです。管理画面での承認操作が必要です。」/ auto=「この予約は自動確定済みです。内容をご確認ください。」。CTA は院内台帳 URL(`{APP_URL}/{slug}`)で**患者用 manage トークンを含まない**。
  - 手順2(患者キャンセル)で `recipient_type='member'`, `kind='booking_cancelled_internal'` が enqueue。件名 `【予約システム】予約がキャンセルされました`。本文に「枠が空きました。台帳をご確認ください。」。
  - いずれも Cron 後に `status='sent'`。`select distinct recipient_type from notifications;` → `patient` と `member` の両方。
- **備考**: **実装済み(2026-07-22 / No.18・No.22)**。院内(member)向け通知は 2 経路のみ:公開予約作成(`booking_created_internal`)と患者セルフキャンセル(`booking_cancelled_internal`)。**院内スタッフ自身の操作(承認確定・院内キャンセル・院内リスケ・院内代理作成)では院内宛通知を積まない**(AT-NTF-003/004/006/007)。宛先解決は `resolveClinicInternalEmail()`(clinics.email → active owner メール)。E2E は `e2e-public-booking.mjs`(作成)・`e2e-self-cancel.mjs`(キャンセル)。

### AT-NTF-009: 問診依頼メール(確定後リンク送付)
- **対象要件**: v2-23, v2-18
- **優先度**: P1
- **前提**: 問診テンプレを紐付けたメニューで予約を確定(受信箱 A)。
- **手順**:
  1. 予約を確定させる。
  2. Cron 手動実行後、受信箱 A を確認。

### AT-NTF-028: RLS — notifications/audit_logs は anon 遮断・service role のみ書込
- **対象要件**: §5 セキュリティ, §6
- **優先度**: P0
- **前提**: anon key と service role key を用意。テスト用に `notifications`・`audit_logs`・`worker_jobs` に行がある状態。
- **手順**:
  1. anon key の Supabase クライアント(または REST)で `select * from notifications` / `audit_logs` / `worker_jobs` を試行。
  2. anon で `insert`/`update` を試行。
  3. service role(サーバー)から `insert`/`select` できることを確認。
  4. 認証済み一般 member で自クリニックの notifications/audit を select できるか、他クリニック分が見えないかを確認。
- **期待結果**(データモデル §3 RLS 表):
  - anon は select/insert/update すべて拒否(0 行 or エラー)。デフォルト拒否・anon ポリシーなし。
  - insert/update/delete は service role(システム)のみ成功。
  - member(自クリニック)/ops は select 可、他クリニックの行は見えない(テナント分離)。
  - `SUPABASE_SERVICE_ROLE_KEY` がクライアントバンドルに露出していない(ビルド成果物 grep で確認、`server-only` 遵守)。
- **備考**: 確認 SQL 例(psql/ダッシュボード SQL エディタ、anon ロールで): `set role anon; select count(*) from notifications;` → エラー/0。service role 経由は `enqueueNotification`/Cron が `createAdminClient()` を使う。監査ログ(閲覧ログ)の記録動作は患者・問診エリアの `recordAudit`/`questionnaire.view` ケースと合わせて検証。

## 補足: 実行順序と後片付け

- メール系ケースは「操作 → Cron 手動実行 → 受信箱/Resend/DB 確認」の 3 段で行う。Cron 未実行だと `queued` のまま届かない点に注意。
- リマインダー系(013・016・017・018)は「明日」判定に依存するため、`booking_sessions.time_range` を JST 翌日にセットしてから実行する。実行時刻が JST 深夜だと対象日がずれる。
- 各ケース後、テスト予約・通知行はクリニック単位でクリーンアップ(利用計測の集計値が後続ケースに影響するため)。
