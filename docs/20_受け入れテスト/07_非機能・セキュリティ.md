## 1. テスト範囲と前提

### 1.1 対象
本書は premake の**横断的な非機能・セキュリティ要件**を検証する。個々の業務フロー(予約・患者・問診等)の機能テストは各エリアの受け入れテストに委ね、本書は以下に絞る。

- RLS テナント分離(anon 直アクセス拒否・別クリニック横断アクセス拒否・行移送防止・権限昇格防止) — 00_要件定義 §5「全テーブル RLS」/ AGENTS.md
- 患者操作トークンの耐性(不正・期限切れ・列挙・エントロピー・ハッシュ保存) — 01_データモデル.md §2.5
- `SUPABASE_SERVICE_ROLE_KEY` のクライアント非露出 — AGENTS.md `server-only`
- Cron エンドポイントの認証 — v2-24
- 監査・閲覧ログの網羅性 — v2-04 / §6 法務(問診・患者データの閲覧ログ動作確認)
- 性能(台帳描画 p95 < 500ms、公開ページ LCP < 2.5s モバイル) — §5
- アクセシビリティ(公開ページ WCAG AA) — §5
- 対応環境(Chrome/Edge/Safari + タブレット、モバイルファースト公開) — §5
- TLS・バックアップ手順の存在 — §5

## 3. テストケース詳細

### AT-NFR-001: anon key で全業務テーブルへ REST 直アクセス → 拒否
- **対象要件**: v2-04 / §5「全テーブル RLS(テナント分離)」/ AGENTS.md「anon ポリシーなし」
- **優先度**: P0
- **前提**: `supabase start` 済み。`$ANON_KEY` 取得済み。
- **手順**:
  1. anon key のみで各業務テーブルを select する。代表テーブルを一巡:
     ```bash
     for t in patients bookings booking_sessions questionnaire_responses \
              schedule_blocks clinic_members invitations services notifications \
              audit_logs booking_access_tokens worker_jobs clinics; do
       code=$(curl -s -o /tmp/body.json -w "%{http_code}" \
         "$SB/rest/v1/$t?select=*&limit=1" -H "apikey: $ANON_KEY")
       echo "$t -> HTTP $code / $(head -c 120 /tmp/body.json)"
     done
     ```
  2. `Authorization: Bearer $ANON_KEY` を付けた場合も同様に実行する。
- **期待結果**:
  - どのテーブルも患者・予約・問診等の**業務行を 1 件も返さない**。
  - anon ロールにはテーブル権限が付与されていない(migration: `grant ... to authenticated, service_role` のみ)ため、`permission denied for table <t>`(PostgREST エラーコード 42501)を含む HTTP 401 または 403 が返る。
  - RLS も有効(anon ポリシーなし)のため、仮に権限があっても 0 件。二重防御が確認できること。
- **備考**: `clinics` も公開ページは service role 経由で取得しており、anon 直 select は不可であることが正。公開ページの表示は本テストの対象外(AT-NFR-016 で別途)。

### AT-NFR-002: anon ロールで SQL 直アクセス → permission denied
- **対象要件**: v2-04 / §5
- **優先度**: P0
- **前提**: `psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres"` で接続可能。
- **手順**:
  1. psql で以下を実行(superuser から anon ロールへ降格して確認):
     ```sql
     set role anon;
     select * from patients limit 1;      -- 期待: ERROR permission denied
     select * from bookings limit 1;       -- 期待: ERROR permission denied
     select * from booking_access_tokens;  -- 期待: ERROR permission denied
     reset role;
     ```
- **期待結果**:
  - 各 select が `ERROR: permission denied for table ...` で失敗する(anon にテーブル権限なし)。
  - `reset role` 後は superuser で参照可能(セットアップの健全性確認)。
- **備考**: 本テストは grant レベルの防御を確認する。AT-NFR-003 は RLS の行レベル防御を確認する。

### AT-NFR-003: 別クリニックの authenticated メンバーによる横断 select → 0 件
- **対象要件**: v2-04 / §5 テナント分離 / AGENTS.md
- **優先度**: P0
- **前提**: §1.2 のセットアップ SQL で clinic `demo-b` と `owner-b@demo-b.local` を作成済み。
- **手順**:
  1. B クリニックのメンバーとしてログインし access_token を取得:
     ```bash
     JWT_B=$(curl -s "$SB/auth/v1/token?grant_type=password" \
       -H "apikey: $ANON_KEY" -H "Content-Type: application/json" \
       -d '{"email":"owner-b@demo-b.local","password":"premake-dev"}' | jq -r .access_token)
     ```
  2. B のトークンで demo(clinic A)の患者・予約を横断参照:
     ```bash
     curl -s "$SB/rest/v1/patients?select=id,name&limit=5" \
       -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_B" | jq .
     curl -s "$SB/rest/v1/bookings?select=id,booking_no,guest_name&limit=5" \
       -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_B" | jq .
     ```
  3. 対照として、demo の owner(`owner@demo.local`)のトークンで同じ select を実行し、demo の行が返ることを確認。
  4. UI 経路も確認: B の owner でログインし、ブラウザで `/demo`(clinic A の台帳)へ直接アクセス。
- **期待結果**:
  - 手順 2: B のトークンでは demo クリニックの行は**1 件も返らない**(`[]`)。RLS の `is_clinic_member(clinic_id)` で他テナント行が除外される。
  - 手順 3: demo の owner では demo の患者・予約が返る(対照が機能)。
  - 手順 4: `/demo` は `notFound()`(404)。B の owner は demo の member でも ops でもないため、`requireMemberBase` が存在を秘匿する(`src/lib/auth.ts`)。
- **備考**: PII(患者名・ゲスト名)が他テナントに漏れないことがリリースゲート。

### AT-NFR-004: authenticated による clinic_id 書き換え(行移送)→ 拒否
- **対象要件**: v2-04 / §5(migration コメント「with check で clinic_id 書き換えを防ぐ」)
- **優先度**: P0
- **前提**: `owner@demo.local` のトークン `$JWT_A`。demo の患者 1 件の id を控える。
- **手順**:
  1. demo の患者 id を取得:
     ```bash
     PID=$(curl -s "$SB/rest/v1/patients?select=id&limit=1" \
       -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_A" | jq -r '.[0].id')
     ```
  2. その患者の clinic_id を B クリニックへ移送しようと update:
     ```bash
     curl -s -o /dev/null -w "%{http_code}\n" -X PATCH \
       "$SB/rest/v1/patients?id=eq.$PID" \
       -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_A" \
       -H "Content-Type: application/json" -H "Prefer: return=representation" \
       -d '{"clinic_id":"b0000000-0000-4000-a000-000000000001"}'
     ```
  3. 患者の clinic_id が変わっていないことを psql または demo owner の select で確認。
- **期待結果**:
  - update が `with check` 違反で拒否される(HTTP 403 / new row violates row-level security policy 相当)。移送後の clinic_id は A のメンバーシップを満たさないため書き込めない。
  - 患者行の clinic_id は demo(`10000000-...`)のまま。
- **備考**: 行移送を許すと A のメンバーが患者データを他テナントへ流出/隠蔽できるため P0。RLS の `with check`(clinic_id 一致)に加え、DB-N-1(2026-07-22)の複合 FK が参照先の clinic_id 一致も強制する(→ AT-NFR-032)。

### AT-NFR-008: 権限昇格防止 — authenticated が profiles.is_ops を書き換えられない
- **対象要件**: §5 / migration「権限昇格防止(監査 CRITICAL)」`revoke update on profiles ... grant update (full_name, updated_at)`
- **優先度**: P0
- **前提**: `nurse1@demo.local` のトークン `$JWT_N`(一般 staff)。
- **手順**:
  1. 自分の profiles を is_ops=true へ書き換え試行:
     ```bash
     NUID=00000000-0000-4000-a000-000000000003  # nurse1
     curl -s -o /dev/null -w "%{http_code}\n" -X PATCH \
       "$SB/rest/v1/profiles?id=eq.$NUID" \
       -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_N" \
       -H "Content-Type: application/json" \
       -d '{"is_ops":true}'
     ```
  2. `curl -s "$SB/rest/v1/profiles?id=eq.$NUID&select=is_ops" -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_N" | jq .` で値を確認。

- **期待結果**:
  - 手順 1: `is_ops` 列への update が権限エラー(`permission denied for column is_ops` 相当 / HTTP 401 or 403)。
  - 手順 2: `is_ops` は false のまま。プラットフォーム管理者へ昇格できない。
  - 手順 3: `full_name` 更新は成功。
- **備考**: is_ops=true になると全テナント横断アクセスが可能(`is_ops()` 経由)。最重要の昇格経路。

### AT-NFR-031: staff の直接 PostgREST 書き込みが owner 限定テーブルで拒否(AUTH-1)
- **対象要件**: v2-04 / §5 / AGENTS.md「RLS はデフォルト拒否」/ `supabase/migrations/20260722000005_db_security.sql`
- **優先度**: P0
- **前提**: `nurse1@demo.local`(staff)のトークン `$JWT_N`。demo のメニュー 1 件の id を控える(`SID`)。`owner@demo.local` のトークン `$JWT_A`(対照用)。
- **手順**:
  1. staff トークンで owner 限定テーブルの料金改ざんを試す(RLS の USING が owner 条件のため 0 行更新=不可視更新):
     ```bash
     SID=$(curl -s "$SB/rest/v1/services?select=id&limit=1" \
       -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_A" | jq -r '.[0].id')
     curl -s -X PATCH "$SB/rest/v1/services?id=eq.$SID" \
       -H "apikey: $ANON_KEY" -H "Authorization: Bearer $JWT_N" \

     ```

  4. 対照 B: service role または owner トークンで、上記メニューの料金が変わっていないこと・患者行が残存していることを確認。

### AT-NFR-032: 複合 FK でクロステナント参照(他院の部屋・スタッフ占有)を DB 遮断(DB-N-1)
- **対象要件**: v2-04 / §5 テナント分離 / `supabase/migrations/20260722000005_db_security.sql`
- **優先度**: P0
- **前提**: `psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres"`(superuser=RLS を通さず複合 FK 制約のみを検証)。§1.2 の clinic B(`demo-b`)と demo の部屋 id(`ROOM_A`)、B の予約 id(`BOOKING_B`)を用意。
- **手順**:
  1. clinic B の予約に、**demo(他院)の部屋**を割り当てて占有ロックしようとする(単一 FK `room_id→rooms.id` は通るが、複合 FK が clinic_id 不一致で発火する状況):
     ```sql
     insert into booking_sessions (clinic_id, booking_id, seq, kind, room_id, time_range, occupied_range)
     values ('b0000000-0000-4000-a000-000000000001', '<BOOKING_B>', 1, 'procedure',
             '<demo の ROOM_A>', '[2095-03-01T10:00:00+09:00,2095-03-01T11:00:00+09:00)',
             '[2095-03-01T10:00:00+09:00,2095-03-01T11:00:00+09:00)');
     ```
  2. 同様に、B の予約に demo のスタッフ(`member_id`)や demo のサービス(`service_id` on bookings)を参照させる insert/update も試す。
  3. 回帰確認: demo 内で正しい院内の部屋・スタッフを参照する `booking_sessions` の insert は成功すること、および `bookings` 削除で `booking_sessions` が cascade 削除されること(複合 FK=NO ACTION と単一 FK=cascade の共存)。
- **期待結果**:
  - 手順 1・2: `ERROR: insert or update on table "..." violates foreign key constraint`(SQLSTATE 23503)。他院のリソースを参照する行は作成できず、他院の部屋・スタッフの時間帯を EXCLUDE で占有ロックできない。
  - 手順 3: 正常な院内参照の insert は成功。`bookings` 削除時に子 `booking_sessions` は cascade 削除される(既存の削除経路を壊さない)。
- **備考**: 実装済み(DB-N-1 / 2026-07-22、コミット 8b8685e)。参照先に `(id, clinic_id)` の複合 UNIQUE(`<table>_id_clinic_uk`)を張り、業務テーブルに複合 FK(`booking_sessions_room_clinic_fk` / `booking_sessions_member_clinic_fk` / `booking_sessions_booking_clinic_fk` / `bookings_patient_clinic_fk` / `bookings_service_clinic_fk` / `bookings_nominated_clinic_fk` / `schedule_blocks_member_clinic_fk` / `schedule_blocks_room_clinic_fk` / `staff_service_assignments_*_clinic_fk` / `services_category_clinic_fk` / `services_template_clinic_fk` / `questionnaire_responses_*_clinic_fk` など計 15 本)を追加。nullable 列は MATCH SIMPLE で NULL 時素通し。RLS(行の可視性)を掻い潜って PostgREST 直叩きで他院リソースを参照する経路を DB 制約で塞ぐ。自動検証は `tests/db-security.test.ts` (d)(f)。
