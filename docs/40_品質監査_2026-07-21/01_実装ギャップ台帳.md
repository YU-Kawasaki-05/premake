# 実装ギャップ台帳 — 仕様にあって実装が無い/仕様と食い違う機能

> 作成日: 2026-07-21 / 監査対象: v2-01〜26(docs/10_v2_仕様/)/ 手法: Opus サブエージェント 8 ドメイン調査 → Opus 敵対的検証 → Fable による裏取り
> 対になる文書: [02_不具合レポート.md](02_不具合レポート.md)(ロジックバグ)・[docs/20_受け入れテスト/](../20_受け入れテスト/00_概要.md)(受け入れテスト仕様)

本書は「仕様に定義があるのに実装が無い/形だけ/仕様と食い違う」項目=**実装ギャップ**を、リリース判断ができるよう **判定と根拠付き** で一覧化したもの。純粋なロジックバグ(タイムゾーン、非トランザクション処理、採番衝突など)は 02_不具合レポート.md に分離した。

## 0. 判定の凡例

| 記号 | 意味 | 目安 |
|---|---|---|
| **A — リリース前必須** | 本番投入前に実装 or 対処しないと、患者安全・法務・情報漏えい・予約喪失・なりすましのいずれかが現実に起きる | リリースゲート |
| **B — 早期実装推奨** | 主要業務フローの一部。回避運用は一応あるが、導入後まもなく詰まる。公開予約を ON にするなら A に格上げ | 導入直後スプリント |
| **C — 仕様を実装に合わせて改訂** | 実装しない判断が妥当。仕様書(docs/10_v2_仕様/)を現状実装に合わせて直し、要件から落とす | ドキュメント修正 |
| **D — Phase 2 送りで妥当** | MVP の検証仮説に不要。導入後の要望で優先度決定という当初方針どおり | バックログ |
| **E — 低コスト即修正** | 数行〜小改修で仕様を満たせる。判断の余地が小さいので直す | 軽微対応 |

**「妥当か/実装必須か」の要約**: A と B(公開 ON 時)が「実装必須」。C・D が「実装しないのが妥当(ただし C は仕様書の修正が必要)」。E は「迷う必要なく直す」。

**最重要の前提**: デモ/本番の既定は `booking_approval_mode='manual'`(公開 Web 予約は院内承認制)、かつ `public_booking_enabled` はテナント設定でオン/オフ可能。**公開予約を当面オフ、または manual で運用する限り、公開予約系ギャップ(No.7〜10, 18)の実害はほぼ回避できる**。逆に公開予約を ON にする日が「実装必須」ラインを一段引き上げる。この分岐が本台帳の読み方の軸になる。

## 2. 予約中核(v2-09〜14)

### No.1 — 予約変更(リスケ)が未実装 【判定: B】
- **要件**: v2-11「日時・担当・部屋の変更、キャンセル理由記録」
- **現状**: `src/features/bookings/actions.ts` の export は `createBooking / updateBookingStatus / cancelBooking` のみ。日時・担当・部屋を変更する関数も UI も無い(`booking-detail-drawer.tsx` に `@implements v2-11` タグだけ残る)。変更時の重複再チェックも当然無い。
- **回避策**: キャンセル → 新規作成。ただし予約番号・作成履歴・監査の連続性が切れ、患者に「キャンセル」通知が飛ぶ(実際は変更なのに)。
- **判定理由**: 受付が毎日触る台帳の基本操作。単院運用でも「30分ずらす」「担当を振り替える」は日常発生する。回避策の副作用(誤ったキャンセル通知)が実運用に響くため **早期実装推奨**。実装時は重複再チェック必須。

### No.2 — セッションの別日分割・ステップ別担当/部屋・後からの追加が未実装 【判定: D(アートメイク主軸なら B)】
- **要件**: v2-14「別日への分割、ステップごとの担当・部屋」/ §4 F3(リタッチを追加セッションとして同一予約に紐付け)
- **現状**: `layoutSessions` は全ステップを開始時刻から同日連続で並べ、`createBooking` は全セッションに単一の担当・部屋を代入(`actions.ts:205-206`)。別日分割不可・ステップ別担当不可・後からのセッション追加関数なし。DB スキーマ(`booking_sessions` の member_id/room_id/seq)は対応済みで、**操作導線だけが無い**。
- **判定理由**: 「カウンセリング当日+施術は別日」はアートメイクの代表パターン。ただし当面は**別予約として2件登録すれば業務は回る**(履歴が「1コース」で束ねられないだけ)。アートメイクが導入クリニックの主軸メニューなら B、そうでなければ Phase 2 送りで妥当。**導入クリニックの実メニュー構成(Q9)で判断すべき事項**。

### No.3 — 患者×時間の重複警告が未実装 【判定: E】
- **要件**: v2-13 第3軸 / 01_データモデル §2.5「患者×時間はアプリ層で検知し警告表示(強制ブロックしない)」
- **現状**: `createBooking` は患者の既存予約との時間重複を参照しない。部屋・スタッフの2軸は DB EXCLUDE で担保済み。
- **判定理由**: 仕様自体が「警告のみ・ブロックしない」なのでデータ破壊はない。ただし同姓患者の取り違え・二重登録の検知に有用で、`createBooking` に patient_id の overlap 照会を1本足すだけ。低コストなので **即修正** 推奨。

## 3. 公開予約(v2-19〜22)

### No.7 — メール確認リンクによる確定フローが未実装 【判定: C または B(下記分岐)】
- **要件**: v2-20「メール確認リンクで確定」/ 02_画面設計 §4「requested で仮押さえ → 確認リンククリックで確定」/ SCR-P03
- **現状**: `createGuestBooking` は auto モードでフォーム送信の瞬間に `status='confirmed'` を直接作成。`purpose='confirm'` トークンも確認ランディングも無く、メール所有者検証ステップが完全に欠落。完了画面が管理リンクを直接表示するため、患者はメールを一度も受信せず予約・管理できる。
- **実害**: auto モードで bot/第三者が架空・他人のメールで即 confirmed 予約を成立させ枠を占有できる(レート制限なしと相乗)。
- **判定分岐**:
  - **公開予約オフ、または manual 運用のまま** → メール所有者検証の必要性が下がる(院内が承認するため)。**仕様を「auto=即確定、確認リンクは設けない」に改訂(C)** が現実的。
  - **公開予約を auto で ON にする** → 仮押さえ+確認リンク+自動解放(No.8)+レート制限(不具合レポート)をセットで **実装必須(A)**。
- **推奨**: MVP 検証段階では **manual 運用に固定し仕様を C で確定**。auto 公開は Phase 2 で anti-abuse ごと実装。

### No.8 — 未確認予約の30分自動解放(worker_jobs)が未実装 【判定: No.7 と一体(C/A)】
- **要件**: 02_画面設計 §4「30分以内未確認で自動解放(worker_jobs)」
- **現状**: `/api/cron` はリマインダーと通知キュー処理のみ。解放ジョブなし。requested 予約が枠を無期限に占有する。
- **判定理由**: No.7 の確認リンク方式とセットの機構。No.7 を C で仕様確定するなら本項も不要(C)。auto 公開するなら A。**単独では判断せず No.7 と一体で決める**。

### No.9 — 担当可否(staff_service_assignments)が空き枠・予約に反映されない 【判定: B(公開 ON なら A)】
- **要件**: §4 F1「公開ページの空き枠に反映(担当可能メニューのみ)」/ v2-07 / v2-22 指名候補
- **現状**: `availability.ts` は open な `schedule_blocks` を clinic_id と block_type だけで引き、担当可否を一切見ない。指名候補(`reserve/page.tsx`)も is_bookable+active で絞るのみで、そのスタッフが当該メニューを施術できるか(`staff_service_assignments`)を見ない。担当設定 UI(v2-07)は書き込めるが、**予約側で完全に死んでいる**。
- **実害**: 「アイラインは看護師 A のみ担当」と設定しても、B が確保した枠が空き枠に出て B に予約が入る。auto なら無審査で確定。院内予約(`createBooking`)も同じく担当可否を見ない。
- **判定理由**: 担当設定機能(v2-07)を実装した意味が消える。公開予約 ON では誤割当が患者に見える形で発生するため A。オフでも院内予約で誤担当が起きうるので **早期実装推奨(B)**。availability と createBooking に assignment の join/フィルタを追加。

### No.10 — 患者側の変更(リスケ)が未実装 & 院内予約の枠外作成の警告/block 自動生成が未実装 【判定: C】
- **要件**: v2-21「照会・変更・キャンセル」/ SCR-P04「変更(枠再選択)」、v2-10「schedule_block 外への強制作成も警告付きで可」/ 01_データモデル §2.4「block を自動生成」
- **現状**: (a) `ManageBookingView` はキャンセルのみで変更導線なし。にもかかわらず公開ページと完了画面は「確認・変更・キャンセル」と案内(**案内文だけ変更可を謳う**)。(b) `createBooking` は `schedule_blocks` を一切参照せず、枠外警告も block 自動生成もなく `schedule_block_id` が常に null。
- **判定理由**: どちらも「実装しない」判断が現実的。(a) は患者にキャンセル→再予約させれば足り、**案内文を「確認・キャンセル」に直す(C)**。(b) の block 自動生成は台帳の枠消費追跡の綺麗さの問題で、二重予約自体は EXCLUDE で防がれる。**仕様 §2.4 の「自動生成」を「院内予約は枠外でも作成可(枠紐付けは任意)」に緩和(C)**。ただし枠外作成時の**警告表示**だけは受付のミス防止に有用なので E で足してもよい。

### No.11 — 指名機能に @implements v2-22 タグが無い 【判定: E】
- **要件**: 07_トレーサビリティ規約「実装ファイルに @implements v2-XX」
- **現状**: 指名機能自体は実装されている(`reserve/page.tsx` で nominees 表示、`createGuestBooking` が nominated_member_id を保存)が、コードベースに `@implements v2-22` タグが存在しない(当初の実装状況調査で唯一タグの無い要件だった)。
- **判定理由**: 機能はあるのでタグを1行足すだけ。**即修正**。ただし指名候補が担当可否を見ない件は No.9、「指定なし」でも nominated_member_id が入る件は不具合レポート参照。

## 4. 患者・問診(v2-15, 16, 18)

### No.12 — 問診の患者記入フローが全面未実装 【判定: A】
- **要件**: v2-18「予約確定後にリンク送付 → 患者が記入」/ v2-23 問診依頼通知 / SCR-P05 / 01_データモデル(purpose='questionnaire' トークン、kind='questionnaire_request')
- **現状**: (1) 患者向け問診記入画面(SCR-P05)が存在しない、(2) `purpose='questionnaire'` トークン生成が皆無、(3) `NotificationKind` に `questionnaire_request` が無い、(4) `questionnaire_responses` への INSERT がコード全域で0件。**問診テンプレ管理(v2-17)だけ実装され、患者が記入する手段が丸ごと無い**。申し送りは S4/S6 で実装済みと記載するが実体がない。
- **実害**: アートメイク等に問診テンプレを紐付けても、患者は記入できず、院内は既往歴・アレルギー・妊娠授乳・ケロイド体質を施術前に把握できない。自由診療・侵襲的施術で **患者安全リスク**。
- **判定理由**: 侵襲的自由診療の事前問診は安全管理の根幹。実装するのが本筋。**紙問診で当面運用するなら、それを正式な運用として文書化し、仕様から v2-18 のオンライン問診を明示的に MVP 外へ落とす**判断が要る(なし崩しの未実装は不可)。いずれにせよ現状の「テンプレは作れるが記入できない」中途半端は解消必須なので A。

### No.13 — 問診回答の院内閲覧が形だけ + 閲覧ログが記録されない 【判定: A(法務ゲート)】
- **要件**: v2-18「院内は権限者のみ閲覧(閲覧ログ付き)」/ §6 法務リリースゲート「問診の閲覧ログ動作確認」
- **現状**: 患者詳細(`patients/[id]/page.tsx:48-62`)は問診回答を「テンプレ名+提出日」だけ表示し、回答本文(answers JSON)を select も表示もしない(answers を読むコードは全域0件)。閲覧時に `questionnaire.view` 監査も記録しない(記録は `patient.view` のみ)。
- **判定理由**: §6 のリリースゲート項目「問診・患者データの閲覧ログ動作確認」を満たさない。要配慮情報の閲覧記録は法務・コンプライアンス上の必須要件。No.12 とセットで **リリース前必須(A)**。

### No.14 — 名寄せ(候補提示・受付による紐付け)が未実装 【判定: B】
- **要件**: v2-16「ゲスト予約の連絡先から既存患者候補を提示、受付が確認して紐付け(自動マージしない)」/ SCR-C02
- **現状**: (1) guest_email/guest_phone を患者と突合して候補を出すロジックなし、(2) patient_id=null のゲスト予約を既存/新規患者へ後付け紐付けする導線なし、(3) `mergePatients`(`actions.ts:128`)は呼び出し元ゼロの死蔵コード。しかもその実装は source 患者を物理削除し notes/tags/birthdate を破棄する破壊的なもの(かつ非トランザクション)。
- **実害**: Web 予約者(guest_* 保持)が患者マスタに永久に取り込まれず、患者詳細の履歴に Web 予約が出ない。§5 のノーショー常習者への受付警告も機能しない。
- **判定理由**: 公開予約 ON が前提の機能。公開オフなら当面不要(D 相当)、公開 ON なら Web 予約と院内台帳が分断されるため B。死蔵の破壊的 `mergePatients` は接続前に論理削除+メモ統合へ作り直すこと。

## 8. 判断が必要な論点(ユーザー/リリース判定会の議題)

以下は「実装するかどうか」が技術判断でなくプロダクト判断のもの。ここを決めれば上表の A/B/C が確定する。

1. **公開 Web 予約を MVP で ON にするか**。ON なら No.7〜10, 14, 18, 22 と レート制限(不具合レポート)が実装必須ラインに上がる。OFF/manual 運用なら大幅に軽くなる。→ **最重要の分岐**
2. **問診をオンライン化するか、紙運用にするか**(No.12, 13, 19, 24)。侵襲的施術の事前問診なので、紙にするなら運用を正式文書化し仕様から落とす。
3. **アートメイクのセッション分割(別日)を MVP で要るか**(No.2)。導入クリニックの実メニュー(Q9)次第。
4. **Google OAuth を要件に残すか**(No.27)。残すなら実装ブロッカー、落とすなら仕様改訂。
5. **仕様書(docs/10_v2_仕様/)の改訂**: C 判定の項目(No.5, 6, 10, 27, 28, 31)は仕様を現状に合わせて直し、要件表から落とす/注記する。なし崩しの未実装を「意図した仕様」に昇格させる作業。
