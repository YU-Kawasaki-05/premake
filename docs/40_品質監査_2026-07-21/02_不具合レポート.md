> 作成日: 2026-07-21 / 監査手法: Opus 8ドメイン調査 → Opus 敵対的検証(critical/high は視点の異なる検証者2名)→ Fable 裏取り / 確定34件・反証0件

本書は「仕様どおりに作ったつもりでも壊れている/危険」なもの=**ロジックバグ・データ整合性・セキュリティ欠陥**を扱う。機能そのものの実装漏れは 01 に分離した。各項目は Opus 調査で検出し、独立した Opus 検証者による反証を経て、さらに Fable がコードを直接読んで裏取りした確定分。

## 重大度の凡例

- **Critical**: データ破壊・二重予約・情報漏えい・予約喪失が本番で現実に起こる
- **High**: 主要フローの障害・誤った表示/割当が患者に見える
- **Medium**: 限定的な誤動作・特定条件下の不整合
- **Low**: 軽微・実害限定的(別紙 03 に一覧)

## 1. 本番環境ですぐ顕在化するバグ

### BUG-01 — jstTime の二重タイムゾーン変換で、本番(UTC ランタイム)の施術枠時刻が +9h ずれる 【High】
- **file**: `src/features/schedule/week.ts:31-33`(使用箇所: `schedule-week-view.tsx:127`)
- **内容**: `jstTime` が `formatInTimeZone(toZonedTime(new Date(iso), TIME_ZONE), TIME_ZONE, "HH:mm")`。`formatInTimeZone` は生の UTC インスタントを受けて自前で TZ 変換する API なので、先に `toZonedTime` を通すと二重変換になり、実行環境の system TZ が Asia/Tokyo でないと `(targetOffset − systemOffset)` だけずれる。
- **実測**: `iso=2026-07-11T15:30:00Z`(=JST 00:30)を、TZ=UTC で `09:30`、TZ=America/New_York で `13:30`、TZ=Asia/Tokyo でのみ正しい `00:30` を返す。
- **実害**: 本番 Vercel(system TZ=UTC)で `/[clinic]/schedule` を開くと、SSR HTML が施術枠を +9h ずれた時刻で描画。東京ブラウザではハイドレーションで補正されるが (1) 誤時刻のフラッシュ、(2) hydration error ログ、(3) 端末 TZ が JST でない環境(出張・kiosk・VPN)では恒久的に誤時刻表示。
- **修正**: `toZonedTime` を外し `formatInTimeZone(new Date(iso), TIME_ZONE, "HH:mm")` にするだけ(1行)。同ファイルの `weekDays/shiftWeek` と `datetime.ts` の各ヘルパーは正しいと実測確認済みで、**この1箇所のみ**。
- **検証**: Opus 検証者2名とも confirmed(補正 High→Medium の意見あり)。Fable が week.ts / datetime.ts を精読しパターン差を確認。

### BUG-02 — 繰り返し施術枠の既定曜日が UTC 基準で1日ずれ、意図と別の曜日に枠が量産される 【Medium】
- **file**: `src/features/schedule/actions.ts:40`(`enumerateDates`)
- **内容**: 曜日チェックボックス未選択時の既定 `targetDows = [start.getUTCDay()]`。`start = new Date("${date}T00:00:00+09:00")`(JST 深夜=UTC では前日15:00)のため `getUTCDay()` が**前日の曜日**を返す。ループ内は `d+9h` で JST 補正しているが、既定曜日算出だけ補正漏れ(コメント「getUTCDay が JST 曜日に一致」は誤り)。
- **実測**: 開始 `2026-07-13`(月)で `start.getUTCDay()=0`(日)。曜日未選択で登録すると月曜ではなく日曜に枠が生成され、狙った月曜の枠は1件も作られない。UI は繰り返し ON でも曜日選択を必須化していないため到達可能。
- **実害**: 「開始日=月曜、終了日=1か月後、曜日ボックス未チェック」で登録 → 日曜(休診)に約4件の open 枠、月曜の枠は不在。公開予約 ON なら休診日に空き枠が出る。
- **修正**: 40行を JST 基準に(`Number(formatInTimeZone(start, TIME_ZONE, "i")) % 7` 等)。曜日を明示選択した場合は正常。

### BUG-03 — cancelBooking / cancelByToken が非トランザクションで、片方失敗時に枠がロックされる 【High】
- **file**: `src/features/bookings/actions.ts:332-348`、`src/features/public-booking/actions.ts:312-324`
- **内容**: ヘッダを `cancelled` に更新(error チェックあり)した後、`booking_sessions` の解放を**別 HTTP 往復**で実行し、その戻り値・error を捨てている。トランザクションでないため、ヘッダ成功・セッション更新失敗が起こり得る。
- **実害**: セッション更新が transient に失敗すると、ヘッダは cancelled なのに `booking_sessions.status='scheduled'` が残る。EXCLUDE 制約(`WHERE status='scheduled'`)がその部屋×時間・スタッフ×時間を占有し続け、同じ枠の再予約が 23P01 で弾かれる = **キャンセル済み予約に枠がロックされ予約不能**。ユーザーには「キャンセルしました」と成功表示される(error 握りつぶし)。DB 直接手当てなしには解けない。
- **修正**: ヘッダ+セッション更新を単一 RPC(SQL 関数)にまとめるか、少なくともセッション更新の error を検査して失敗時にヘッダをロールバック/リトライ。

### BUG-04 — booking_no がランダム4桁hex採番で衝突しうる(リトライなし) 【Medium】
- **file**: `supabase/migrations/20260707000001_init.sql:186`
- **内容**: `booking_no` default が `B-YYMMDD-<md5 の先頭4hex>`。4hex=65536通りで unique 制約は**全クリニック共通名前空間**。`createBooking`・`createGuestBooking` は default 依存で 23505 時のリトライが無く汎用エラーを返すだけ。仕様(`B-250707-001` の日次連番)とも不一致(実装漏れ側の No.—と重複)。
- **実害**: 同一日に予約が積むと誕生日問題で n=30〜50/日で約0.7〜1.9%衝突 → unique違反 → 「予約の作成に失敗しました」。再送で回避可だが稀に予約が一時的に取れない。
- **修正**: 採番を日次連番の DB 関数(採番テーブル or シーケンス)にする。当面の緩和は 23505 時のリトライ追加。

## 2. セキュリティ

### SEC-01 — CRON_SECRET 未設定時に /api/cron が無認証で開放(fail-open) 【Medium・既知】
- **file**: `src/app/api/cron/route.ts:16-21`
- **内容**: `CRON_SECRET` が env で optional。設定時のみ Bearer 検証し、**未設定なら誰でも GET 可能**(コメント「未設定=開発は許可」)。
- **実害**: 本番デプロイで CRON_SECRET を失念すると、/api/cron が公開エンドポイント化。第三者が繰り返し叩いて通知の一括送信や `booking_access_tokens` の発行を誘発できる。
- **修正**: 本番(`NODE_ENV==='production'` or `VERCEL_ENV`)では CRON_SECRET 必須の fail-closed に。env バリデーションで本番のみ required にするのが堅い。

### SEC-02 — 短い booking_no + メール一致 + レート制限なしで他人の予約を照会・キャンセル可能 【Medium・既知】
- **file**: `src/features/public-booking/actions.ts:256`(lookupBooking)
- **内容**: `lookupBooking` は `booking_no` と `guest_email` の一致だけで manage(キャンセル権付き)トークンを再発行。booking_no は日付部が推測容易+ランダム4hex(65536通り)。レート制限が全く無い(申し送り #3 既知)。
- **実害**: 被害者のメールと予約日を知る攻撃者が `B-YYMMDD-XXXX` を総当たりし、予約詳細(メニュー・日時)の閲覧と嫌がらせキャンセルが可能。
- **修正**: (1) レート制限(IP/対象単位、Upstash 等)、(2) booking_no のランダム部を拡張(BUG-04 と同時)、(3) 照会失敗のレスポンス時間を一定化。

### SEC-03 — member に bookings 等の DELETE 権限があり、cascade で問診が監査なしに消える 【Medium→Low】
→ 実装ギャップ台帳 No.32(RLS 修正)を参照。RLS で member の DELETE を落とせば塞げる。監査 append-only 化も同じ修正で対応。

> レート制限の全面欠如(ログイン・ゲスト予約・照会・検索)は申し送り #3 の既知事項。SEC-01/02 の前提でもあり、**本番前にまとめて対処すべき横断課題**。

## 3. 通知・処理系の堅牢性

### ROB-01 — renderNotification に default 節が無く、未知 kind で cron が全滅 【High(潜在)】
- **file**: `src/features/notifications/templates.ts`(switch)、`src/app/api/cron/route.ts:104`(processQueue)
- **内容**: `renderNotification` の switch に default 節が無い。将来 `questionnaire_request` 等が notifications に積まれると undefined を返し、processQueue が「Cannot destructure」で例外 → **その実行の残り通知送信が全滅**。
- **実害**: 問診依頼(実装ギャップ No.19)を追加した瞬間、あるいは想定外 kind が1件混じるだけで、その cron 実行のキュー全体が送信されなくなる。
- **修正**: switch に default 節(未知 kind をスキップ+ログ)。1件の不正データが全体を止めない設計に。

### ROB-02 — メール送信失敗のリトライが無く通知が恒久消失 【High】
→ 実装ギャップ台帳 No.20 参照(worker_jobs 不使用)。堅牢性の観点でも本番前対処が望ましい。

### ROB-03 — processQueue に排他制御が無く二重送信の窓がある 【Low→Medium】
- **file**: `src/app/api/cron/route.ts:83`
- **内容**: queued を select → 送信 → sent 更新の間にロックが無い。cron が重複起動(Vercel のリトライ等)すると同一通知を二重送信しうる。
- **修正**: 送信前に `status='sending'` へ条件付き UPDATE(楽観ロック)して1回だけ処理。

### ROB-04 — 深夜作成の翌日予約でリマインダーが欠落しうる 【Low】
- **file**: `src/app/api/cron/route.ts:31`
- **内容**: リマインダー走査が「実行時点の翌日」だけを対象にするため、cron 実行間隔と JST 深夜境界の兼ね合いで、直前に作られた翌日予約が対象窓から漏れる可能性。
- **修正**: 走査窓を「翌日 + 当日残り」に広げる、または送信済みフラグベースに。

## 5. 確認して問題なしだった点(誤検出を防ぐための記録)

監査で「疑ったが正しかった」点。今後の再監査で二度手間にしないため明記する。

- **部屋×時間・スタッフ×時間の二重予約は DB EXCLUDE で原子的に防止**。`createBooking` はセッションを単一 bulk insert で投入するため「1本目成功・2本目違反」の部分成功は構造上起きない(単一 INSERT=単一トランザクションで全ロールバック)。違反は 23P01 で捕捉しヘッダ+新規患者を補償削除。
- **同時実行**: 2受付が同一枠に同時 createBooking しても DB EXCLUDE で片方が確実に 23P01 失敗し、敗者は自身のヘッダ+患者を補償削除。公開側も同様。
- **状態機械が v2-12 と一致しサーバー強制**: `nextStatuses` は requested→{confirmed,cancelled} / confirmed→{checked_in,no_show,cancelled} / checked_in→{done,cancelled} / done・cancelled・no_show=終端。`updateBookingStatus` が現状取得→許可遷移照合。cancelled は専用 `cancelBooking` に限定。
- **RLS はデフォルト拒否・anon ポリシーなし・テナント分離**(clinic_id + slug 再解決 + cross-tenant memberId 検証)が一貫。service role は `admin.ts` に server-only 限定。`SUPABASE_SERVICE_ROLE_KEY` はクライアント露出なし('use client' + admin/env 併存0件)。
- **検索インジェクション対策**: `sanitizeSearchTerm` が `.or` を使う全2経路に適用。他経路なし。
- **Next.js 16 規約準拠**: 全 page/layout/route で params・searchParams・cookies を await。revalidateTag 不使用(revalidatePath のみ)で第2引数漏れ該当なし。proxy.ts は関数名 proxy・nodejs 前提で準拠。
- **日時の中核ヘルパー**: `datetime.ts` の formatDate/formatDateTime/formatTimeRange、`jstDateTimeToUtcISO`、`booking-status.ts` の jstMinutesOfDay、day-ledger の位置計算はいずれも TZ 非依存で正しい(BUG-01/02 の2箇所のみが例外)。
- **ビルド健全性**: `pnpm typecheck` は exit 0(green)、`pnpm lint` も exit 0(警告1件: cron/route.ts:127 の useOptionalChain)。
- **dow 規約(0=日〜6=土)** が設定保存・台帳読取・公開表示で一貫。
- **過去日時ガード**: createBooking / createGuestBooking とも開始 < now を拒否。
