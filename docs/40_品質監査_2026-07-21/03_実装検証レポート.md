### 実 DB / 型検証(オーケストレーター実測)
- **RPC 存在・権限**: `cancel_booking(uuid,uuid,text)` が public に作成され、EXECUTE は `authenticated`・`service_role` のみに付与(PUBLIC は revoke 済み)。→ ✅ Data API から解決可能。実装者が懸念した「明示 GRANT が無いと new-cloud-default で呼べない」問題はクリア。
- **型乖離(実装者が最も懸念した点)**: `pnpm db:types` を再生成すると codegen は `p_reason: string`(NULL 非許容)を出力。手書きの `string | null` と食い違い、呼び出し側 `p_reason: parsed.data.reason || null` が **`pnpm typecheck` で TS2322 エラー(ビルド破壊)**になることを実測で確認。→ ⚠️ **要修正**(下記で対応)。
  - 対応: マイグレーションの引数を `p_reason text default null` にし、codegen が optional 引数(`p_reason?: string`)として生成 → 呼び出し側の `|| null` を除去 → `pnpm typecheck` 緑を確認。生成型(手書きでない)を正としたまま NULL を渡せる形になり、CI での再生成でも壊れない。
- **BUG-03 の原子性・テナント安全性を実 DB テストで実証**: `tests/booking-flow.test.ts` に 2 ケース追加(既存テストは RPC を通らず `booking_sessions` を直接更新していたため BUG-03 修正を検証できていなかった)。
  - 「cancel_booking RPC がヘッダとセッションを原子的にキャンセルし枠を解放する」= 実 DB でヘッダ `status=cancelled`・`cancel_reason`・`cancelled_at` がセットされ、全セッションが `cancelled` に解放され、**解放後の同一枠(room+member+time_range)を別予約で再取得できる**ことを確認。
  - 「他クリニック ID ではロールバックし予約を変更しない」= `no_data_found` 例外でトランザクション全体がロールバックし、予約が `confirmed` のまま変わらないことを確認(セッション UPDATE から clinic_id 述語を落とした件のテナント安全性の裏取り)。
