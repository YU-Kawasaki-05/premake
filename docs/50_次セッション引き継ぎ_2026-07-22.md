### 4-5. 品質保証のやり方(前セッションで有効だったパターン)
- **Workflow ツール**でパイプライン化: 実装 → 独立検証(反証) → 統合。`model: 'opus'`、`schema` で構造化出力。
- **敵対的検証**: 実装したエージェントとは別の Opus エージェントに「この実装は仕様を満たさない/バグがある、と証明せよ」と反証させる。critical/high は視点を分けて複数。
- **落とし穴**: `schema`(StructuredOutput)を厳しくしすぎると再試行上限でエージェントが落ちる(前回 booking-core が失敗)。スキーマは緩めに、または markdown 返しにするフォールバックを用意。
- 各実装は必ず `pnpm typecheck`(= `next typegen && tsc --noEmit`)と `pnpm lint`(biome)を green にする。`any` 禁止。

現状の受け入れテスト仕様書(`docs/20_受け入れテスト/`)は、前セッション執筆時点で **「期待結果 = 仕様準拠、備考に『現状実装: 〜』でズレを明記」** という方針で書かれている。実装が進む/仕様側を改訂すると、この前提が変わるので改修が必要になる。改修の指針:

1. **実装漏れを実装した項目**(タスクA で埋めたもの)= 該当テストケースの備考「現状実装: 〜(未実装)」を削除し、実装後の挙動に合わせて手順・期待結果を実機準拠に精緻化する。テストが「実装済み機能の検証」として成立する状態にする。
2. **仕様側を改訂して『実装しない』と決めた項目**(台帳 C 判定など)= 期待結果を仕様準拠のまま残すのではなく、**改訂後の仕様(=実装の実態)に合わせて期待結果を書き換える**。該当テストが恒久的に不合格になるのを防ぐ。どの仕様をどう改訂したかは `docs/10_v2_仕様/` 側の更新と整合させること。
3. **Playwright 検証(§4-4)で判明した実際の画面遷移・文言・バリデーションメッセージ**にテスト手順を合わせる。前セッションはブラウザ実行できなかったため、手順は実装コードから推定した文言で書いている箇所がある。実機で確認した正確な文言・URL に直す。
4. **改修は必ず「仕様(docs/10_v2_仕様/)× 実装 × テスト」の三者整合**を保つ。実装だけ直してテストを放置しない。ユーザーは「実装漏れは絶対にないように」と強く求めているので、**テスト側でも網羅性(v2-01〜26 全カバー)を再確認**する。
5. 各ファイルの `spec_deviations`(前セッションのサブエージェントが列挙した実装ズレ)は、`docs/40_品質監査_2026-07-21/01_実装ギャップ台帳.md` の No. と対応する。台帳の判定(A〜E)を見ながら「実装で解消/仕様改訂で解消」を判断してテストを直す。

進め方: これも **Opus サブエージェントで、実装済みコードを読ませて改修 → 別エージェントで敵対的にレビュー**(手順が実機と食い違わないか、期待結果が仕様と実装の両方に整合するか)。改修したテスト仕様書は実装ブランチに一緒にコミットしていく(実装とテストを同じ PR で対にすると差分がレビューしやすい)。

## 7. 技術コンテキスト・制約・落とし穴(AGENTS.md 要点の再掲)

### Next.js 16(訓練データとの差分。間違えると壊す)
- `middleware.ts` は**廃止** → ルートの `proxy.ts`(関数名も `proxy`、nodejs ランタイム)。
- `cookies()` / `headers()` / `params` / `searchParams` は **await 必須**。
- `PageProps<'/path'>` / `LayoutProps<'/path'>` 型ヘルパーがグローバル生成される(`next typegen` が前提。`rm -rf .next && next typegen`)。
- `revalidateTag(tag, profile)` は**第2引数必須**。Server Action での即時反映は `updateTag(tag)`、ルーター再描画は `refresh()`。
- Turbopack がデフォルト(`--turbopack` フラグ不要)。
- 実装前に `node_modules/next/dist/docs/` の該当ガイドを読む(AGENTS.md 冒頭の指示)。

### セキュリティ境界(必読・違反はリリースブロッカー)
- RLS は**デフォルト拒否・anon ポリシーなし**。未ログイン導線(公開ページ・ゲスト予約・問診)は Server Action / Route Handler + `createAdminClient()`(service role)+ アプリ層検証(トークン・zod・レート制限)で実装。
- 院内機能は `requireMember(clinicSlug, role?)` を Server Action / layout の入口で必ず呼ぶ。
- 患者情報・問診の閲覧は `recordAudit()` で閲覧ログを残す。
- `SUPABASE_SERVICE_ROLE_KEY` をクライアントに露出させない(`server-only` を守る)。

### コーディング規約
- Biome(`pnpm lint`)。TypeScript strict、`any` 禁止。
- UI は `src/components/ui/`(shadcn 再テーマ済み)。Tailwind 標準色の直書き禁止 → `docs/10_v2_仕様/04_デザインシステム.md` のトークン(CSS 変数)を使う。
- 日時は **UTC 保存(tstzrange)・表示は Asia/Tokyo(date-fns-tz)**。表示形式は `7/12(金) 13:00–15:30`。日時ヘルパーは `src/lib/datetime.ts`(正しい実装の見本)。
- 実装ファイルに `@implements v2-XX` タグを付ける。
- **コミットはユーザーの明示指示があるとき** → 本作業ではユーザーが「コミット & push しながら進めろ」と指示済みなので、実装ブランチでこまめにコミット可。
