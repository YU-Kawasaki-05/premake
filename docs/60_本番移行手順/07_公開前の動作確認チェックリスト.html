STEP 7 公開前チェック

公開 Web 予約をオンにした状態で、患者の申し込みから院内の確定・当日の受付・予約の変更・キャンセル・メール通知までが本番で通るかを、チェックボックスで確認します。

目安 約120分実機で確認一部は開発担当者に依頼

この STEP でやること

実際の運用を始める前に、中核フロー(患者が Web から申し込む → 院内が確認して確定 → 当日の受付 → 施術完了。必要なら変更・キャンセル)が本番で正しく通るかを確認します。下のチェックボックスを、実際に画面を操作しながら 1 つずつ確認してください。

各項目の AT-... は受け入れテスト仕様書の管理番号です。1 項目でも「おかしい」と思ったら、その番号を開発担当者に伝えてください。

ⓘこのページと「受け入れテスト仕様書」の役割分担

このチェックリスト= 本番の環境で、最低限これだけは確認するという項目です。すべて画面を見て自分で判断できる粒度で書いてあります。

docs/20_受け入れテスト/= 全機能の網羅的な検証仕様です。全 219 ケース(うちリリース必須の「P0」が 86 件)あり、データベースを直接見る確認や、別のクリニックのデータを使った越境テストを含みます。こちらは開発担当者が実施します。

中核業務だけを最短で通したいときは 00_最優先MVPパス.md を上から順に実行します(このチェックリストの並びは、おおむねその順番に合わせてあります)。

クリニック担当者 画面を見て自分で判断できる項目開発担当者 データベースやコマンドが必要な項目

ⓘ確認をはじめる前の準備

STEP 3〜6 が完了していることを確認してください。特に次の 6 点がそろっていないと、このチェックは正しく行えません。

  • APP_URL が本番の URL になっている(STEP 3)。メールの中のリンクが localhost になっていたらここが原因です
  • CRON_SECRET を設定し、定期実行が動いている(STEP 5)。未設定だとメールが一切送られません
  • メール送信(Resend)の設定が済んでいる(STEP 4)
  • クリニック設定の「基本情報」のメールアドレスが入っている(STEP 6-2)。院内へのお知らせメールの宛先です
  • 「患者向けオンライン予約」がオンで、確定方法が「院内で確認してから確定(推奨)」(STEP 6-5)
  • 自分で受信できるメールアドレスを 2 つ用意する(患者役と院内役。院内役は「基本情報」に入れたアドレスと同じで構いません)

⚠本番環境での確認です。テストで作ったデータは必ず片づけてください

ここでの確認は本番のデータベースに対して行います。作ったテスト予約は最後に必ずキャンセルし、テスト用に登録した患者は「患者」画面から削除してください(患者の削除は院長=管理者だけができます)。片づけを忘れると、開院初日の台帳にテスト予約が残ります。

⚠メールはすぐには届きません(最大 1 時間)

メールは1 時間ごとに動く定期実行がまとめて送ります(STEP 5)。ボタンを押した直後には届きません。⑧ の通知の確認は、①〜⑦ をひととおり終えてから、時間をおいてまとめて行うのが効率的です。すぐに確認したい場合は、開発担当者に定期実行を手動で 1 回動かしてもらってください。

① ログインと権限 クリニック担当者

② 院内での予約作成(電話予約の想定) クリニック担当者

③ 当日の流れ(来院 → 施術完了) クリニック担当者

④ 予約の変更(リスケ) クリニック担当者

今回から使えるようになった機能です。以前は「キャンセルして作り直す」しかありませんでした。

⑤ キャンセルと枠の空き戻り クリニック担当者

⑥ 患者側の公開 Web 予約 クリニック担当者

必ずスマートフォンで、本番の公開ページ(本番URL/c/スラッグ)を開いて確認してください。患者の 9 割はスマートフォンから見ます。

⑦ 名寄せ(Web 予約を患者台帳に紐付ける) クリニック担当者

今回から使えるようになった機能です。⑥ で入れた Web 予約を使って確認します。

⑧ メール通知 クリニック担当者

ここは①〜⑦ を終えたあとにまとめて確認します。メールは 1 時間ごとの定期実行がまとめて送るため、押した直後には届きません。迷惑メールフォルダも必ず見てください。

⑨ バッファ(準備・清掃の時間)が効いているか クリニック担当者

メニューに設定したバッファ(片づけ・清掃の時間)が無視されると、施術が終わった直後に次の患者が入ってしまいます。ここは現場が最も困る不具合なので必ず確認してください。

ⓘ台帳のチップにはバッファは表示されません

台帳のチップに出る「開始〜終了」は施術の時間だけで、バッファは含みません。そのため、チップの直後に見た目のすき間が無くても、実際にはバッファぶんの時間は予約が入らないように押さえられています。「チップがくっついているから詰めて入れられる」と誤解しないようにしてください。

⑩ 開発担当者に依頼する確認(画面では判断できません) 開発担当者

ここから下はデータベースを直接見る操作やコマンドが必要で、画面を見ただけでは合否を判断できません。この一覧をそのまま開発担当者に渡して、実施と結果の報告を依頼してください。患者情報の漏えいに直結する項目なので、1 つでも未確認のまま公開しないでください。

このチェックリストでは合格にできない、残る注意点

✓以前「未対応」だった 3 点は解消しました

前の版のこのページでは、予約の変更(リスケ)・手動承認したときの患者への確定メール・院内向けのお知らせ通知の 3 点を「現状の実装では未対応」としていましたが、すべて実装済みです。今回は ④ と ⑧ のチェック項目として確認します。

⚠次の点は運用でカバーするか、公開後の課題として残ります

  • 連続投稿を止める仕組み(レート制限)が未実装(AT-NFR-014)。公開予約はいたずら投稿を機械的に止められません。公開直後は台帳と院内へのお知らせメールを毎日確認し、不審な予約はキャンセルしてください。
  • 「メール確認後に自動確定」の確認リンクが未実装(AT-PUB-010)。この設定を選ぶと申し込みと同時に確定になります。「院内で確認してから確定(推奨)」を使ってください(STEP 6-5)。
  • 法定ページ(プライバシーポリシー・利用規約)は、構成の整った暫定版です。本文の確定と弁護士・専門家の確認は終わっていません(AT-NTF-026・AT-NTF-027 は本文が確定するまで合格にできません)。開院前に必ず終わらせる作業です。
  • オンライン問診は使いません。MVP では紙で運用するというスコープ判断です(AT-PAT-021〜024 は対象外)。
  • 施術枠は営業時間・休診日と自動で突き合わされません。営業時間外の枠を作ると患者に見えてしまうため、枠の登録時に目で確認してください(STEP 6-2)。
  • 週単位の一覧・承認待ち専用の画面・Google ログインはスコープ外です(今回は作りません)。

くわしい背景と対応方針は 未対応事項と注意点 を参照してください。

公開判定の目安

✓①〜⑨ を自分でチェックでき、⑩ を開発担当者が確認できたら本番開始の準備完了

患者が Web から申し込む → 院内にお知らせメールが届く → 台帳で内容を確認して「確定にする」→ 患者に確定メールが届く → 当日「来院」→「完了」。そして日時の変更・キャンセルもきちんと通知が届き、空いた枠がまた予約できる——この一周が本番の環境で通ったことになります。

⚠公開前に必ず終わらせること

① 法定ページ(プライバシーポリシー・利用規約)の本文確定と専門家の確認。② このチェックで作ったテスト予約のキャンセルとテスト患者の削除。この 2 つは、上の一周が通っていても別途必ず終わらせてください。

網羅的な検証(全 219 ケース / P0 86 件)は docs/20_受け入れテスト/ 側で行います。中核業務だけを縦断で通す実行台帳は 00_最優先MVPパス.md です。
