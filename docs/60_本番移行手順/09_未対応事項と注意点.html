A. 本番前に必ず対応すべき事項(いま残っているもの)

残っているのは次の 5 件です。上の 2 件は公開前に必ず、続く 2 件は条件つき(その運用をしないなら関係ありません)、最後の 1 件はプログラムは対応済みで、設定を 1 つ入れるだけです。

⚠A-1. 法定ページ(利用規約・プライバシーポリシー)の本文確定と弁護士確認 開発担当者

利用規約とプライバシーポリシーは、標準的な構成(目次つき)の「暫定版」までは整備済みです。見栄えの整ったページとして表示されます。ただし、

  • ページ内に「正式公開前の暫定版です」と明記された注意書きが入っています
  • 事業者情報・委託先・お問い合わせ窓口などは仮の記載(プレースホルダ)のままです
  • 弁護士の確認は受けていません

今回は患者向けの公開Web予約を使う方針のため、これらのページは患者が必ず目にします。仮の記載を実際の内容に置き換え、弁護士の確認を受けた正式版に差し替えるまで、患者への案内(公開)を開始しないでください。医療広告および診療情報の取扱いに関する条項の確認も必要です。差し替え作業は開発担当者に依頼してください(対象はアプリ内の /privacy と /terms の 2 ページです)。

⚠A-2. 不正アクセス対策(レート制限)が未実装

レート制限とは、「同じ相手からの短時間の連続アクセスを制限し、機械的ないたずらを止める仕組み」です。現在、ログイン・公開予約の申し込み・予約の照会に、この回数制限がありません。パスワードを機械的に試す攻撃や、いたずらの連続送信を受ける可能性があります。

公開Web予約を使う方針のため、当面は次の緩和策で運用します(実装は次の開発段階の候補です)。

  • 承認モードを「院内で確認してから確定」(手動承認)にしておく — これが最も効きます。いたずらの申し込みが入っても、院内が承認するまで予約は確定しません。
  • Vercel・Supabase が標準で備えるアクセス保護に依存する状態であることを理解しておく(専用の追加対策は入っていません)。
  • 不自然な増え方に気づける運用にする — 台帳に見覚えのない予約が急に増える、同じ連絡先から何件も申し込みが来る、といった兆候を毎日の台帳確認で見ます。設定画面の「通知の送信状況」(STEP 8 参照)も手がかりになります。
  • おかしいときは一時的に止められる — 設定 → オンライン予約 の「患者向けオンライン予約」をオフにすれば、公開ページからの申し込みを即座に止められます(院内での予約登録は続けられます)。
  • 明らかな悪用が続く場合は、開発担当者にレート制限の実装を依頼してください。

ⓘA-3.【条件つき】公開予約を「自動確定」にする場合の仕組みが未実装

設定画面の「Web 予約の確定方法」で選べるのは 「院内で確認してから確定(推奨)」 だけです。かつてあった 「メール確認後に自動確定」 は、その前提となる「患者がメールの確認リンクを踏んで初めて確定する」「一定時間(30 分)内に確認されなければ枠を自動で解放する」仕組みが未実装で、選ぶと申し込みと同時に確定になってしまうため、選択肢から削除しました。

そのため、いまは「院内で確認してから確定」以外を選べません。今回の推奨運用もこちらです。将来「自動確定に切り替えたい」と判断したときは、上記の仕組みの追加実装(と選択肢の復活)を開発担当者へ依頼してください。

ⓘA-4.【条件つき】重複した患者どうしの統合(マージ)が未実装

公開Web予約は、はじめは患者マスタ(患者の台帳)と結び付いていない状態で入ります。これを既存の患者に結び付ける機能(名寄せ)は実装済みで、台帳から数クリックで行えます(下の「使い方」参照)。

一方、すでに患者マスタに二重登録されてしまった患者を 1 件にまとめる機能はありません。運用でこう防いでください。

  • 紐付けのときに表示される候補一覧をよく確認し、同じ人を新規で作らない。
  • 誤って二重に作ってしまったら、片方の患者にメモを残して以後は使わないようにする。

なお、以前あった危険な統合処理(取り消しのきかない上書き)は削除済みです。勝手に統合されてデータが失われることはありません。

✓A-5. 異常検知(エラー監視・定期実行の死活監視)は対応済み — 残るは SENTRY_DSN の登録だけ

受け入れテストの時点では、メールの送信失敗以外に異常を知る手段がありませんでした(500 エラーが出続けていても、定期実行が止まっていても、誰も気づけない状態)。この点はプログラム側の対応が完了しています。

  • サーバー側のエラー — 画面表示・予約登録・メール送信などで例外が起きると、自動で監視サービス(Sentry)へ記録・通知されます。
  • 定期実行(リマインダー・メール送信)の停止 — 実行のたびに「動きました」と報告し、2 回続けて報告が来ないと通知されます(およそ 2 時間止まったら気づけます)。

残っている作業は環境変数 SENTRY_DSN を 1 つ登録することだけです。手順は STEP 3 の 3-7(無料アカウント作成 → プロジェクト作成 → DSN をコピー → Vercel に登録 → 再デプロイ。10 分程度)、見方は STEP 5 の 5-7 と STEP 8 の 8-2 です。

登録しないと「気づけない」状態のまま公開することになります。SENTRY_DSN が未設定でもアプリの動きは一切変わりません(監視の処理は完全に停止します)。つまり未設定は「動くが気づけない」という状態です。運用開始直後こそ不具合が出やすいため、公開前に登録しておくことを強く推奨します。

なお、次の 3 つは今回も自動通知の対象外です。当面は運用でカバーしてください: データベースの容量枯渇(Supabase の通知設定で補う)/ 予約データの不整合(日々の台帳確認)/ 不審なアクセスの急増(A-2 の緩和策と台帳確認)。

C. まとめ: 推奨する始め方

✓『公開Web予約はオン・承認は院内の手動承認・問診は紙』で始める

この形が今回の推奨運用です。次の流れがひと通り成立します。

患者が Web から申し込む(または看護師が電話予約を台帳に入れる) → 院内に通知が届く → 台帳で内容を確認して「確定にする」 → 患者に確定メール → 前日にリマインダー → 当日「受付(チェックイン)」→「施術完了」。キャンセルすれば枠は自動で空きに戻ります。

手動承認にする理由: いたずらや入力間違いの申し込みが、院内の確認なしに確定枠になることを防げます。レート制限が未実装(A-2)の状態でも、被害を「確認して却下すれば済む」範囲に抑えられます。

⚠患者への案内(公開)を始める前に、必ず片付ける 3 つ

  1. 法定ページの本文確定と弁護士確認(A-1)利用規約・プライバシーポリシーの仮の記載を実際の内容に差し替え、法務確認を受けます。これが終わるまで公開しないでください。
  2. メールのドメイン認証と差出人アドレスの設定(STEP 4)ドメイン認証(SPF / DKIM = 「このクリニックが本当に送ったメールだ」と証明する設定)を済ませ、EMAIL_FROM_ADDRESS に認証済みドメインの差出人(例: reserve@クリニックのドメイン)を登録します。未設定のままだとメール配信サービスの共有テスト用アドレスから送られ、迷惑メールに入りやすくなります。
  3. CRON_SECRET と APP_URL の設定(STEP 3・STEP 5)CRON_SECRET が未設定だと定期実行がすべて拒否され、リマインダーも通知メールも一切送られません(安全側に倒す設計です)。APP_URL が未設定だと本番アプリがそもそも起動しません(メール内のリンクが開発用アドレスを指す事故を防ぐための仕様です)。

この形での進め方(順番)

  1. STEP 1〜5 を済ませるアカウント準備・データベース構築・アプリの公開・メール送信・定期実行の確認まで。
  2. STEP 6 で初期データを登録する院長・看護師・メニュー・部屋・担当・施術枠まで。
  3. 院内通知の宛先を登録する設定 → 基本情報 の「メール」欄に、毎日必ず見るクリニックのアドレスを入れます。ここが公開予約の通知先になります。
  4. 公開予約をオンにする設定 → オンライン予約 で「患者向けオンライン予約」をオンにし、「Web 予約の確定方法」を「院内で確認してから確定(推奨)」に、「患者キャンセル期限(時間前まで)」をクリニックの方針に合わせて決めます。
  5. STEP 7 で通しの確認をするとくに「公開ページから申し込む → 院内に通知が届く → 『確定にする』→ 患者に確定メールが届く」までを実際に確認します。
  6. 上の『必ず片付ける 3 つ』が済んでから案内を始めるクリニックの Web サイトや SNS への予約リンク掲載は、ここまで終わってからにします。
  7. STEP 8 の定期チェックを運用に組み込む承認待ちの放置がないか・Sentry の新規エラー(A-5)を日次で、通知の送信状況・バックアップを週次で確認します。
