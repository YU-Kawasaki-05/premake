## 2. 重要な判断とその理由

1. **旧仕様(88機能のマッチングプラットフォーム)を凍結し、v2(26機能の単院向け予約管理)を新設**。弁護士見解(6/7)でプラットフォーム型業務委託スキーム自体にリスク指摘があり、6/28 pivot 検討とも整合。旧 docs は参照資産に格下げ。
2. **単院・院内ツール化により premake は純粋なソフトウェアベンダーになる**(職業紹介・派遣・募集情報等提供に非該当、決済も患者→クリニック直接)。残る法務論点は医療広告(公開ページ)と医療情報の安全管理のみ。
3. **User 回答による仕様確定**: ①施術は雇用看護師中心+業務委託の人もいる可能性(→ スタッフに雇用区分属性)、②患者予約+院内管理+**看護師の場所予約(施術枠確保)**の3層、③決済なし(料金表示はフラグ制御)、④全メニュー対応(メニュー抽象化)。
4. **患者向け公開予約はテナント設定でオン/オフ**(User「患者の予約を受け付けるかまだ微妙」を吸収。オフでも院内管理として完結)。
5. **マルチテナント + メニュー抽象化を最初から**(User「拡張しやすく」)。6/28 の本命 B(メーカー試験)/M(クロスセル)に同じ器を流用可能な設計。
6. **RLS はデフォルト拒否・anon ポリシーなし**。ゲスト導線(公開予約・問診)は Server + service role + トークン検証で実装する方針。

## 4. つまずきと対処(次回のための記録)

| 問題 | 対処 |
|---|---|
| Next.js 16 は破壊的変更あり(middleware→proxy、async request APIs 完全移行、revalidateTag 第2引数) | `node_modules/next/dist/docs/` の v16 ガイドを精読し AGENTS.md に差分を記録 |
| `supabase start` が analytics コンテナ unhealthy で失敗(WSL2 定番) | `config.toml` で `[analytics] enabled = false` |
| service_role の insert が 42501(insufficient_privilege) | **`app` スキーマ(トリガー関数置き場)に `grant usage` が漏れていた**。制約検証テストで発覚 → マイグレーションに grant 追記 |
| `@supabase/realtime-js` が Node 22+ の WebSocket を要求(Node 20.19 で落ちる) | nvm で Node 22.23.1 導入、`.nvmrc`=22、`engines.node>=22`。**User の nvm default は変更していない**(下記依頼参照) |
| shadcn 新 CLI はプリセット制(`-b radix -p vega`) | components.json は radix-vega。ui コンポーネントは biome の lint 対象外に |
