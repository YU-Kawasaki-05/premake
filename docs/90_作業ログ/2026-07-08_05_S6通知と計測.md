## 1. 実装内容

### 通知基盤(v2-23)
- `lib/email.ts` — Resend 送信。`RESEND_API_KEY` 未設定(開発)はログ出力のみで成功扱い。
- `features/notifications/templates.ts` — 確定/受付/キャンセル/リマインダーの件名・HTML。
- `features/notifications/enqueue.ts` — `notifications` テーブルへ status=queued で積む(送信失敗が予約処理を止めないよう分離)。
- 予約イベントに配線: 院内確定(createBooking)/ ゲスト確定・受付(createGuestBooking)/ キャンセル(cancelBooking)。

### リマインダー + Cron(v2-24)
- `app/api/cron/route.ts`(GET, `CRON_SECRET` で Bearer 認可):
  1. 前日リマインダー走査(翌日の confirmed 予約で未リマインドのものを enqueue)
  2. queued 通知の送信(コンテキスト構築 → 管理リンク用トークン再発行 → メール送信 → status 更新)
- `vercel.json` に毎時 Cron(`0 * * * *`)を登録。

### 利用計測(v2-26)
- `app/ops/metrics/page.tsx` — 直近7日の KPI(アクティブ日数 / 予約数 Web・電話別 / キャンセル率)。アクティブ日数 < 2 は撤退シグナルとして赤表示。検証設計(Kill/Doubledown)と直結。

### 法定ページ
- `(public)/privacy` / `(public)/terms` — β暫定。公開ページのフッターからリンク。「施術はクリニックが提供」「本サービスは予約支援ソフト」を明記(医療提供主体の分離)。

## 3. 既知の制約・運用メモ

- **本番前提**: `RESEND_API_KEY`(送信元ドメイン認証)、`CRON_SECRET`(Vercel Cron 認可)を設定。未設定でもアプリは動作し、メールはログのみ。
- Cron の実挙動(送信・リマインダー)はサンドボックスのサーバー起動制約で E2E 未実施。ロジックは build/type + DB スキーマで検証。ローカルでは `curl localhost:3000/api/cron` で手動実行可能(dev は認可スキップ)。
- 送信元は現状 `onboarding@resend.dev`。本番はクリニックドメインの認証済みアドレスに差し替え。
