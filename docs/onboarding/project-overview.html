Team Brief · チーム共有用

premake とは何で、いま何を賭け、どう確かめるのか

クリニックの自由診療予約を、規制対応込みで一気通貫に管理する院内 SaaS。第一弾はアートメイク、器は業種非依存。

このページは、もう一人の仲間がプロジェクトの事業の狙い・意思決定の経緯・検証の進め方・技術構成・見るべき場所を一気に掴むためのブリーフです。実装は MVP(S0〜S6)が完了し main にマージ済み。ここからは「本番投入」と「事業としての検証」に入ります。

MVP 実装完了(v2-01〜26) 検証フェーズへ移行 対象: 実在クリニック1院 → 紹介で2〜3院
01 — 経緯

なぜ「単院向け」に舵を切ったか

当初は別の構想だった。2つの転機(弁護士見解と事業レビュー)を経て、いまの形に着地している。ここを共有しておかないと「なぜこの設計なのか」が伝わらない。

弁護士見解(6/7)

「Webプラットフォーム経由の業務委託看護師の派遣」はスキーム自体が禁止される可能性を内包。患者→premake の支払いフローも職安法上むずかしい。→ マッチング/派遣型は断念。

6/28 の結論

賭けるべきは「空き部屋」ではなく医師の信頼・時間と既存の美容顧客。アートメイクは“売り物”でなく“入口”。純粋な予約SaaS単体は競合が密で勝てない。

いまの立ち位置 premake は医療提供主体にならない院内業務ツール。マッチングも決済代理受領も施術者斡旋もしない。この整理により、旧構想で問題になった法的リスク(職業紹介・派遣・募集情報等提供)が発生しない。
02 — 戦略

何に賭け、器をどこへ伸ばすか

アートメイクは第一弾であって目的ではない。予約・患者・メニューの「器」を業種非依存に作り、信頼のある医師ネットワークを足がかりに用途を広げる。

これから改めて調べたいこと マネタイズ本命の B(化粧品・美容機器メーカーの臨床評価/モニター試験の会場提供) は、需要・支払額・規制(GCP該当性)・競合を別途しっかりリサーチして詰める予定。器の拡張は過剰設計せず、リサーチ結果を待って判断する。
03 — 事業方針

合意済みの事業方針

これまでの検討で決まった/同意したこと。チームの共通前提として突き合わせたい。

論点決めたこと
商業条件無償提供は避ける(支払意思の検証を放棄しないため)。実際に使って売上・価値が出たら有償化。
マネタイズ本命メーカー試験の会場提供(B)。他候補も継続探索(要リサーチ)。
撤退/全振り判断導入後 4週で判断(下の「検証」参照)。
展開紹介で 2〜3院。運営手動もありつつ、オンボーディング UI を作り込む。
公開ページ症例写真・スタッフ指名まで出す想定 → 医療広告の限定解除対応が必須。
電子カルテGMO 等競合が強く本格参入しない。指示書に絞り、記録はログとして残す。
患者連絡LINE + メール(LINE の優先度を上げる)。MVP はメール、LINE は早期 Phase 2。
弁護士顧問でなく論点を絞ったスポット相談。
04 — 検証

どう確かめるか(ここが本題)

「作ったから成功」ではない。1院で実運用に載せ、本当に使われるか・お金が出るか・器が伸びるかを測る。KPI は運営画面(ops/metrics)に実装済み。

検証したい仮説

仮説測り方(システムに実装済み)
H1 予約管理は実ペイン(あれば嬉しい、でなく無いと困る)週次アクティブ日数、システム外(電話→手入力)の残存
H2 患者はオンライン予約を使う公開ページ経由の予約比率
H3 有償でも使い続ける(WTP)継続利用 + 商業条件の合意
H4 器は他用途へ伸びるクリニックからの拡張要望(B/M 方向)

4週間後の判断ライン

▼ Kill(撤退を検討)

4週たっても週次利用が定着しない(受付が紙/既存運用に戻る)。医師がどの拡張にも乗らない。

▲ Double-down(全振り)

日次利用が定着し、クリニックから拡張要望(スタッフ追加・他メニュー・集客系)が自発的に出て、有償化に合意。

運営ダッシュボード /ops/metrics に、クリニック別のアクティブ日数・予約数(Web/電話別)・キャンセル率を直近7日で表示。アクティブ日数が週2日未満なら赤=撤退シグナルとして出る。
05 — 機能

プロダクトの全体像

院内スタッフが使う管理面と、患者が使う公開面の2層。決済は MVP では扱わず(料金表示のみ)、無断キャンセル対策のデポジットは Phase 2 でリスクベース導入。

院内(スタッフ)

予約台帳・オペレーション

予約台帳(部屋×時間グリッド)/ 施術枠の確保(看護師が自分の枠を作る)/ 予約作成・ステータス(来院・完了・無断)・キャンセル / 患者マスタ・履歴・名寄せ / メニュー・部屋・担当・問診テンプレ / スタッフ・クリニック設定。

公開(患者)

オンライン予約

クリニック公開ページ(医療広告に配慮した最小構成)/ 空き枠から予約 / 予約番号+メールで照会・キャンセル(ログイン不要・トークン)/ 問診記入。テナント設定でオン/オフでき、オフでも院内管理として完結。

06 — 技術

技術構成とセキュリティ

医療情報を扱うため、認可を3層で重ねる。患者データはクリニック単位(マルチテナント)で厳密に分離する。

スタック

Next.js 16(App Router)/ TypeScript / Supabase(Postgres・Auth・RLS)/ Tailwind v4 + shadcn/ui / Biome / Vitest / Resend(メール)/ Vercel Cron(リマインダー)。Node 22 必須。

堅牢性の要点

予約二重取りは DB の排他制約で防止。ステータス遷移はサーバーで状態機械として強制。患者情報・問診の閲覧は監査ログ化。検索インジェクション対策済み。トークンはハッシュ保存。

※ 品質は各スプリントで typecheck / lint / build / DB制約テストを実測。S1・S3 は敵対的レビューを実施し重大指摘を修正済み(docs/25_品質記録)。ブラウザE2Eのみローカルでの実施が残タスク。

08 — 現在地

ここまでと、これから

MVP は完了。次は本番投入と、1院での実地検証。並行して事業側(特に B のリサーチ)を詰める。

Done

MVP 実装(S0〜S6)

基盤・認証・メニュー/枠・予約台帳・患者・公開予約・通知/計測。main マージ済み・全検証 green。

Now

本番投入の準備

ローカルでのブラウザ E2E / 手動 QA、本番インフラ(Supabase/Vercel/Resend)、レート制限、owner不在ガードの DB 化、弁護士スポット確認。

Next

1院で実地検証(4週)

実運用に載せ、KPI(アクティブ日数・予約経路・キャンセル率)で Kill/Double-down を判断。

Then

Phase 2 / 事業拡張

LINE連携・症例ギャラリー・指示書電子化・デポジット決済・2院目オンボ。B(メーカー試験)のリサーチを別途走らせ器の拡張を判断。

まだ詰めきれていない論点(突き合わせたい)

  • 導入クリニックの実態 — 規模(スタッフ/施術室数・月間件数)、実際のメニュー構成。シードを実データに差し替える。
  • LINE 連携の要否と優先度 — 患者連絡の主力になるなら早期に。
  • 商業条件の具体 — 何をもって「価値が出た」とし、いくらでどう課金するか。
  • B のリサーチ設計 — 需要・支払額・規制・競合。別途しっかり調査。
