premake を動かす・公開するための手順

コードは実装済みです。ここでは「あなたの手で」やる必要がある設定だけを、順番どおりに並べました。① まず手元で動かす → ② 本番サービスを用意 → ③ Vercel に公開、の3段階です。

実装 S0〜S6 完了・main マージ済み 所要: ローカル 20分 / 本番 1〜2時間 要 GitHub アクセス権

はじめに — 全体像

3つのステージ。まず 1 だけで「動くものを自分の目で確認」できます。本番公開(2〜3)は落ち着いてからで大丈夫です。

ステージやることこれが終わると
① ローカル手元の PC で起動して触る全機能を自分で動作確認できる
② 本番サービスSupabase / Resend を用意本番のデータベース・メール基盤ができる
③ 公開Vercel にデプロイURL でアクセスできる本番サイトになる
前提ツール(ローカル用) Node.js 22(必須・22 未満だと起動しません)、pnpm、Docker Desktop(ローカル DB 用)。macOS なら brew install node@22 pnpm と Docker Desktop アプリ。

ステージ①　ローカルで動かす

まずは手元で。ここまでで全機能(予約台帳・公開予約など)を触って確認できます。

  1. リポジトリを取得して依存をインストール
    ~5 min 
    # リポジトリを clone(すでにあればスキップ)
git clone https://github.com/YU-Kawasaki-05/premake.git
cd premake

# Node 22 に切り替え(.nvmrc があるので nvm use でOK)
nvm use          # 22 が無ければ: nvm install 22
pnpm install
  2. ローカルの Supabase(DB)を起動
    ~5 min(初回はイメージ取得で長め)
    なぜ: 予約・患者などのデータを保存する PostgreSQL を、Docker で手元に立てます。
    pnpm db:start

    起動すると API URL と各キーが表示されます。その値を .env.local に書きます:

    # .env.example をコピーして編集
cp .env.example .env.local
# db:start の出力から下記3つを転記
#  NEXT_PUBLIC_SUPABASE_URL      = API URL
#  NEXT_PUBLIC_SUPABASE_ANON_KEY = anon key
#  SUPABASE_SERVICE_ROLE_KEY     = service_role key
  3. スキーマとサンプルデータを投入
    ~1 min
    なぜ: テーブル・権限(RLS)・デモクリニックのサンプルを一括で作ります。
    pnpm db:reset
  4. 開発サーバーを起動して触る
    ~1 min 
    pnpm dev
# ブラウザで http://localhost:3000 を開く

    デモ用のログイン(パスワードはすべて premake-dev):

    役割メール入口
    運営(ops)ops@premake.local/ops でクリニック作成
    院長(owner)owner@demo.local/demo で全機能
    看護師(staff)nurse1@demo.local施術枠・予約台帳
    確認するとよい流れ owner でログイン → メニュー/部屋/施術枠を確認 → 予約台帳で新規予約 → クリニック設定で「オンライン予約」をオンに → /c/demo(公開ページ)から患者として予約 → 予約番号の管理リンクでキャンセル。
補足 メール(確認・リマインダー)はローカルでは実送信されず、サーバーのログに出るだけです(RESEND_API_KEY 未設定のため)。本番では送信されます。

ステージ②　本番サービスを用意

公開に必要な外部サービスを作り、キーを控えます。ここで集めた値を次のステージ③で Vercel に登録します。

  1. 本番用 Supabase プロジェクトを作成
    ~20 min
    なぜ: 本番のデータベース・ログイン基盤です。Region は Tokyo (ap-northeast-1) を選んでください(患者データを国内に)。

    手順:

    • supabase.com で新規プロジェクト作成(Region: Northeast Asia / Tokyo)
    • Project Settings → API から Project URL / anon key / service_role key を控える
    • 手元からスキーマを反映(CLI):
    # 本番プロジェクトに接続してマイグレーションを反映
npx supabase link --project-ref <あなたのプロジェクトref>
npx supabase db push
    重要 service_role key は全データにアクセスできる最重要の秘密鍵です。ソースコードや Slack に貼らないでください。登録先は Vercel の環境変数(サーバー側)だけです。
  2. Resend(メール送信)を用意
    ~15 min(DNS 反映待ち含む)
    なぜ: 予約確認・前日リマインダーのメール送信に使います。未設定でもアプリは動きますが、メールは飛びません。
    • resend.com でアカウント作成
    • 送信元にするドメインを追加し、表示される DNS レコードを登録して認証
    • API Key を発行して控える(RESEND_API_KEY)
    後まわし可 ドメイン認証は時間がかかることがあります。メール無しでまず公開し、あとから設定を足しても構いません。その場合はコード内の送信元アドレス(src/lib/email.ts の FROM)を認証済みドメインに変更してください。
  3. Cron 用の秘密文字列を生成
    ~1 min
    なぜ: リマインダーを自動送信する定期実行(Cron)を、外部から叩かれないよう保護するための合言葉です。
    openssl rand -hex 32
# 出た文字列を CRON_SECRET として控える

ステージ③　Vercel に公開

GitHub リポジトリを Vercel に繋ぎ、環境変数を登録すればデプロイされます。Cron は vercel.json で自動設定されます。

  1. Vercel にリポジトリをインポート
    ~10 min
    • vercel.com/new で YU-Kawasaki-05/premake をインポート
    • Framework は Next.js が自動検出される(そのまま)
  2. 環境変数を登録
    ~5 min
    なぜ: アプリが本番 DB・メールに接続するための設定です。ステージ②で控えた値を入れます。
    変数名値必須
    NEXT_PUBLIC_SUPABASE_URL本番 Supabase の Project URL必須
    NEXT_PUBLIC_SUPABASE_ANON_KEY本番の anon key必須
    SUPABASE_SERVICE_ROLE_KEY本番の service_role key(秘密)必須
    APP_URL公開 URL(例 https://premake.vercel.app)必須
    RESEND_API_KEYResend の API キー任意(メール送信時)
    CRON_SECRET生成した秘密文字列任意(推奨)
  3. デプロイして動作確認
    ~10 min

    Deploy を実行 → 発行された URL を開く。運営アカウントを作って(下記メモ参照)、クリニックを作成し、招待リンクを院長へ渡します。

    運営アカウントの作り方 本番にはデモの ops アカウントはありません。① 通常サインアップでアカウントを作る → ② Supabase の Table Editor で profiles の自分の行の is_ops を true にする、で運営になれます。

公開前に確認したいこと

技術ではなく運用・法務の観点。特に患者向け公開ページを本格運用する前に。

  • 弁護士スポット相談 — 公開ページの医療広告(症例写真を出す場合の「限定解除」要件)と、premake が診療情報を預かる立場の契約条項。
  • 公開ページの内容 — 現状は症例写真なし・自由診療の注意書きありの最小構成。症例やスタッフ指名を出す場合は上記確認後に。
  • クリニックとの利用契約 — 個人情報・診療情報の取扱いを含む簡易な契約書。
詳しくは 本番投入前の残タスク一式は docs/30_申し送り/S2以降_申し送り.md に、法務の論点は docs/10_v2_仕様/05_主要設計論点.md にまとまっています。

よく使うコマンド

コマンド用途
pnpm dev開発サーバー起動(localhost:3000)
pnpm db:start / db:stopローカル DB の起動 / 停止
pnpm db:resetローカル DB を初期化(スキーマ+サンプル)
pnpm typecheck / lint / build型 / 整形 / 本番ビルド確認
pnpm test:dbDB 制約テスト(要ローカル DB)

困ったら Node が 22 か Docker が起動しているか .env.local を書いたか の3つをまず確認してください。
